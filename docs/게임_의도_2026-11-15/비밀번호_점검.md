비밀번호를 만들고·넣고·잊고·바꾸는 모든 길을 코드로 읽어, 의도와 다르게 도는 곳·사람이 막히는 곳·보안 빈틈·정해야 할 것을 모은 글임. 코드·시험·설정은 하나도 안 고침.

## 1. 흐름마다 지금 동작

이 장은 "지금 코드가 실제로 어떻게 도는지"를 단계 번호로 적음. 숫자는 전부 코드 기본값(환경값(.env)으로 바꿀 수 있는 것은 이름만 적음).

### 1-1. 비밀번호 규칙과 저장

| 규칙 | 값 | 근거 |
|---|---|---|
| 길이 | 8~64자 | 서버 `validations/auth/signup.js:10-11,75`, 화면 `frontend/src/domains/auth/validation/signupValidation.js:10-11,101` |
| 바이트 상한 | 72바이트 (bcrypt(비번 해시 방식)가 72바이트 뒤를 버려서) | 서버 `signup.js:12,78`, 화면 `signupValidation.js:12,104` |
| 글자 종류 | 규칙 없음 (숫자만·영문만 됨) | 위 두 파일에 종류 검사 없음 |
| 앞뒤 빈칸 | 안 자름 (로그인·가입·재설정 모두 원문 그대로) | `signup.js:70`, 시험 이름 "비밀번호를 trim하지 않는다" |

| 저장 | bcrypt 세기(cost) 10, 원문 안 남음 | `utils/auth/credentials.js:7-9` |

### 1-2. 가입 (사용자가 직접 짠 화면)

1. 가입 칸: 이메일·중복확인·비번·비번 확인·닉네임·생일 — PC `SignupFields.jsx:21-86`, 모바일 `signup/SignupFields.jsx`
   - 비번 두 칸 다 보기 단추 있음, `autoComplete="new-password"`
   - 비번 칸 안내 글은 "비밀번호를 입력하세요"뿐 (규칙 없음) — 닉네임 칸은 "(2~8자, 한글/영문/숫자)" 있음
2. 가입 누름 → 화면 검사(`useLoginSubmit.js:27-31`) → 막히면 `alert` (PC는 브라우저 알림, 모바일은 양피지 창으로 바꿔 띄움 `parchmentAlert.js:64`)
3. 서버 `POST /auth/signup`(`routes/auth.routes.js:34`) → 같은 검사 → 이메일 인증 증명 확인 → 약관 → 해시 → 한 덩어리 처리(트랜잭션)로 계정 만들기 — `services/auth/account/signup.js:18-79`
4. 성공 → "회원가입이 완료되었습니다! 로그인해주세요." → 로그인 모드로 (`useLoginSubmit.js:59-62`)

### 1-3. 로그인 (사용자가 직접 짠 화면)

1. 이메일·비번 넣고 로그인 → `POST /auth/login` (ip당 10분 50번 제한 `LOGIN_IP_MAX`·`LOGIN_IP_WINDOW_MS`, `authRateLimit.middleware.js:100-105`; 문서 기준 nginx 1분 10번도 있음)
2. 빈 값·글자 아님 → 400 "이메일과 비밀번호를 입력해주세요." (`login.js:31-33`)
3. 계정 행 잠그고 찾기(`login.js:38`)
   - 없는 이메일 → 가짜 해시와 한 번 비교(응답 시간 맞추기) → 401 "이메일 또는 비밀번호가 일치하지 않습니다." (`login.js:39-42`)
4. 잠금 시간 안이면 → 비번 안 보고 423 "비밀번호 연속 오류로 계정이 잠겼습니다. 잠시 후 다시 시도해주세요." — **맞는 비번이어도 거절, 기록·셈 안 함** (`login.js:46-48`)
5. 비번 비교 → 맞든 틀리든 로그인 기록(`login_history`) 남김 (`login.js:52-61`)
6. 틀림 → 실패 횟수 +1 (`users.failed_login_count`)
   - 1~4번째: 401 같은 문구 (`login.js:76`)
   - 5번째: `users.locked_until` = 지금+15분, 423 "비밀번호를 5회 잘못 입력하여 15분간 계정이 잠깁니다." (`login.js:12-13,66-75`)
   - 잠금이 끝난 계정은 0부터 셈 (`login.js:50`)
   - **잠금이 없으면 실패 횟수는 성공하기 전까지 시간이 지나도 안 줄어듦** (`login.js:50`, 5장 P-Q1)
7. 맞음 → 정지면 세션 끊고 403(사유 보임) → 계정 상태가 ACTIVE 아니면 403 → 실패 횟수 0·잠금 지움 → 앞 세션 전부 끊고 새 세션 (`login.js:80-100`, `account/session.js:12`)
8. 화면: 401·423·429 문구를 그대로 알림 (`useLoginSubmit.js:79-81`). 로그인 401은 공통 401 처리기를 거치지만 `/login`은 공개 화면이라 튕기지 않고 문구만 (`domains/auth/api/unauthorized.js:6-22`)

- 잠금 저장 자리: DB `users` 표 두 칸 → 서버가 여러 대여도 같은 값 (서버 메모리 아님)
- ip 제한 셈: 서버 한 대면 메모리, 여러 대면 Redis로 합쳐 셈 (`rateLimit.middleware.js:9-12,75-83`)
- 소셜 로그인은 잠금을 안 봄 (`locked_until`을 읽는 곳이 `login.js`뿐)

### 1-5. 비밀번호 바꾸기 (로그인한 채, 계정 관리)

1. 칸 두 개: "현재 비밀번호", "새 비밀번호" — **확인 칸 없음**, 규칙 안내 없음 (PC `AccountPanel/PasswordSection.jsx:28-50`, 모바일 `account/PasswordSection.jsx:24-43`)
2. 화면은 빈칸만 막음, 규칙 검사는 서버에 맡김 (`usePasswordForm.js:31-32`)
3. `PATCH /user/me/password` (`routes/user.routes.js:43`, 경로 요청 수 제한 없음) → 글자 아님·빈 값 400 → 새 비번 규칙 400(서버 문구 그대로 보임) (`profile.controller.js:39-50`)
4. 현재 비번 틀린 횟수: 계정당 15분 창에 5번 → 6번째부터 비교 없이 429 "현재 비밀번호를 여러 번 잘못 입력했습니다…" (`account/password.js:10-12,18-20`, 셈은 서버 메모리, 여러 대면 Redis `attemptCounter.js:7-47`). 로그인 잠금과 따로 셈 (결정 BE-057)
5. 틀림 → 400 `CURRENT_PASSWORD_INVALID` (401 아니라 로그아웃 안 됨)
6. 맞음 → 새 해시 저장 + **지금 세션 포함 전부 끊음** → `reloginRequired: true` → 화면 "비밀번호가 변경되었습니다. 다시 로그인해 주세요." 1.5초 뒤 로그인 화면 (`password.js:28-31`, `usePasswordForm.js:45-47`)
7. 새 비번 = 지금 비번이어도 막지 않음 (검사 없음)
8. 소셜 전용 계정: 서버도 화면도 `has_local_password`를 안 봄 → 칸이 보이고, 무작위 비번과 비교라 늘 틀림 (P-B1). 설계상 소셜 계정에 비번을 새로 만들어 주지는 않음 (F-29 2-3a "소셜 전용 계정에 새 로컬 비밀번호를 발급하거나 계정을 병합하지 않는다")

### 1-6. 비번을 다시 묻는 다른 곳

| 곳 | 비번 있는 계정 | 소셜 전용 | 틀린 횟수 제한 | 근거 |
|---|---|---|---|---|
| 탈퇴 `POST /user/me/withdraw` | 비번 | 계정 이메일 그대로 다시 쓰기 | 비번 틀림 15분 5번 → 429 `WITHDRAW_LOCKED` + 경로 15분 10번 | `withdraw.js:14-26,60-62`, `user.routes.js:35-39` |
| 이메일 바꾸기 `POST /user/me/email/code` | 현재 비번 | 비번 없이 번호만 | **비번 틀림 셈 없음**, 경로 요청 1시간 5번만 | `emailChange/request.js:19-23`, `user.routes.js:24-28` |
| 계정 정보 `GET /user/me/account` | `{ email, hasLocalPassword }` → 위 두 칸이 칸 종류를 고름 | | | `controllers/auth/member.js:22-31`, `useWithdrawForm.js:30` |

- 탈퇴·이메일 바꾸기는 `hasLocalPassword`를 보고, 비번 바꾸기만 안 봄

### 1-7. 아이디(메일) 찾기

1. `/find-id`: 닉네임 + 생일 → `POST /auth/find-id` (ip 10분 10번, 같은 닉네임 10분 5번 `authRateLimit.middleware.js:45-58`)

3. 비번 재설정 요청은 이 표에 안 남김 (P-B2)

### 1-8. 관리자 비밀번호

1. 문 두 개: 클라우드플레어 Access(이메일 번호) → 아이디·비번·OTP(6자리 번호) 한 번에 (`admin/services/core/login.js:49-59`)
2. 틀리면 어느 칸인지 안 알려 줌, 없는 아이디도 가짜 해시 비교 (`login.js:20,28-33,51`)
3. 막힘: 같은 아이디 15분 안 5번 또는 같은 ip 15분 안 20번 틀리면 15분 막힘, 막힌 동안 맞는 값도 429 + 남은 분 안내 (`loginLock.js:10-13,60-67`, 화면 `admin/shared/api/errorText.js:27-28`)
   - 셈은 DB 표 `admin_login_attempts` → 서버 여러 대도 같은 수
   - 성공하면 아이디 셈 끊김, IP 셈은 안 끊김 (`loginLock.js:33-57`)
4. 계정 만들기·비번 다시 정하기·막힘 풀기는 명령으로만 (`npm run admin:account -- create|reset-password|unlock …`), 화면 없음 (`admin/scripts/admin-account.js:110-117`)
   - 비번 12자 이상·72바이트 이하, 두 번 물어 같아야 함, 친 글자 화면에 안 찍힘 (`admin-account.js:22-34,129-133,173-183`)
   - 비번 다시 정하면 그 관리자 세션 전부 끊음 (`admin-account.js:73-78`)
   - `password_changed_at`은 저장만 하고 읽는 곳 없음 (주기 변경 강제 없음)
5. 관리자 로그인 화면: 비번 칸 `type="password"`·`autoComplete="current-password"`, 보기 단추 없음, 오류는 `text-danger` 색 정해짐 (`frontend/src/admin/domains/auth/pages/LoginPage.jsx:61-65`)

### 1-9. 저장·전송에서 잘 된 것 (사실)

- 재설정 토큰: 32바이트 무작위, DB엔 sha256 해시만, 저장소 쿼리 로그 끔 (`tokens.js:8-11`, `repositories/auth/passwordResetToken.js:4-32`)
- refresh(로그인 유지 열쇠)도 DB엔 해시만 (`account/session.js:18-26`)
- 서버 요청 로그: 재설정·가입 경로는 뒤를 가림, 나머지도 쿼리 뺀 경로만 (`backend/index.js:87-92`), 로그 파일은 `password=`·`token=` 같은 값 가림 (`utils/logFile.js:23`)
- 재설정 응답 전부 `Cache-Control: no-store` (`controllers/auth/passwordReset.js:9,21,37`)
- 응답 본문에 비번 해시·토큰 없음 (지운 시험 "HTTP 로그인 성공: 토큰은 쿠키로만, 응답 본문엔 토큰·비번 해시 없음")
- 운영에서 SQL 로그 꺼짐 (`models/index.js:26-27`)
- 비번 바꾸기·재설정·탈퇴 뒤 세션·소켓 끊김

## 3. 사람이 막히는 길

### P-S1. 잠긴 사람이 재설정해도 잠금이 그대로
- 겪는 모습: 비번이 기억 안 나 5번 틀림 → 15분 잠김 → "비밀번호 찾기"로 바로 새 비번 → 새 비번으로 로그인 → 또 423 "계정이 잠겼습니다". 사람은 "재설정이 안 됐다"로 오해하기 쉬움
- 왜: `services/auth/passwordReset/confirm.js:59-60`이 `password_hash`만 바꿈, `failed_login_count`·`locked_until`은 안 건드림. 로그인은 잠금부터 봄(`login.js:46-48`)
- 다시 겪는 차례: 틀린 비번 ×5 → 재설정 메일 → 새 비번 저장 → 새 비번 로그인
- 얼마나 큰가: 보통 (최대 15분이면 풀림, 하지만 가장 흔한 "비번 잊음" 길 한가운데)
- 의도: 옛 설계엔 "계정 정지·권한 상태는 바꾸지 않는다"만 있고 잠금은 안 적힘 → 5장 P-Q2

### P-S2. 재설정 메일이 안 나가도 아무도 모름
- 겪는 모습: 사람은 "접수했어요"만 보고 메일을 기다림 → 안 옴 → 다시 보내기 3번 → 1시간 막힘. 운영자는 로그·표 어디에도 흔적이 없어 문제를 모름
- 왜:
  - `request.js:18-21` — 앱 주소(`PASSWORD_RESET_APP_URL`)가 없거나 http(s)가 아니면 메일을 아예 안 만듦, 로그 없음
  - `request.js:57-62` — 발송 결과(`{ ok: false }`)를 안 보고, 던져도 삼킴, 로그 없음 (주석: 응답이 달라지면 가입 여부가 드러나서)
  - 발송기도 실패 이유를 밖에 안 냄 (`mailSenders/smtp.js:34-42,63-75`)
  - 서버 시작 때 메일 설정 검사 없음
  - 이메일 바꾸기는 같은 발송기 실패를 503으로 알려 줌(`emailChange/request.js:79-87`) — 재설정만 깜깜
- 다시 겪는 차례: 운영 `.env`에 `PASSWORD_RESET_APP_URL` 빼고(또는 메일 비번 틀리게) 켬 → 재설정 요청
- 얼마나 큰가: 높음 — 설정 하나 빠지면 **모든 사람이** 비번을 못 찾고, 아무도 모름. Gmail 하루 한도 같은 바깥 이유도 같은 모양 (짐작)
- 고칠 곳 후보: 응답은 그대로 두고 서버 로그에 "재설정 메일 실패(이유 종류만, 주소 없이)" 한 줄, 운영 시작 때 메일 설정 빠짐 경고 (P-Q7)

### P-S3. "다시 보내기"가 먼저 온 링크를 죽임
- 겪는 모습: 접수 안내가 "메일이 보이지 않으면 … '다시 보내기'를 눌러주세요"라고 권함(`recoveryMessages.js:14`) → 누르면 앞 토큰 폐기(`request.js:41`) → 늦게 도착한 첫 메일 링크를 열면 "유효하지 않은 링크예요. 이메일에 있는 링크 주소를 다시 확인해주세요."(`recoveryMessages.js:24`) — 주소를 다시 봐도 소용없음. 메일 두 통 중 어느 것이 새것인지 모름
- 더해서: 같은 주소 1시간 3번(`authRateLimit.middleware.js:72-78`) → 4번째는 "너무 많은 요청입니다" 최대 1시간. PC는 "다시 보내기"에 기다림이 없음(`RequestPage.jsx:33`), 모바일도 보내는 중에만 막음
- 왜: 밀려난(폐기) 토큰도 없는 토큰과 같은 `INVALID`로 답함 (`confirm.js:21-22`, 일부러 — 주석 "새로 요청해 밀려난 토큰도 없는 토큰과 같게")
- 얼마나 큰가: 보통 (메일이 늦게 오는 날이면 흔함)
- 고칠 곳 후보: 5장 P-Q6

### P-S4. 비번 바꾸기에 확인 칸이 없음
- 겪는 모습: 새 비번을 한 글자 틀리게 침 → 서버는 그대로 저장 → 세션 전부 끊기고 1.5초 뒤 로그인 화면 → 자기가 친 새 비번을 모름 → 재설정 메일을 받아야만 들어옴 (메일이 안 오면 P-S2·P-S5로 갇힘)
- 왜: 칸 두 개뿐 (PC `PasswordSection.jsx:28-50`, 모바일 `PasswordSection.jsx:24-43`, 상태 `usePasswordForm.js:12`). 가입·재설정은 확인 칸이 있음. 서버 `PATCH /user/me/password`도 확인 값을 안 받음
- 얼마나 큰가: 보통 (보기 단추가 있지만 P-A1로 잘 안 보임)
- 고칠 곳 후보: 5장 P-Q4

### P-S5. 로그인 못 하는 사람이 연락할 길이 없음
- 겪는 모습: 메일이 안 옴·가입 이메일을 잊음(아이디 찾기는 가린 이메일만)·잠김 등으로 못 들어가는 사람이 도움을 청할 곳이 화면에 없음
- 왜: 문의는 `verifyToken`(로그인 확인) 뒤에만 (`routes/inquiry.routes.js:9-11`), 고객센터(디스코드) 링크는 로비 메뉴에만 (`lobby/constants/lobbyMenu.js` 등) — 로그인·찾기 화면엔 없음
- 얼마나 큰가: 보통 (P-S2·P-S4가 터지면 탈출구가 하나도 없음)
- 고칠 곳 후보: 5장 P-Q8

### P-S6. 소셜 전용 계정으로 비번 로그인하면 이유를 모름
- 겪는 모습: 구글로 가입한 사람이 이메일·비번 칸으로 로그인 → "이메일 또는 비밀번호가 일치하지 않습니다." → 5번이면 "비밀번호 연속 오류로 계정이 잠겼습니다"(비번이 원래 없는 계정인데)
- 왜: 소셜 가입은 무작위 비번 해시를 넣음(`social/signup.js:105-113`), 로그인은 `has_local_password`를 안 보고 비교·셈 (`login.js:52-75`)
- 탈출구는 있음: "비밀번호 찾기" → 소셜 로그인 안내 메일 (`request.js:13-16`) — 단 메일이 나가야 함
- 얼마나 큰가: 낮음 (가입 여부 숨기기 때문에 문구로 알려 주기는 어려움, 일부러일 수 있음)

## 4. 보안에서 걸리는 곳

### P-X1. 이메일만 알면 남의 계정을 15분씩 잠글 수 있음
- 무엇: 아무나 남의 이메일로 틀린 비번 5번 → 그 사람은 15분 비번 로그인 못 함, 15분마다 되풀이 가능
- 조건: 이메일을 앎 (가입 화면 중복 확인으로 있는지 확인 가능, ip 10분 20번)
- 얼마나 큰가: 낮음~보통. 결정 문서에서 알고 둔 것 (`버그수정_결정_2026-11-09.md:59` BE-009: "남의 계정 잠그기는 … 완전히는 못 막음", ip 10분 50번으로 줄임). 실패 횟수가 시간이 지나도 안 줄어(P-Q1) 4번을 미리 쌓아 두면 사람 오타 한 번에 잠기게 할 수도 있음
- 소셜 로그인은 안 막힘

### P-X2. 재설정 토큰이 주소에 실림
- 무엇: 메일 링크 `…/password-reset?token=…`과 확인 요청 `GET /auth/password-reset/verify?token=…`에 토큰 원문
  - 서버(Express) 로그는 가림 (사실, `index.js:87-92`)
  - nginx 설정엔 `access_log` 줄이 없음 → nginx 기본 접근 기록은 요청 줄 전체(쿼리 포함)를 남김 (nginx 기본 동작 기준 짐작, 실제 로그 안 봄)
  - 화면이 토큰을 읽은 뒤 주소창에서 안 지움 (`ResetPage.jsx:61`, 모바일 같음) → 브라우저 방문 기록·공유 PC에 남음
  - 다른 사이트로 나갈 때는 화면 nginx `Referrer-Policy: strict-origin-when-cross-origin`이라 주소 뒷부분 안 감 (`nginx/snippets/security-headers.conf:8`)
- 조건: 30분 안·아직 안 씀·로그나 기록을 볼 수 있는 사람
- 얼마나 큰가: 낮음 (한 번만 쓰이고 30분이면 끝, 흔한 방식)

### P-X3. 세션 훔친 사람의 비번 맞히기 기회가 곳마다 따로
- 무엇: 로그인 세션만 훔친 사람이 지금 비번을 맞혀 보는 길이 셋
  - 비번 바꾸기 15분 5번 (`password.js:10-12`)
  - 탈퇴 15분 5번 (`withdraw.js:14-16`)
  - 이메일 바꾸기: 비번 틀림 셈 없음, 번호 보내기 요청 1시간 5번만 (`emailChange/request.js:19-23`, `user.routes.js:24-28`)
  - 셋이 따로라 합치면 15분에 약 10번 + 1시간 5번
- 얼마나 큰가: 낮음 (세션을 먼저 훔쳐야 하고, 맞혀도 비번 바꾸면 세션이 끊김)

### P-X4. 비번 규칙이 길이뿐
- 무엇: 8자 이상이면 `12345678`·`password` 같은 흔한 비번도 됨. 흔한 비번 막기·이메일과 같은 비번 막기 없음 (`validations/auth/signup.js:71-82`)
- 얼마나 큰가: 낮음 (잠금 5번 + ip 제한이 있어 한 계정 맞히기는 느림, 여러 계정에 흔한 비번 뿌리기는 ip 10분 50번까지 가능) → 5장 P-Q5

### P-X5. 아이디 찾기로 가린 이메일이 나옴
- 무엇: 닉네임은 게임에서 누구나 봄, 생일만 맞히면 가린 이메일(첫 글자·끝 글자·도메인 첫 글자·끝 도메인) 나옴 (`accountRecovery.js:21-40`, 가리기 규칙 F-29 2-2)
- 조건: 같은 닉네임 10분 5번 → 하루 약 720번 시도, 생일 범위가 넓어 며칠 걸림 (계산 짐작)
- 얼마나 큰가: 낮음 (원문 이메일은 안 나옴, 설계대로)

### 정보 (문제 아님, 확인만)
- 재설정 요청: 있는 계정은 메일을 기다렸다 답해 응답이 조금 늦음 → 가입 여부 짐작 가능. 보안 점검 문서가 알고 둠 (`보안_점검_2026-11-09.md:22`)
- 5번째 잠금 423 문구는 있는 계정만 나옴 → 알고 둠 (`보안_점검_2026-11-09.md:16,43`)
- bcrypt 세기 10: 흔한 하한. 올리면 로그인마다 느려짐
- 관리자: 클라우드플레어 Access 뒤라 아이디 막기 괴롭힘은 거의 못 함. 로그인 칸은 200자까지 받지만 만드는 명령이 72바이트로 막아 잘림 문제 없음 (`admin/controllers/auth.controller.js:17`, `admin-account.js:33`)
- DB 표 `password_reset_tokens`에 옛 원문 칸 `token`이 남아 있으나 새로 안 채움, 옛 줄은 마이그레이션이 무효로 바꿈 (`passwordResetToken.model.js:7-8`, 설계 2-3)

## 5. 사용자가 정할 것

### P-Q1. 로그인 실패 횟수를 언제 0으로 돌리나
- 지금: 성공하거나 잠금이 끝날 때만 0. 한 달에 걸쳐 4번 틀려도 다음 한 번에 잠김 (`login.js:50`). 문구는 "연속 오류"
- 안 1: 지금대로 (성공 전까지 쌓임)
- 안 2: 첫 실패부터 15분 창 안에서만 셈 (관리자 로그인·비번 바꾸기·탈퇴가 이 방식)
- 안 3: 마지막 실패에서 하루 지나면 0
- 추천: 안 2 — 다른 세 곳과 같은 규칙, "15분에 5번"이라는 문서 말과도 맞음

### P-Q2. 재설정이 끝나면 로그인 잠금을 풀까
- 안 1: 지금대로 (잠금 남음, 최대 15분 기다림)
- 안 2: 재설정 성공 때 실패 횟수 0·잠금 지움
- 추천: 안 2 — 메일 링크를 쓴 것 자체가 본인 확인이고, 가장 흔한 "잊음 → 잠김 → 재설정" 길이 막히지 않음

### P-Q3. 소셜 전용 계정의 "비밀번호 변경" 칸
- 안 1: 칸 숨김 + "소셜 로그인 계정은 비밀번호가 없습니다" 한 줄
- 안 2: 칸 대신 "비밀번호 만들기"(현재 비번 없이 새 비번) — 옛 설계는 "새 로컬 비밀번호를 발급하지 않는다"라 설계 바꾸기
- 안 3: 지금대로
- 추천: 안 1 — 설계 그대로, 탈퇴·이메일 칸이 이미 이렇게 갈림

### P-Q4. 비번 바꾸기에 "새 비번 확인" 칸
- 안 1: 확인 칸 넣기 (화면만, 가입·재설정과 같은 검사)
- 안 2: 지금대로 + 보기 단추만 잘 보이게(P-A1)
- 추천: 안 1 — 틀리면 곧바로 세션이 끊겨 되돌릴 길이 메일뿐

### P-Q5. 비번 규칙을 더 세게 할까
- 안 1: 지금대로 8~64자
- 안 2: 영문+숫자 섞기 의무
- 안 3: 길이는 그대로 + 아주 흔한 비번 목록(수백 개)과 이메일 앞부분만 막기
- 추천: 안 3 — 외우기 부담은 그대로, 흔한 비번 뿌리기만 막음. 이미 가입한 사람은 다음 바꿀 때부터

### P-Q6. "다시 보내기" 때 먼저 보낸 링크
- 안 1: 지금대로 무효 + 문구만 고침 ("새로 요청했다면 가장 최근 메일의 링크를 써 주세요", 밀려난 링크는 따로 코드)
- 안 2: 30분 안에선 앞 링크도 살림 (한 사람 열린 링크 여러 개)
- 안 3: 다시 보내기에 1분 기다림 + 안 1
- 추천: 안 3 — 보안은 그대로, 헷갈림·한도 소진 둘 다 줄임

### P-Q7. 재설정 메일 실패를 어디에 남길까
- 안 1: 서버 로그에 한 줄 (실패 종류만, 주소·토큰 없이)
- 안 2: 안 1 + 운영 시작 때 메일 설정·앱 주소 빠짐 경고(또는 시작 거부)
- 안 3: 안 2 + 관리자 화면에 "최근 메일 실패 수"
- 추천: 안 2 — 응답은 그대로라 가입 여부 안 드러나고, 설정 빠짐을 배포 때 바로 앎

### P-Q8. 로그인 못 하는 사람의 연락 창구
- 안 1: 로그인·찾기 화면에 고객센터(디스코드) 링크
- 안 2: 로그인 없이 쓰는 문의 칸 (이메일 받음, 스팸 막기 필요)
- 안 3: 지금대로 없음
- 추천: 안 1 — 이미 있는 링크를 한 곳 더 두는 것뿐

## 6. 새 시험에 꼭 넣을 케이스 목록

이 장은 새로 짤 때 빠지면 안 되는 케이스를 겉으로 보이는 결과 기준으로 적음. 정답은 1장 동작·5장 결정에서. 끝에 [새]는 지운 옛 시험에도 없던 것.

### 가입
1. 비번 7자·65자·한글 25자(75바이트)는 화면에서 막히고 서버도 400 — 경계 8자·64자·한글 24자(72바이트)는 통과
2. 비번과 확인이 다르면 화면·서버 둘 다 거절
3. 비번 앞뒤 빈칸을 자르지 않음 (빈칸 붙인 비번으로 가입 → 같은 빈칸 붙여야 로그인)
4. 가입 비번 칸에 규칙 안내가 보임 [새, P-A3 결정 뒤]

### 로그인
5. 없는 이메일과 틀린 비번은 상태·문구가 똑같음 (가입 여부 안 드러남)
6. 1~4번째 틀림은 401 같은 문구, 5번째는 423 잠금 문구, 잠긴 동안 맞는 비번도 423
7. 잠긴 지 14분 59초는 423, 15분이면 맞는 비번으로 들어감
8. 잠금이 끝난 뒤 한 번 틀려도 바로 다시 안 잠김
9. 실패 횟수가 P-Q1 결정대로 시간이 지나면 줄어듦 [새]
10. 4번 틀린 뒤 맞으면 들어가고 셈이 0
11. 정지 계정: 비번 틀리면 보통 문구, 맞으면 정지 사유 403
12. 소셜 전용 계정으로 비번 로그인하면 보통 실패 문구 (그리고 P-Q1·P-S6 결정대로) [새]
13. 같은 ip 한도 넘으면 429 + 화면에 문구
14. 로그인 실패 뒤 화면이 로그인 화면에 그대로 있고 알림이 보임 (PC·모바일)

### 비밀번호 찾기(재설정)
15. 있는 이메일·없는 이메일·소셜 전용 이메일 셋 다 같은 200 + 같은 접수 안내
16. 있는 이메일 → 링크 메일 1통, 없는 이메일 → 0통, 소셜 전용 → 안내 메일 1통·토큰 없음
17. DB엔 토큰 해시만 (원문 없음), 30분 뒤 만료
18. 링크를 여러 번 열어도(verify) 토큰·비번·세션이 안 바뀜
19. 새 비번 저장 → 새 비번 로그인 됨, 옛 비번 안 됨, 다른 기기 세션·소켓 끊김
20. 같은 링크 두 번째 → USED 안내, 동시에 두 번 → 한 번만 성공
21. 만료 링크 → EXPIRED 안내 + 다시 요청하기, 열어 둔 사이 만료돼도 저장 때 EXPIRED
22. 다시 요청하면 앞 링크는 못 씀 + 안내 문구가 P-Q6 결정대로 [문구는 새]
23. 같은 주소 1시간 4번째·ip 1시간 11번째 → 429 안내
24. **5번 틀려 잠긴 계정이 재설정 뒤 새 비번으로 바로 들어감** (P-Q2 안 2일 때) [새]
25. 메일 발송 실패·앱 주소 없음이어도 응답은 같은 200, 그리고 서버 로그에 실패 한 줄(주소·토큰 없이) [새, P-Q7]
26. 토큰 없이·아무 글자 토큰·43자 아닌 토큰 → 유효하지 않은 링크 안내, DB 안 감
27. 로그아웃 상태에서 링크를 열면 로그인 화면으로 안 튕김 (PC·모바일)
28. 서버 로그·응답에 토큰 원문·이메일·새 비번이 안 남음, 응답은 `no-store`
29. 재설정 요청이 조회 기록 표에 남음 (P-B2 고친 뒤) [새]

### 비밀번호 바꾸기
30. 현재 비번 틀리면 400 문구, 로그아웃 안 됨, 비번 그대로
31. 현재 비번 5번 틀리면 6번째는 맞아도 429, 15분 뒤 풀림, 로그인은 안 잠김
32. 새 비번 규칙 위반 → 400 규칙 문구, 비번 그대로
33. 성공 → 새 비번만 됨, 이 기기 포함 모든 세션·refresh·소켓 끊김, 화면은 안내 뒤 로그인 화면
34. 새 비번 확인이 다르면 보내지도 않음 (P-Q4 안 1일 때) [새]
35. 소셜 전용 계정엔 비번 변경 칸이 안 보이고, 서버도 비교 없이 거절 (P-Q3 안 1일 때) [새]
36. 같은 순간 두 번 눌러도 요청 한 번

### 탈퇴·이메일 바꾸기
37. 탈퇴: 비번 계정은 비번, 소셜 전용은 계정 이메일, 비번 5번 틀리면 15분 429

39. 이메일 바꾼 뒤 새 이메일로 로그인·재설정 됨, 옛 이메일로 안 됨

### 아이디 찾기
40. 닉네임·생일 맞으면 가린 이메일, 어디가 틀렸든 같은 NOT_FOUND, 같은 닉네임 10분 6번째 429

## 7. 확인 못 한 것

- 진짜 메일 받기: Gmail·게이트웨이로 실제 메일이 오는지, 스팸함에 가는지, 하루 한도 — 서버 안 띄움
- 운영 DB 글자 비교 규칙: 시험 DB는 대소문자 무시(`utf8mb4_unicode_ci`, `scripts/setup-test-db.js:36`)라 `User@…`와 `user@…`가 같은 계정으로 찾아짐. 운영 DB 설정은 못 봄 — 다르면 로그인·재설정이 대소문자에 갈림
- 화면 색 대비 숫자: 입력 칸 그림의 실제 색을 재지 않고 눈으로만 봄 (P-A1 비율은 짐작)
- PC 계정 관리 긴 문구가 실제로 잘리는지 (P-A4)
- 비번 바꾼 뒤 1.5초 안내 사이에 다른 요청(알림·친구 목록 새로고침 등)이 401을 받아 안내를 읽기 전에 로그인 화면으로 먼저 튕기는지 — 공통 401 처리가 바로 이동함(`unauthorized.js:24-25`), 그 사이 요청이 있는지는 안 봄
- nginx 접근 기록이 실제로 어디에 얼마나 남는지 (P-X2)
- 서버 여러 대 + Redis에서 틀림 셈(`wrong:pw:`·`wrong:wd:`)·요청 수 제한이 실제로 합쳐지는지 (코드만 읽음)
- 로컬 가입 뒤 소셜을 연결한 계정의 `has_local_password` 실제 값 (설계상 true 유지)
- 브라우저 비번 저장기가 재설정 화면에서 새 비번을 어느 계정에 붙이는지 (재설정 칸엔 이메일 칸이 없음)
- 지운 시험은 이름만 읽음 — 실제로 무엇을 확인했는지 본문은 대부분 안 읽음
