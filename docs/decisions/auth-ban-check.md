# 인증 미들웨어의 활성 밴 검사 결정 (AC-06)

## 결정

보호된 REST 요청마다 다음 두 조회를 `Promise.all`로 병렬 실행한다.

1. `user_sessions`에서 JWT의 `sessionId`와 `uuid`가 모두 일치하고 `is_online:true`인 행
2. `user_bans`에서 해당 `uuid`의 영구 밴 또는 아직 끝나지 않은 밴

캐시는 사용하지 않는다. 로그아웃·다른 기기 로그인·운영 밴을 다음 요청부터 즉시
반영하는 정확성을 우선한다. 오프라인이거나 사용자와 맞지 않는 세션은 401, 활성 밴은
403이다. DB 장애는 인증 실패로 위장하지 않고 5xx로 전달한다.

## 성능 영향과 후속 측정

기존 보호 요청의 인증 DB 조회는 0회였고, 이 결정 뒤에는 독립된 인덱스 조회 2회다.
세션은 기본키 `id`와 `user_id`를 함께 제한한다. 활성 밴 조회는 `user_id`와 종료 조건을
사용하므로 실제 배포 스키마의 `user_bans.user_id` 인덱스를 확인해야 한다.

두 쿼리는 병렬이라 직렬 왕복 두 번의 지연을 그대로 더하지는 않지만, 요청량만큼 DB와
커넥션 풀 부하는 증가한다. 배포 전후로 인증 요청 p95, 쿼리 p95, 풀 acquire 대기와
타임아웃을 비교한다.

## 캐시를 지금 쓰지 않는 이유

TTL 캐시는 평균 조회량을 줄이는 대신 TTL 동안 밴과 세션 무효화를 늦춘다. 다중 서버에서는
인스턴스별 값도 어긋난다. 먼저 정확한 즉시 무효화를 적용하고, 실측에서 병목이 확인될 때만
짧은 TTL과 명시적 무효화 채널을 함께 설계한다. 단순 TTL 캐시만으로 바꾸지 않는다.

## 범위

이번 결정은 REST 인증 미들웨어에 한정한다. 소켓 핸드셰이크는 별도 인증 경로이므로 이
슬라이스에서 수정하지 않는다.
