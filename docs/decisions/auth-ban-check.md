# 활성 밴 검사를 인증 미들웨어에 넣을 것인가 (AC-06)

관련 코드: `backend/middleware/auth.middleware.js`, `backend/repositories/user.repositories.js`,
`backend/service/auth.service.js`

## 지금 상태

밴 검사(`checkActiveBan`)는 **로그인 시점에 딱 한 번** 돈다(`auth.service.js`의 `login`).
토큰 수명은 1일이므로(`utils/jwt.js`), 로그인한 뒤에 밴된 사용자는 최대 하루 동안 모든
보호된 라우트를 그대로 통과한다. 이번 작업에서 인증 미들웨어에 세션 검사를 넣으면서
요청당 DB 조회가 0회에서 1회로 늘었기 때문에, 밴 검사를 여기에 더 얹을지 함께 정한다.

## 결정

**밴 검사를 매 요청 별도 쿼리로 인증 미들웨어에 넣지 않는다.** 대신 이번에 추가한
세션 검사를 무효화 지점으로 쓴다 — 밴을 부과할 때 그 사용자의 `user_sessions`를
`is_online:false`로 내리면, 다음 요청에서 이미 존재하는 세션 검사가 401을 낸다.
요청당 추가 비용은 0이다.

이 결정에는 조건이 하나 붙는다: **밴 부여 경로가 세션을 함께 내려야 한다.** 현재
저장소에는 밴을 생성하는 코드가 없다(`UserBan`은 모델과 `checkActiveBan` 조회에서만
쓰인다 — 운영 도구나 DB 직접 조작으로 삽입되는 것으로 보인다). 밴 부여가 애플리케이션
밖에서 일어난다면 아래 대안 B로 넘어가야 한다.

## 검토한 선택지와 비용

요청당 비용은 실측하지 않았다. 아래는 왕복 횟수 기준의 구조적 비교다.

| 안 | 요청당 추가 왕복 | 밴 반영 지연 | 비고 |
|---|---|---|---|
| A. 세션 무효화 (채택) | 0 | 즉시(다음 요청) | 밴 부여 코드가 세션을 내려야 성립 |
| B. 세션 조회에 UserBan LEFT JOIN | 0 (쿼리 1건이 조인 1개 늘어남) | 즉시 | 앱 밖 밴 부여도 잡힘 |
| C. 요청당 `checkActiveBan` 별도 호출 | +1 | 즉시 | 인증 요청 수만큼 쿼리가 2배 |
| D. TTL 캐시 (예: 60초) | 평균 <1 | 최대 TTL만큼 | 다중 인스턴스면 인스턴스별로 흩어짐 |

C를 고르지 않은 이유는 이득 대비 비용이 명백히 나쁘기 때문이다. 밴은 전체 사용자 대비
희소한데, 희소한 조건을 확인하려고 **모든** 인증 요청에 왕복을 하나 더 붙인다. 같은
효과를 A(0회)나 B(왕복 0회 추가)로 얻을 수 있다.

D는 지금 필요 없다. 채택안의 요청당 조회는 `user_sessions` PK 단건 조회 한 번이고,
이건 이미 캐시가 필요할 만큼 비싸지 않다. 캐시는 밴 반영 지연을 만들면서 다중 인스턴스
배포에서 인스턴스마다 다르게 동작하는 부작용이 있어, 실측으로 병목이 확인되기 전에는
넣지 않는다.

## B로 넘어가야 하는 신호

- 밴이 애플리케이션 밖(운영 콘솔, DB 직접 SQL)에서 부여되어 세션을 내리지 못한다
- 밴된 사용자가 401 이후 재로그인으로 새 세션을 만들어 우회하는 사례가 관측된다
  (재로그인 경로에는 `login`의 `checkActiveBan`이 살아 있으므로 403으로 막히지만,
  이 가정이 깨지면 확인이 필요하다)

B를 적용할 때는 `findSessionById`의 조회에 `UserBan`을 `is_permanent OR end_at > now`
조건으로 include하면 된다. 왕복은 그대로 1회다. 전제는 `user_bans.user_id`에 인덱스가
있다는 것 — 모델에 인덱스 선언이 없으므로(`models/user/user_ban.model.js`), B를 적용하기
전에 실제 스키마에서 인덱스 존재를 확인하고 없으면 먼저 추가해야 한다. 인덱스가 없으면
조인이 풀스캔이 되어 위 표의 비용 계산이 무너진다.

## 함께 남기는 사실

- **소켓 경로는 이 검사를 거치지 않는다.** `socket/socket.js`의 `authenticateSocket`이
  HTTP 미들웨어와 별개로 `jwt.verify`만 수행한다. 세션 검사도 밴 검사도 여기엔 없다.
  이번 범위 밖이라 손대지 않았지만, 밴/세션 무효화를 실효성 있게 만들려면 같은 검사가
  소켓 핸드셰이크에도 필요하다.
- **배포 시 기존 토큰은 전부 401이 된다.** 세션 검사는 `sessionId` 클레임을 요구하는데,
  배포 이전에 발급된 토큰 중 이 클레임이 없는 것이 있으면 재로그인이 필요하다.
  토큰 수명이 1일이라 영향 구간은 하루로 끝난다.
- **측정할 것.** 인증 요청의 p95 지연과 커넥션 풀 대기 시간(`config/dbPool.js`의
  `acquire`)을 배포 전후로 비교한다. 요청당 왕복이 0 → 1로 늘었으므로, 풀이 이미
  포화 상태였다면 여기서 먼저 드러난다.
