# Codex 작업 프롬프트: [The Joker] 인게임 코어 하네스 구축

너는 기존 게임 프로젝트 레포를 수정하는 Codex 에이전트다.

목표는 `[The Joker]` 인게임 코어 시스템의 **게임 로직 하네스 / 테스트 하네스**를 구축하는 것이다.

이번 작업의 최우선 목표는 UI, 연출, 사운드, 에셋 구현이 아니라, 게임이 서버/코어 레벨에서 정상적으로 흘러가는지 검증 가능한 구조를 만드는 것이다.

현재 프로젝트에는 프론트엔드 UI 코드가 어느 정도 이미 만들어져 있으나, 게임 상태 처리 코드는 거의 구현되어 있지 않다. 또한 SQLite를 사용할 예정이다.

---

## 0. 가장 중요한 작업 규칙: 승인 전 코드 작성 금지

Codex는 바로 코드 파일을 생성/수정/삭제하지 마라.

먼저 레포를 분석한 뒤, 실제 코드 작성 전에 반드시 사용자에게 다음 내용을 보고하고 명시적인 허락을 받아라.

1. 수정하려는 파일 목록
2. 새로 생성하려는 파일 목록
3. 삭제하거나 이동하려는 파일이 있는지 여부
4. 각 파일에서 구현할 기능 요약
5. 테스트 추가 계획
6. 예상되는 영향 범위
7. 불명확한 기획 또는 확인이 필요한 가정
8. 유지보수성을 위해 어떤 구조로 나눌 것인지
9. 기존 프론트 UI 중 어떤 파일을 유지하고 어떤 파일에 상태 연결이 필요한지
10. 현재 상태 관리 방식이 있는지, 없다면 어떤 방식을 권장하는지
11. SQLite가 이미 쓰이고 있는지, 새로 설정해야 하는지
12. SQLite 저장 계층을 어디에 둘 것인지
13. DB 테이블 또는 repository interface 설계 초안
14. 기존 UI를 수정하지 않고도 하네스를 먼저 검증할 수 있는지 여부

사용자가 “진행해”, “구현해”, “허락”, “승인”, “그대로 해”처럼 명확하게 승인하기 전까지는 실제 코드 변경을 하지 마라.

승인 전에는 다음만 허용된다.

- 레포 구조 분석
- 기존 코드 읽기
- 구현 계획 작성
- 파일별 변경 계획 작성
- 테스트 설계 작성
- 필요한 질문 정리

승인 전에는 다음을 하지 마라.

- 코드 파일 생성
- 코드 파일 수정
- 코드 파일 삭제
- 자동 포맷팅 적용
- 패키지 설치
- package.json 수정
- 테스트 파일 생성
- 마이그레이션 파일 생성
- SQLite 테이블 생성
- 프론트 UI 신규 구현

코드 변경이 필요할 경우 반드시 먼저 변경 계획을 제시하고, “이대로 코드 작성/수정 진행해도 되는지” 사용자에게 확인하라.

단, 설계 후 실제 파일 생성/수정은 사용자 승인 전까지 하지 마라.

## 2-A. 현재 프로젝트 상황 반영

현재 프로젝트에는 프론트엔드 UI 코드가 어느 정도 이미 만들어져 있다.

다만 아직 다음 부분은 거의 구현되어 있지 않다.

- 게임 상태 처리
- 프론트 UI와 게임 코어 로직 연결
- 투표 상태 관리
- 페이즈 상태 관리
- 밤 액션 상태 관리
- 승리/종료 상태 반영
- SQLite 기반 저장 구조

따라서 이번 작업에서 Codex는 새로운 UI를 만들려고 하지 말고, 기존 프론트 UI를 최대한 보존하면서 **상태 처리 계층과 게임 코어 로직 연결 구조**를 우선 설계하라.

---

## 2-B. 프론트엔드 관련 작업 원칙

1. 기존 프론트 UI 컴포넌트를 무리하게 갈아엎지 마라.
2. 기존 UI 파일을 수정해야 한다면, 어떤 상태를 연결하기 위해 수정하는지 먼저 설명하고 사용자 허락을 받아라.
3. UI의 디자인, 레이아웃, 스타일, 에셋, 애니메이션은 이번 작업 범위가 아니다.
4. 이번 작업의 목적은 UI를 예쁘게 만드는 것이 아니라, 기존 UI가 게임 상태를 받아 표시할 수 있게 만드는 것이다.
5. 기존 UI가 이미 있는 경우, 새 화면을 만들기보다 상태 hook, store, adapter, controller를 통해 연결하는 방향을 우선 고려하라.
6. 프론트 상태 처리는 게임 코어 로직을 직접 복붙하지 말고, 코어 모듈의 결과를 받아 화면에 반영하는 구조로 설계하라.
7. UI 컴포넌트 안에 투표 판정, 밤 스킬 판정, 승리 조건 같은 도메인 로직을 넣지 마라.
8. UI 컴포넌트는 가능한 한 현재 GameState, PlayerState, GameEvent를 받아 렌더링하는 역할에 집중하게 하라.

---

## 2-C. 프론트 미구현 기능 처리 원칙

현재 프론트엔드에 이미 구현되어 있지 않은 기능은 이번 작업에서 새로 구현하지 마라.

이번 작업의 목적은 기존 프론트 UI를 새 기능으로 확장하는 것이 아니라, 이미 존재하는 UI가 있다면 그 UI에 연결 가능한 코어 상태와 하네스를 준비하는 것이다.

따라서 다음 원칙을 반드시 지켜라.

1. 프론트에 이미 존재하지 않는 화면, 버튼, 모달, 패널, 애니메이션, 이펙트, 사운드, 아이콘, UI 기능은 새로 만들지 마라.
2. 기획서에는 있지만 현재 프론트 UI에 구현되어 있지 않은 기능은 이번 작업에서 구현하지 말고, “추후 구현 필요” 항목으로만 정리하라.
3. 기존 프론트 UI에 대응되는 기능이 있는 경우에만 상태 연결 계획을 세워라.
4. 기존 UI가 없는 기능은 코어 로직에도 무리하게 UI 연결 코드를 만들지 마라.
5. 단, UI 없이도 검증 가능한 순수 게임 코어 로직과 테스트 하네스는 구현 계획에 포함할 수 있다.
6. 프론트에 없는 기능을 구현해야 할 필요가 생기면, 즉시 멈추고 사용자에게 다음을 보고한 뒤 허락을 받아라.
   - 어떤 프론트 기능이 없는지
   - 왜 필요한지
   - 새로 만들 파일 또는 수정할 파일
   - UI 없이 코어 하네스만으로 대체 가능한지
7. 사용자 승인 없이 프론트 기능을 새로 만들지 마라.
8. 특히 다음은 프론트에 이미 구현되어 있지 않다면 새로 만들지 마라.
   - 투표 UI
   - 단두대 찬반 투표 UI
   - 밤 스킬 선택 UI
   - 직업 공개 UI
   - 채팅 UI
   - 게임 결과 UI
   - 이벤트 로그 UI
   - 방/로비 UI
   - 사후세계 UI
   - 핑 UI
   - 상점/이모티콘 UI
9. 이번 작업에서 프론트는 “기존 UI 보존”을 기본값으로 한다.
10. Codex는 프론트 미구현 기능을 발견하면 직접 구현하지 말고, 완료 보고 또는 분석 보고에 `프론트 미구현으로 인해 연결 보류`라고 명확히 적어라.

핵심 원칙:

> 프론트에 이미 구현되어 있지 않은 기능은 이번 작업에서 새로 구현하지 말고, 코어 하네스 또는 TODO/보류 항목으로만 남겨라.

## 2-D. 상태 처리 계층 요구사항

기존 UI와 게임 코어 사이에 상태 처리 계층을 둬라.

프로젝트 구조에 따라 다음 중 적절한 방식을 선택하라.

- React state
- Zustand
- Redux
- Context API
- Next.js server/client boundary
- NestJS service
- Electron IPC bridge
- 기존 프로젝트에서 이미 쓰고 있는 상태 관리 방식

새로운 상태 관리 라이브러리를 설치해야 한다면, 먼저 사용자에게 이유를 설명하고 허락을 받아라.

상태 처리 계층은 최소한 다음을 다룰 수 있어야 한다.

1. 현재 페이즈
2. 현재 생존자 목록
3. 사망자 목록
4. 내 역할
5. 내 투표 상태
6. 전체 투표 진행 상태
7. 단두대 후보자
8. 밤 액션 제출 여부
9. 밤 액션 결과
10. 게임 이벤트 로그
11. 승리 결과
12. 게임 종료 여부

단, 위 상태를 표시할 프론트 UI가 이미 없다면 UI를 새로 만들지 말고 상태 구조와 하네스 검증에만 머물러라.

## 2-E. SQLite 사용 방침

이 프로젝트는 SQLite를 사용할 예정이다.

다만 게임 코어 로직이 SQLite에 직접 의존하면 유지보수가 어려워지므로, 반드시 저장 계층을 분리하라.

다음 구조를 우선 고려하라.

```txt
UI Component
  ↓
Frontend State / Store
  ↓
Game Controller or Service
  ↓
Game Core Logic
  ↓
Repository Interface
  ↓
SQLite Adapter
```

SQLite 관련 구현 원칙:

1. 게임 코어 로직은 SQLite를 직접 import하지 않는다.
2. 게임 코어는 순수한 GameState를 입력받고, 변경된 GameState와 GameEvent를 반환하는 구조를 우선한다.
3. SQLite 저장은 Repository 또는 Persistence Adapter 계층에서 담당한다.
4. DB 저장 구조는 나중에 교체 가능하도록 interface를 먼저 설계한다.
5. SQLite 테이블 설계가 필요하면 먼저 제안하고 사용자 허락을 받아라.
6. 마이그레이션 파일 생성이 필요하면 먼저 사용자 허락을 받아라.
7. 기존 SQLite 설정이나 DB 파일이 있다면 새로 만들기 전에 반드시 분석하라.
8. 기존 DB 구조가 있다면 충돌하지 않게 확장하라.
9. package.json에 SQLite 관련 패키지를 추가해야 한다면 반드시 사용자 허락을 받아라.

## 2-F. 권장 SQLite 저장 대상

이번 작업에서 SQLite 저장을 고려할 수 있는 데이터는 다음이다.

```txt
games
players
game_events
day_votes
tribunal_votes
night_actions
game_snapshots
```

단, 실제 테이블 생성이나 마이그레이션은 사용자 승인 후 진행하라.

우선은 다음처럼 interface 중심으로 설계하는 것을 권장한다.

```ts
GameRepository {
  saveGameState(gameState): Promise<void>;
  loadGameState(gameId): Promise<GameState | null>;
  appendGameEvent(gameId, event): Promise<void>;
  listGameEvents(gameId): Promise<GameEvent[]>;
}
```

프로젝트가 아직 비동기 저장 구조를 쓰지 않는다면 sync/async 방식은 기존 코드 스타일에 맞춰 결정하라.

## 4. 게임 개요

게임 이름은 `[가면무도회 살인사건]`다.  
마피아류 소셜 디덕션 게임이며, 기본 페이즈는 다음 3개가 반복된다.

### Phase 1: 거짓된 왈츠 / 낮

- 생존자 전원 채팅 가능
- 의심자 색출
- 처형 후보 투표 진행
- 첫날 낮 시간은 기본 150초
- 사람이 죽어 나갈수록 낮 시간이 짧아지는 구조
- 정확한 시간 산정 공식은 아직 미정이므로 전략 함수 또는 설정값으로 분리한다

예시:

```ts
calculateDayDuration(dayIndex, aliveCount, initialPlayerCount): number
```

기본값은 다음처럼 둔다.

- 첫 낮: 150초
- 이후 낮: 생존자가 줄수록 감소
- 최소 낮 시간은 설정값으로 제한

정확한 밸런스는 나중에 조정 가능해야 한다.

### Phase 2: 단두대의 심판 / 저녁

- 낮 투표 최다 득표자가 처형 후보가 된다
- 후보자의 최후 변론 단계가 존재한다
- 찬반 투표 후 처형 여부를 결정한다
- 처형되면 사망 처리된다

현재 구현에서는 최후 변론의 실제 채팅 UI는 필요 없다.  
대신 상태와 이벤트만 기록하라.

### Phase 3: 피의 장막 / 밤

- 밤 시간은 기본 40초
- 전체 공개 채팅 금지
- 광대 전용 채팅 또는 광대 전용 액션만 허용
- 각 직업별 고유 스킬 타겟팅
- 제한 시간 내 선택하지 않으면 skip 처리

## 5. 직업과 진영

직업은 다음을 지원하라.

```ts
  | "JOKER"
  | "DOCTOR"
  | "GUARD"
  | "WITCH_HUNTER"
  | "NOBLE";
```

진영은 다음처럼 구분하라.

```ts
Team = "JOKER" | "CITIZEN";
```

- 광대 / JOKER: 광대 진영
- 주치의 / DOCTOR: 시민 진영
- 경비원 / GUARD: 시민 진영
- 마녀사냥꾼 / WITCH_HUNTER: 시민 진영
- 귀족 / NOBLE: 시민 진영

## 8. 낮 투표 로직

낮에는 생존자들이 처형 후보를 투표한다.

구현할 기능:

```ts
castDayVote(gameId, voterId, targetId)
resolveDayVote(gameState)
```

규칙:

1. 사망자는 투표할 수 없다.
2. 연결 해제된 유저는 투표할 수 없다.
3. 자기 자신에게 투표 가능 여부는 설정값으로 분리하라.
4. 최다 득표자가 1명이면 저녁/단두대 페이즈로 이동한다.
5. 최다 득표자가 동점이면 “단두대 고장” 이벤트를 기록하고 아무도 처형하지 않은 채 즉시 밤으로 이동한다.

동점 처리 이벤트 예시:

```ts
{
  type: "GUILLOTINE_BROKEN",
  message: "단두대 고장: 최다 득표자가 동점이므로 아무도 처형되지 않습니다."
}
```

## 9. 저녁 / 단두대 로직

저녁에는 낮 투표 최다 득표자가 최종 처형 후보가 된다.

구현할 기능:

```ts
startTribunal(candidateId)
castTribunalVote(voterId, vote: "APPROVE" | "REJECT")
resolveTribunalVote(gameState)
```

규칙:

1. 생존자만 찬반 투표 가능
2. 후보자 본인의 투표 가능 여부는 설정값으로 분리
3. 찬성이 반대보다 많으면 후보자 처형
4. 그 외에는 처형하지 않음
5. 결과 처리 후 밤으로 이동
6. 처형자는 alive=false, deathReason="EXECUTED" 처리

## 10. 밤 스킬 로직

밤 스킬 판정 우선순위는 반드시 다음 순서를 따른다.

1. 주치의 보호
2. 광대 암살
3. 경비원 조사
4. 마녀사냥꾼 확인

구현할 기능:

```ts
submitNightAction(actorId, action)
resolveNight(gameState)
```

액션 예시:

```ts
NightAction =
  | { type: "PROTECT"; actorId: string; targetId: string }
  | { type: "ASSASSINATE"; actorId: string; targetId: string }
  | { type: "INVESTIGATE"; actorId: string; targetId: string }
  | { type: "CONFIRM"; actorId: string; targetId: string }
  | { type: "SKIP"; actorId: string };
```

### 주치의

- 한 명을 보호할 수 있다.
- 보호 대상이 광대 암살 대상이면 암살은 무효화된다.
- 자기 자신 보호 가능 여부는 설정값으로 분리하라.

### 광대

- 밤에 암살 대상을 선택한다.
- 광대가 1명이면 해당 광대의 타겟을 사용한다.
- 광대가 2명 이상 살아 있고 서로 다른 대상을 골랐다면, 랜덤으로 한 명의 타겟만 암살 시도한다.
- 랜덤 결과는 테스트 가능해야 하므로 seed/RNG 주입을 사용하라.
- 주치의 보호 대상이면 암살 실패 이벤트를 기록한다.
- 보호받지 않았다면 대상은 사망 처리된다.

### 경비원

- 대상을 조사한다.
- 조사 결과로 대상이 광대 진영인지 여부를 반환한다.
- 결과는 해당 경비원에게만 전달 가능한 이벤트로 기록한다.

### 마녀사냥꾼

- 대상을 확인한다.
- 현재 기획상 정확한 효과가 더 상세히 정해지지 않았으므로, 우선 대상의 role 또는 team을 확인하는 구조로 구현하라.
- 나중에 쉽게 규칙을 교체할 수 있게 별도 resolver 함수로 분리하라.

### 미선택 / 시간 초과

- 제한 시간 내 액션을 선택하지 않은 생존자는 자동으로 SKIP 처리한다.
- SKIP 이벤트를 기록하라.

## 11. 탈주자 처리

게임 중 유저가 이탈하면 즉시 사망 처리한다.

구현할 기능:

```ts
handlePlayerDisconnect(playerId)
```

규칙:

1. connected=false
2. alive=false
3. deathReason="DISCONNECTED"
4. 돌연사 이벤트 기록
5. 승리 조건을 즉시 재검사
6. 현재 투표/스킬 대상에 해당 유저가 포함되어 있다면 안전하게 무효화하거나 skip 처리

이벤트 메시지 예시:

```txt
돌연사: 플레이어가 폭풍우에 휩쓸려 사망했습니다.
```

## 12. 승리 조건

매 주요 처리 이후 승리 조건을 검사하라.

검사 타이밍:

- 게임 시작 직후
- 낮 투표 결과 처리 후
- 저녁 처형 후
- 밤 암살 후
- 탈주 처리 후

### 시민 진영 승리

광대가 전원 사망하면 시민 진영 승리.

```ts
winner = "CITIZEN"
reason = "ALL_JOKERS_ELIMINATED"
```

### 광대 진영 승리

생존한 광대 수가 남은 시민 수와 같거나 많아지면 광대 진영 승리.

```ts
winner = "JOKER"
reason = "JOKERS_REACHED_PARITY"
```

승리 조건이 달성되면 phase="ENDED"로 전환하고 더 이상의 액션 입력은 거부하라.

## 13. 채팅 권한 로직

실제 채팅 UI를 새로 구현하지 마라.

대신 채팅 메시지를 보낼 수 있는지 판정하는 순수 함수를 구현하라.

```ts
canSendChat(playerId, channel, gameState): boolean
sendChat(playerId, channel, text)
```

채널:

```ts
ChatChannel =
  | "PUBLIC"
  | "JOKER_NIGHT";
```

### PUBLIC

- 낮에는 생존자 전원 가능
- 저녁은 설정값에 따라 허용/제한 가능
- 밤에는 일반 공개 채팅 금지
- 사망자는 PUBLIC 채팅 불가

### JOKER_NIGHT

- 밤 페이즈에만 가능
- 살아있는 광대만 가능

시스템 메시지는 일반 유저 채팅과 구분해서 `GameEvent`로 기록하라.

사망자 채팅, 영혼 채팅, 사후세계 채팅은 이번 범위에서 구현하지 않는다.

프론트에 채팅 UI가 없다면 채팅 UI를 만들지 말고, 권한 판정 함수와 테스트만 준비하라.

## 14. 유지보수성 요구사항

이번 구현은 단순히 테스트만 통과하는 코드가 아니라, 이후 기능 확장과 밸런스 조정을 고려한 유지보수 가능한 구조로 작성하라.

특히 다음 사항을 반드시 지켜라.

1. 게임 룰과 실행 로직을 분리하라.
   - 직업 구성, 낮/밤 시간, 자기 투표 가능 여부, 주치의 자기 보호 가능 여부, 처형 찬반 기준 등은 하드코딩하지 말고 config로 분리한다.
   - 밸런스 조정이 필요할 때 핵심 로직 파일을 직접 수정하지 않아도 되게 만든다.

2. 페이즈 전환 로직을 명확히 분리하라.
   - DAY, TRIBUNAL, NIGHT, ENDED 전환 조건을 한곳에서 추적 가능하게 만든다.
   - 여러 파일에 흩어진 if문으로 페이즈를 변경하지 않는다.

3. 밤 스킬 판정 로직은 우선순위 기반으로 확장 가능하게 작성하라.
   - 현재 순서는 `주치의 -> 광대 -> 경비원 -> 마녀사냥꾼`이다.
   - 추후 신규 직업이 추가되더라도 기존 판정 로직 전체를 갈아엎지 않도록 resolver 또는 pipeline 형태를 고려한다.

4. 이벤트 로그를 표준화하라.
   - 투표, 처형, 암살, 보호 성공, 조사 결과, 탈주, 승리 판정 등은 일관된 GameEvent 타입으로 기록한다.
   - UI나 서버 소켓은 나중에 이 이벤트를 구독해서 사용할 수 있게 한다.
   - 문자열 메시지만 남기지 말고, type, actorId, targetId, phase, visibility 같은 구조화된 데이터를 포함한다.

5. 테스트 가능한 구조를 유지하라.
   - Math.random(), Date.now()를 직접 사용하지 않는다.
   - RNG, Clock, Config를 주입 가능하게 만든다.
   - 같은 입력과 같은 seed에서는 항상 같은 결과가 나오게 한다.

6. 도메인 로직과 입출력 로직을 분리하라.
   - 게임 판정 로직은 DB, Socket, UI, React 상태, HTTP 요청에 직접 의존하지 않는다.
   - 코어 로직은 순수 함수 또는 독립 서비스로 유지한다.
   - 나중에 NestJS, WebSocket, Electron, Next.js 어디에서 호출해도 재사용 가능해야 한다.

7. 타입과 네이밍을 명확하게 유지하라.
   - Role, Team, GamePhase, DeathReason, GameEventType 등 핵심 개념은 문자열 난발을 피하고 enum 또는 union type으로 관리한다.
   - 함수명은 `resolveNight`, `checkWinCondition`, `castDayVote`처럼 의도가 드러나야 한다.

8. 큰 함수를 만들지 마라.
   - 하나의 함수가 투표 집계, 사망 처리, 승리 판정, 페이즈 전환까지 모두 처리하지 않게 한다.
   - 각 함수는 하나의 책임만 가지게 한다.
   - 복잡한 로직은 작은 함수로 나누고, 테스트도 작은 단위로 작성한다.

9. 예외 처리를 명확하게 하라.
   - 사망자가 투표하는 경우
   - 없는 플레이어를 타겟으로 잡는 경우
   - 이미 종료된 게임에 액션을 입력하는 경우
   - 밤이 아닌데 밤 스킬을 쓰는 경우
   - 직업과 맞지 않는 스킬을 쓰는 경우
   - 연결 해제된 유저가 액션을 시도하는 경우

   위 상황은 조용히 무시하지 말고, 명확한 에러 또는 실패 결과를 반환한다.

10. 추후 제외 기능을 붙일 수 있게 경계면을 남겨라.
   - 이번 작업에서 사후세계와 핑 시스템은 구현하지 않는다.
   - 다만 나중에 붙일 수 있도록 GameEvent, PlayerState, ChatChannel 구조가 지나치게 폐쇄적이지 않게 만든다.
   - 사후세계/핑 관련 코드는 실제 구현하지 말고 필요한 경우 TODO 주석만 남긴다.

11. 주석은 유지보수에 도움이 되는 위치에 작성하라.
   - 모든 주요 타입, 함수, 클래스, 상태 전이 함수, 판정 함수에는 주석을 작성한다.
   - “무엇을 하는지”보다 “왜 이렇게 판정하는지”를 우선 설명한다.
   - 밤 스킬 우선순위, 투표 동점, 탈주 사망, 승리 조건처럼 게임 결과에 영향을 주는 로직에는 반드시 의도 주석을 남긴다.

12. 테스트 이름은 기획 의도가 드러나게 작성하라.
   - `should work` 같은 모호한 테스트명을 피한다.
   - 예: `should skip execution and enter night when day vote is tied`
   - 예: `should block joker assassination when doctor protects target`

13. 변경 범위를 최소화하라.
   - 기존 구조가 있다면 그 구조를 존중한다.
   - 이번 하네스와 직접 관련 없는 리팩터링은 하지 않는다.
   - 린트/포맷 변경, 패키지 변경, 전역 설정 변경이 필요하면 먼저 사용자 승인 후 진행한다.

14. 완료 보고 시 유지보수 관점도 함께 설명하라.
   - 어떤 로직을 config로 분리했는지
   - 어떤 코어 로직을 pure function으로 만들었는지
   - RNG/Clock 주입이 어디에 적용됐는지
   - 신규 직업 추가 시 어느 파일을 수정하면 되는지
   - UI/Socket 연동 시 어떤 이벤트를 사용하면 되는지

## 15. 주석 작성 원칙

코드를 작성할 때는 유지보수성을 위해 반드시 주석을 작성하라.

1. 모든 주요 타입, 함수, 클래스, 상태 전이 함수, 판정 함수에는 주석을 작성한다.
2. TypeScript를 사용하는 경우 공개 함수와 핵심 타입에는 TSDoc/JSDoc 형식의 주석을 작성한다.
3. 단순한 변수까지 과도하게 설명하는 주석은 피한다.
4. 게임 룰, 예외 처리, 판정 순서, 기획상 가정은 반드시 주석으로 남긴다.
5. 밤 스킬 판정, 투표 동점 처리, 탈주 처리, 승리 조건처럼 버그가 나면 게임 결과가 바뀌는 로직에는 의도를 설명하는 주석을 반드시 작성한다.
6. 불명확한 기획은 임의로 확정하지 말고 TODO 주석으로 남긴다.
7. 이번 작업에서 제외된 사후세계와 핑 시스템은 실제 구현하지 말고, 필요한 경우 TODO 주석으로만 남긴다.

## 16. 테스트 하네스 요구사항

반드시 게임 흐름을 코드로 재현할 수 있는 테스트/시뮬레이션 하네스를 만들어라.

가능한 형태:

- `scripts/game-core-harness.ts`
- `src/game-core/__tests__/game-core.test.ts`
- `tests/game-core/*.test.ts`
- 기존 테스트 구조가 있다면 그 구조를 따를 것

하네스는 다음을 할 수 있어야 한다.

1. 플레이어 N명을 생성
2. seed 기반으로 역할 배정
3. 낮 투표 입력
4. 동점 투표 시나리오 실행
5. 저녁 찬반 투표 실행
6. 밤 스킬 입력
7. 밤 스킬 판정 실행
8. 탈주 처리
9. 승리 조건 검사
10. 최종 이벤트 로그 출력

가능하면 CLI에서 다음처럼 실행 가능하게 만들어라.

```bash
npm run game:harness
```

또는 기존 패키지 매니저에 맞춰 적절히 스크립트를 추가하라.

하네스 출력 예시:

```txt
[DAY 1] phase=DAY alive=8
[VOTE] A -> B
[VOTE] C -> B
[TRIBUNAL] candidate=B
[EXECUTED] B
[NIGHT 1] doctor protects=D, jokers target=D
[ASSASSINATION_BLOCKED] target=D protected by doctor
[WIN_CHECK] no winner
```

## 17. 필수 테스트 시나리오

최소한 다음 테스트를 작성하라.

### 테스트 1: 5인 역할 분배

- 5명 생성
- 역할 분배
- 광대 1, 주치의 1, 귀족 3인지 확인

### 테스트 2: 8인 역할 분배

- 8명 생성
- 역할 분배
- 광대 2, 경비원 1, 주치의 1, 마녀사냥꾼 1, 귀족 3인지 확인

### 테스트 3: 낮 투표 동점

- 낮 투표에서 최다 득표자가 동점
- 아무도 처형되지 않음
- `GUILLOTINE_BROKEN` 이벤트 발생
- 밤으로 이동

### 테스트 4: 저녁 찬반 투표 처형

- 낮 투표 최다 득표자가 단두대 후보가 됨
- 찬성이 반대보다 많음
- 후보자가 처형됨
- 밤으로 이동

### 테스트 5: 저녁 찬반 투표 부결

- 낮 투표 최다 득표자가 단두대 후보가 됨
- 찬성이 반대보다 많지 않음
- 후보자가 생존
- 밤으로 이동

### 테스트 6: 주치의 보호 성공

- 주치의가 A를 보호
- 광대가 A를 암살 시도
- A는 생존
- 암살 무효 이벤트 발생

### 테스트 7: 광대 2명의 타겟 불일치

- 광대 2명이 서로 다른 타겟 선택
- seed 기반 RNG로 하나의 타겟만 선택됨
- 결과가 deterministic 해야 함

### 테스트 8: 시간 초과 미선택

- 밤에 특정 직업이 액션을 제출하지 않음
- 자동 SKIP 처리
- SKIP 이벤트 발생

### 테스트 9: 탈주자 즉시 사망

- 생존자가 게임 중 이탈
- alive=false
- connected=false
- deathReason="DISCONNECTED"
- 승리 조건 재검사

### 테스트 10: 시민 승리

- 모든 광대 사망
- phase="ENDED"
- winner="CITIZEN"

### 테스트 11: 광대 승리

- 생존 광대 수 >= 생존 시민 수
- phase="ENDED"
- winner="JOKER"

### 테스트 12: 밤 채팅 권한

- 밤에 일반 시민은 PUBLIC 채팅 불가
- 밤에 광대는 JOKER_NIGHT 가능
- 사망자는 PUBLIC 채팅 불가

## 18. 구현 원칙

1. 게임 코어 로직은 가능하면 pure function 중심으로 작성하라.
2. Date.now(), Math.random()을 직접 쓰지 말고 clock/RNG를 주입하라.
3. UI, 사운드, 연출 문구는 이벤트 타입과 메시지로만 남겨라.
4. 테스트가 쉬운 구조를 우선하라.
5. 타입 안정성을 최대한 확보하라.
6. 기존 코드 스타일을 따른다.
7. 불명확한 기획은 하드코딩하지 말고 config로 분리한다.
8. 구현 중 불가피한 가정은 코드 주석 또는 TODO 주석으로 명확히 남겨라.
9. 기존 기능을 깨지 말고, 변경 범위를 최소화하라.
10. 테스트가 실패하면 원인을 수정하고 다시 실행하라.
11. 모든 주요 타입, 함수, 클래스, 상태 전이 함수, 판정 함수에는 반드시 주석을 작성하라.
12. TypeScript를 사용하는 경우 공개 함수와 핵심 타입에는 TSDoc/JSDoc 형식의 주석을 작성하라.
13. 단순한 변수까지 과도하게 설명하는 주석은 피하되, 게임 룰·예외 처리·판정 순서·기획상 가정은 반드시 주석으로 남겨라.
14. 밤 스킬 판정, 투표 동점 처리, 탈주 처리, 승리 조건처럼 버그가 나면 게임 결과가 바뀌는 로직에는 의도를 설명하는 주석을 반드시 작성하라.
15. 사용자가 명시적으로 승인하기 전까지 실제 코드 작성, 파일 수정, 파일 생성, 파일 삭제를 하지 마라.
16. 코드 변경이 필요할 경우 먼저 변경 계획을 제시하고 “이대로 코드 작성/수정 진행해도 되는지” 확인하라.
17. 사용자의 승인을 받은 뒤에만 코드 작업을 시작하라.
18. 승인받은 범위를 넘어서는 추가 구현이 필요해지면 다시 사용자에게 허락을 받아라.
19. 작업 완료 후에는 변경한 코드의 핵심 구조와 주석을 어디에 달았는지 요약하라.
20. 이번 작업에서 제외하기로 한 사후세계 시스템과 핑 시스템은 구현하지 말고, 필요한 경우 TODO 주석으로만 남겨라.
21. 단순히 동작하는 코드가 아니라, 추후 직업 추가, 룰 변경, UI/Socket 연동, 밸런스 조정을 쉽게 할 수 있는 유지보수 가능한 구조로 작성하라.
22. 프론트에 이미 구현되어 있지 않은 기능은 새로 만들지 마라.
23. 기존 UI가 없는 기능은 상태 연결 대상으로 잡지 말고 `연결 보류` 또는 `추후 구현 필요`로 보고하라.
24. SQLite는 코어 로직에 직접 결합하지 말고 repository/adapter 계층으로 분리하라.

## 21. Acceptance Criteria

작업은 다음 조건을 만족해야 완료로 본다.

- 5/6/8/10인 역할 분배가 동작한다.
- DAY → TRIBUNAL → NIGHT → DAY 흐름이 동작한다.
- 낮 투표 동점 시 아무도 죽지 않고 밤으로 간다.
- 저녁 찬반 투표로 처형 여부가 결정된다.
- 밤 스킬 판정 우선순위가 `주치의 → 광대 → 경비원 → 마녀사냥꾼` 순서를 따른다.
- 주치의 보호가 광대 암살을 막는다.
- 광대 복수 타겟 불일치 시 seed 기반 랜덤으로 하나만 선택된다.
- 미선택은 SKIP 처리된다.
- 탈주는 즉시 사망 처리된다.
- 시민/광대 승리 조건이 자동 판정된다.
- 낮/밤/광대 전용 채팅 권한이 구분된다.
- 하네스 또는 테스트 스크립트로 전체 흐름을 재현할 수 있다.
- 주요 타입, 함수, 상태 전이, 판정 로직에 주석이 작성되어 있다.
- 룰/밸런스 값은 가능한 config로 분리되어 있다.
- RNG/Clock은 직접 호출하지 않고 주입 가능한 구조다.
- 사후세계와 핑 시스템은 코드에 섣불리 구현하지 않는다.
- 사용자 승인 전에는 코드 파일을 생성/수정/삭제하지 않는다.
- 기존 프론트 UI를 불필요하게 재작성하지 않는다.
- 프론트에 이미 없는 기능을 새로 구현하지 않는다.
- 기존 UI가 없는 기능은 상태 연결 대상으로 잡지 않는다.
- 프론트 미구현 기능은 `연결 보류` 또는 `추후 구현 필요`로 보고한다.
- 사용자 승인 없이 새 프론트 화면, 버튼, 모달, 패널, UI 기능을 만들지 않는다.
- UI 컴포넌트 안에 게임 판정 로직을 넣지 않는다.
- 게임 코어 로직과 프론트 상태 처리 계층이 분리되어 있다.
- SQLite는 코어 로직에 직접 결합되지 않고 repository/adapter 계층으로 분리되어 있다.
- SQLite 테이블 생성, 마이그레이션, 패키지 추가가 필요할 경우 사용자 승인 후 진행한다.
- 기존 UI에 연결 가능한 GameState / GameEvent 구조가 준비되어 있다.
- 하네스는 UI 없이도 먼저 실행 가능해야 한다.
