# 트래픽 실측 · 2,000명 한 달 비용 어림 (2026-11-09)

사용자 한 명이 실제로 받는 바이트를 재고, 한 달 활동 2,000명 기준으로 트래픽·서버비를 어림함. 개발자용.
원자료: `reports/전수조사_2026-11-09/perf/traffic/` (`raw-desktop.json`·`raw-mobile.json` 요청 하나하나, `summary.json` 단계·종류 합계, `cost-model.json` 계산, `public-files.json` 공개 파일 목록, `webp-estimate.tsv`·`video-crf26-estimate.tsv` 압축 시험) — `reports/`는 git에 안 올라감, 이 PC에만

## 0. 한 줄 결론

- 새 사용자 첫 방문(로그인~한 판~상점·마이페이지) **데스크톱 약 67MB · 모바일 약 58MB** (우리 서버에서 나간 것만, 외부 글꼴 약 5MB 뺌). 그중 **그림 PNG 36MB + 영상 MP4 19~29MB = 90% 넘음**, JS·CSS는 0.5MB
- 캐시 남은 채 다시 오면 **0.2~4MB** (새 연출 영상이 처음 나올 때만 늘어남). 한 판 소켓은 **약 21~24KB**
- 2,000명 한 달 트래픽 **74GB / 187GB / 471GB(적게/보통/많이) → 약 5천 / 1.7만 / 4.5만 원**. 서버+DB 고정비(약 9만~30만 원)가 훨씬 큼 → **2,000명 규모에선 트래픽이 제일 큰 돈은 아님**
- 그래도 줄일 값어치는 있음: PNG→WebP 하나로 첫 방문 약 33MB 줄음(그림 몫 90%), 영상 다시 압축하면 약 15~20MB 더 줄음 → 첫 방문 60MB대 → **15MB 안팎**. 돈보다 **모바일 데이터·첫 화면 속도** 문제가 큼

## 1. 실측 방법

| 항목 | 값 |
|---|---|
| 구성 | `docker compose` (저장소 nginx 설정 그대로: gzip, `/assets/` 1년 immutable, 그림·영상·소리 7일 `max-age=604800`, index.html no-cache) + 백엔드 이미지 + MySQL 8.4 컨테이너 |
| 운영과 다른 점 | `NODE_ENV=development`(http 로그인). 덧붙임 compose는 저장소 밖(scratchpad)에만 둠 |
| 주소 | 화면 `example.com:8080`·`m.example.com:8080`, API `api.example.com:8080` → 브라우저 `--host-resolver-rules`로 127.0.0.1에 묶음. **`localhost`/`api.localhost`로는 로그인 안 됨**: 둘이 다른 사이트로 잡혀 `SameSite=Lax` 쿠키가 안 실림(문서 `배포_설정.md`의 로컬 docker 방법 그대로면 브라우저 로그인 불가 — 별도 확인 필요). nginx `server_name`에 이미 있는 example.com 이름을 써서 운영처럼 같은 사이트로 맞춤. 화면 이미지는 `VITE_API_BASE_URL=http://api.example.com:8080`으로 다시 빌드 |
| 브라우저 | 설치된 Chrome(H.264 재생되는 것), 머리 없는 모드, Playwright 1.62.1. 데스크톱 1280×800, 모바일 Pixel 7 흉내(375×812, 안드로이드 UA → nginx가 `m.`으로 보냄) |
| 잰 값 | CDP `Network.loadingFinished.encodedDataLength`(전송된 압축 크기, 머리 포함) · 소켓 `webSocketFrameReceived/Sent` 글자 길이 + 틀 머리(받기 4·보내기 8바이트 어림) |
| 흐름 | ① `/login` 첫 접속 ② 로그인 → 로비(인트로 3초 보고 건너뛰기) ③ `/gameMode`·`/game-setup` 보고 → 봇 방장이 만든 방에 코드로 입장 → 대기방·준비 ④ 한 판(사람 1 + 봇 4, `backend/scripts/loadtest/bot.js`, 토론·투표·밤 30초) → 결과 ⑤ `/store` → `/mypage` |
| 다시 옴 | 같은 브라우저 프로필(캐시 그대로)로 껐다 켜서 ①~⑤ 한 번 더 (세션 쿠키라 다시 로그인) |
| 정리 | 시험 계정 6개(`loadtest+N@example.test`) 지움, 백엔드·nginx 컨테이너 멈춤, 화면 이미지 기본값(api.localhost)으로 다시 빌드, 브라우저 프로필 지움. DB 컨테이너는 원래 켜져 있어 그대로 |

| 첫 달 추가로 받는 것(E) | 10MB | 25MB | 45MB | 다른 밤 연출 4개 18MB·승패 영상 2.5MB·설정 영상 3.9MB·튜토리얼 PNG 14MB·명예의 전당 14MB 중 일부 |
| 접속마다 캐시 날아가 처음처럼 받을 확률 | 5% | 10% | 20% | 캐시 7일(nginx `max-age=604800`)이라 만료 자체는 304로 거의 0. 문제는 브라우저가 지움(모바일·사파리·용량 한도·시크릿 창) |
| 다시 올 때 기본 | 0.3MB/접속 | 같음 | 같음 | 실측 0.24MB |
| 배포로 JS·CSS 새로 받기 | 0.45MB × 월 4번 | 같음 | 같음 | 실측 |
| 판당 소켓(서버→사람) | 30KB | 60KB | 150KB | 실측 21~24KB(5명·짧은 판) |
| 동시 접속 최대 | 100~200명 | 100~200명 | 100~200명 | 활동자의 5~10% (요청 기준) |

계산: `월 GB = 새 사람 × (61.7 + E) + 로그인만 × 8.1 + 전원 × 접속 날 × (0.3 + 날아갈 확률 × 61.7) + 전원 × 1.8 + 전원 × 접속 날 × 판 수 × 소켓` (`cost-model.json`)

## 5. 줄이는 방법 (효과 큰 순)

절감 GB·원은 "보통"(187GB/월) 기준. 첫 방문 MB는 데스크톱·모바일 섞은 61.7MB 기준.

| 순위 | 방법 | 첫 방문 | 한 달 (보통) | 할 일 | 위험 |
|---|---|---|---|---|---|
| 1 | **PNG → WebP** (q80 안팎, 투명 유지) | 약 −33MB (그림 36MB → 약 3.6MB) | 약 −90GB · **−9,000원** | 339개 일괄 바꾸기, 코드의 `.png` 경로 바꾸기(글자 조립 경로 포함: `프로필-${name}_사각형.png` 등), `.normalize("NFD")` 경로 주의 | 화질(틀 장식 가장자리) 눈으로 확인. 아주 옛 브라우저 미지원(지금 사파리 14+는 됨). 큰 배경은 q75, 작은 틀은 무손실도 고려 |
| 2 | **영상 다시 압축** (720p 1.5~2.5Mbps, `+faststart`, 쓸데없는 소리 트랙 빼기) | 약 −15~20MB | 약 −45GB · **−4,500원** | ffmpeg `-crf 26~28`로 13개 다시 뽑기. 밤 연출 `*-stacked`는 위아래 투명 판이라 따로(crf 28 시험) | 연출 화질·투명 경계 확인. 이름 같으면 캐시 7일 동안 옛 파일 → 이름 바꾸기 |
| 3 | **모바일 전용 작은 그림** (세로 화면 폭 1080px 안팎) | 모바일 추가 약 −40~60% (WebP 뒤 기준) | 약 −10GB · −1,000원 | `m.` 쪽에 작은 판 폴더, nginx 모바일 미디어 경로 바꾸기 | 그림 두 벌 관리 |
| 4 | **늦게 받기(lazy)·미리 받기 줄이기**: 로그인 배경 영상 5.5MB를 첫 화면 정지 그림(poster) + 짧은/낮은 화질 루프로, 상점 진입 영상·결과 영상 `preload="auto"` → `metadata`, 화면 밖 상점 그림 `loading="lazy"` | 로그인만 보고 가는 사람 8MB → 약 2MB | 약 −5~15GB | `LobbyBackground`·`StoreEntryBackground`·`GameResultIntroVideo`·`SettingBackground`·밤 연출 `preload` 손보기 | 연출 시작이 늦어질 수 있음(연출은 미리 받기 유지, 배경만 줄이기) |
| 5 | **캐시 기간·이름**: 그림·영상 파일 이름에 해시(또는 `?v=`) 붙이고 `immutable` 1년 | 0 | 0.5~2GB (304 왕복·옛 파일 섞임 막기) | Vite로 불러오기(import)하거나 빌드 때 이름 바꾸기 | 경로 바꾸는 일이 큼. 돈 효과는 작고 **바꾼 그림이 7일간 안 바뀌는 문제**를 막는 게 주 목적 |
| 6 | **배경음 Opus 64k** | −0.85MB | 약 −1.5GB | ogg vorbis → ogg/webm opus | 사파리 옛 버전 opus 재생 확인 |
| 7 | **CDN(Global CDN) + Object Storage로 옮기기** | 0 | 단가 100 → 77원: 보통 **약 −3,000원**(요청 요금 더하면 거의 0) | 정적 파일 버킷에 올리고 CDN 주소로 | 지금 규모에선 돈 이득 거의 없음. 서버 대역폭·속도(지방·해외)엔 좋음. 1TB/월 넘으면 다시 볼 것 |
| 8 | **안 쓰는 파일 빼기** (webm 5개 20MB, `로비 설정창 영상.mp4` 4.3MB, 로고 몇 개, `frontend-mobile/dist`의 public 복사본) | 0 | 0원 | 지우기 전 참조 다시 확인(글자 조립 경로) | 트래픽 효과 없음. 이미지 크기·배포 시간만 줄음 |

추가로(우리 돈 아님, 사용자 데이터): 외부 글꼴 `Shilla_Culture*.woff2` 2개 4.5MB → 쓰는 글자만 남기기(subset)면 수백 KB. 모바일 첫 방문의 약 8%

1+2만 해도 첫 방문 약 62MB → **약 12~15MB**, 보통 한 달 187GB → **약 55GB(약 3,500원)**. 돈은 월 1만 원 남짓 줄지만 모바일 첫 로딩·데이터가 4~5배 가벼워짐
