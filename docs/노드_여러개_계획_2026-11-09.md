# Node 여러 개로 돌리기 구현 계획 (2026-11-09)

## 0. 한눈에

| 항목 | 결론 |
|---|---|
| 방 고정 방법 | **하이브리드 추천**: 로비 연결은 아무 Node나 받음(least_conn). 방은 만든 Node가 주인. 다른 Node 방에 들어갈 때 화면이 `?node=<SERVER_ID>`를 붙여 그 Node로 다시 붙음. nginx는 `$arg_node`로 그 Node에 보냄. 방·판·사람 → Node 짝은 Redis에 둠 |
| 지켜야 할 규칙 | "사람 소켓은 늘 그 사람 방·판이 있는 Node에 붙어 있음". 이 규칙이 지켜지면 판·방 코드(소켓 객체를 직접 쓰는 곳 15곳 이상)는 거의 그대로 둬도 됨 |
| HTTP | 아무 Node나 받음. 다른 Node 상태가 필요하면 Redis 디렉터리나 주인 Node에 묻는 RPC로 처리 |
| Redis 없을 때 | `REDIS_URL`이 비면 **단일 Node 모드**(지금과 같음, 기존 시험 212개 그대로). 값이 있는데 Redis가 죽었으면 **대체 동작**(4-6표) |
| 판·방 방송 | `io.local`로 보냄(Redis를 안 탐). 노드끼리 오가는 건 계정 채널·운영 신호·RPC뿐 |
| 프로세스 띄우기 | pm2 **cluster 모드는 안 씀**(포트를 같이 써서 특정 Node를 고를 수 없음). pm2 fork N개 또는 compose 서비스 N개로 띄우고, Node마다 포트와 `SERVER_ID`를 따로 줌 |
| 조각 | 1 기반(먼저) → 2 캐시·운영 신호·HTTP 읽기 / 3 접속·위치 / 4 방·로비·초대 / 5 화면·봇 / 6 운영·e2e 틀(병렬) → 감독이 통합 확인 |

## 1. 프로세스 메모리에만 있는 상태 전부

고치는 법 표기
- **고정**: 방 고정으로 충분함
- **Redis**: Redis로 옮김
- **방송**: 버스로 다른 Node에 알림
- **RPC**: 주인 Node에 물어봄
- **DB**: DB를 기준으로 삼음
- **그대로**: 손대지 않아도 됨

## 3. 방 고정 방법 비교와 추천

| 기준 | (a) nginx가 방 id로 나눔(hash) | (b) 연결은 아무 Node, 방 이벤트는 Redis로 주인에게 넘김 | (c) sticky + 방 만들 때 주인 정함 | **추천: (a)+(c) 하이브리드** |
|---|---|---|---|---|
| 로비에서 목록 보고 들어가기 | 로비 연결 때는 방 id가 없음. 방을 만든 Node ≠ hash 결과라 맞지 않음 | 됨 | sticky는 "한 화면 = 한 Node"일 뿐 방 사람끼리 모아 주지 않음 | 들어갈 때 한 번 `?node=`로 다시 붙음(100~300ms) |
| 재접속 | hash가 맞으면 됨. Node 수가 바뀌면 hash가 바뀌어 진행 중인 방이 깨짐 | 됨 | 쿠키·IP가 바뀌면 깨짐 | sessionStorage 힌트 + 접속 때 `loc:<uuid>`를 보고 `WRONG_NODE`로 제자리에 보냄 |
| 한 사람 한 판 | 어긋날 수 있음 | 사람 상태를 전부 Redis에 둬야 함 | 같음 | 사람 소켓이 늘 판 Node에 있음 → 지금 `playerSession` 검사가 그대로 맞음 + 노드 넘는 밀어내기 |
| 코드 고칠 양 | nginx만. 대신 위 문제들이 남음 | **매우 큼**: ack·`socket.join`·`socket.data`·`io.sockets.sockets.get`을 쓰는 판·방 처리기 전부, 메시지 직렬화 두 번(CPU가 오히려 늘어남) | 중간 | 연결 미들웨어 1개 + 입장 계열 답 4곳 + 디렉터리 쓰기 + 화면 재접속 도우미 |
| Node 수 바꾸기 | hash 다시 나눔 → 위험 | 상관없음 | 상관없음 | 상관없음(주인 기록이 Redis에 있음) |
| Redis 죽음 | 영향 없음 | **전부 멈춤** | 일부 | 판은 계속 돎. 다른 Node 방 입장만 "잠시 후" |

추천하는 이유
- 판 코드가 소켓 객체에 기대는 곳이 많음(앞 문서 1-5·1-6 표, `ownership.js` `getSocketForUuid`, 밤 `notify.js`의 `registry.get`, `start.js` `game_started` 사람마다 다른 내용). 그래서 사람을 판 Node로 옮기는 쪽이 가장 작고 안전함
- 웹소켓만 씀(`transports:["websocket"]`, socket.js:46). 그래서 손잡기용 sticky는 필요 없음. 업그레이드 요청 한 번만 nginx가 고르면 됨
- 파티(판 끝 → 다음 방)는 모두 같은 Node에 있어서 이동이 없음

이동 흐름

| 상황 | 서버 | 화면 |
|---|---|---|
| 접속 | `io.use(nodeRouting)`(인증 다음): `loc:<uuid>`가 살아 있는 다른 Node고 bootEpoch가 같으면 `next(err)` (`err.message='WRONG_NODE'`, `err.data={node}`). 죽은 Node면 loc를 CAS로 지우고 받음. 내가 draining이고 loc가 없으면 덜 바쁜 Node로 보냄 | connect_error에서 `WRONG_NODE`면 `socket.io.opts.query.node=data.node` → `socket.connect()`. 30초에 3번이 넘으면 힌트를 지우고 그냥 접속 |
| 코드 입장·공개방 입장 | `roomcode`/`room` 주인 ≠ 나 → `room_join_failed{code:'ROOM_ON_OTHER_NODE', node}` | `moveToNode(node)` 뒤 같은 요청을 한 번 다시 |
| 초대 수락 | 초대 행 `room_id` → `room:<id>` 주인 ≠ 나 → ack `{ok:false, code:'ROOM_ON_OTHER_NODE', node}` (DB는 안 건드림) | 같음 |
| 다음 방 묻기 | 우편함에 없고 `game:<id>` 주인 ≠ 나 → 같은 답 | 같음 |
| 목표 Node 죽음 | `NODE_UNAVAILABLE` | "방을 찾을 수 없습니다" + 로비 그대로 |
| 방 만들기 | 지금 Node가 주인(이동 없음). 2단계에서 바쁘면 덜 바쁜 Node로 옮기기(선택) | - |

## 8. 운영

### 8-1. compose (base의 `backend`를 n1로 쓰고 생성기가 n2.. 추가 → `compose exec backend` 스크립트는 그대로 됨)

```yaml
# docker-compose.yml 추가
  redis:
    image: redis:7.4-alpine
    command: ["redis-server","--save","","--appendonly","no","--maxmemory","256mb","--maxmemory-policy","volatile-lru","--requirepass","${REDIS_PASSWORD}"]
    healthcheck: { test: ["CMD","redis-cli","-a","${REDIS_PASSWORD}","ping"], interval: 5s, retries: 20 }
    restart: unless-stopped
  backend:
    environment: [ ..., SERVER_ID=n1, "REDIS_URL=redis://:${REDIS_PASSWORD}@redis:6379" ]
    depends_on: { db: {condition: service_healthy}, redis: {condition: service_healthy} }
# docker-compose.nodes.yml (gen-nodes.js가 NODE_COUNT로 만듦)
services:
  backend-n2:
    extends: { service: backend }
    environment: [ SERVER_ID=n2 ]
```

- Redis는 캐시·버스 용도라 디스크에 저장하지 않음. 키에는 전부 TTL을 둠
- 포트는 밖으로 안 엶. 기계가 여럿이면 사설망 + 비번(`rediss://` 고려)

### 8-2. nginx upstream 예시 (생성)

```nginx
upstream mmc_any { least_conn; zone mmc_any 64k;
  server backend:4000    max_fails=1 fail_timeout=5s;
  server backend-n2:4000 max_fails=1 fail_timeout=5s; }
upstream mmc_n1 { zone mmc_n1 64k; server backend:4000 max_fails=1 fail_timeout=5s; server backend-n2:4000 backup; }
upstream mmc_n2 { zone mmc_n2 64k; server backend-n2:4000 max_fails=1 fail_timeout=5s; server backend:4000 backup; }
map $arg_node $mmc_upstream { default mmc_any; n1 mmc_n1; n2 mmc_n2; }
# location /socket.io/ · / · /internal 안: proxy_pass http://$mmc_upstream;
```

- 주인 Node가 죽으면 backup으로 감 → 받은 Node가 loc를 안 믿고 그냥 받음(MN-109)
- 컨테이너가 꺼진 채 nginx가 켜질 때 대비: `resolver 127.0.0.11` + `server ... resolve` 확인 필요(10장)
- pm2(도커 없이): Node마다 `127.0.0.1:4001..`

### 8-3. pm2

- `ecosystem.config.cjs`가 `NODE_COUNT ?? os.cpus().length`개 앱을 만듦
  - fork 모드, 앱마다 `PORT=4001+i`, `SERVER_ID=n{i}`
  - `max_memory_restart`·`kill_timeout`은 그대로
- cluster 모드를 안 쓰는 이유: 워커들이 포트 하나를 같이 써서 nginx가 `?node=`로 특정 워커를 고를 수 없음

### 8-4. SERVER_ID·로그

- Node마다 고정된 값. 컨테이너 hostname은 쓰지 않음(다시 만들면 바뀜)
- 로그 파일: `app-<SERVER_ID>-YYYY-MM-DD.log`. 같은 기계에서 pm2 Node들이 같은 폴더에 쓰기 때문에 이름을 나눔. 정리 패턴도 같이 바꿈
- 콘솔 줄 앞에 `[n2]`, morgan 줄에 `:server-id`

### 8-5. /health·/internal/live 합치기

| 경로 | 보여 줄 것 |
|---|---|
| `/health` (Node마다, docker healthcheck) | `ok`, `serverId`, `redis: up\|down\|off`, `draining`, (열쇠 있으면) 서버 숫자. Redis down이어도 200(대체 동작으로 돎). 응답에 표시만 함 |
| `/internal/cluster` (새) | 하트비트 표: id·bootEpoch·startedAt·games·rooms·online·loopP95·draining·lastSeen |
| `/internal/live` | 전 Node `ops.liveSummary` callAll 합침: `onlineCount` 합, rooms·games에 `node` 칸, `nodes:[...]`, `partial`. `?node=n2`면 nginx가 그 Node로 보내고 그 Node 것만 |
| 관리자 서버 | 위 둘만 부르면 됨 |

### 8-6. 배포할 때 Node 하나씩 바꾸기

| 순서 | 할 것 |
|---|---|
| 0 | 화면 먼저 배포(조각 5) · DB 마이그레이션은 앞뒤 버전이 같이 돌 수 있는 것만(넓히기→좁히기) · 이미지 pull |
| 1 | `POST /internal/nodes/n1/drain` → n1이 새 로비 접속·방 만들기를 다른 Node로 보냄. 판·방은 계속 |
| 2 | `/internal/cluster`에서 n1 games=0·rooms=0이 될 때까지 기다림(최대 40분. 넘으면 그 Node만 점검 안내 뒤 진행) |
| 3 | n1 끄기(SIGTERM → 그 Node 사람에게만 server_shutdown) → 새 이미지로 켜기 → `/health` ok + redis up |
| 4 | 새 부팅은 drain이 꺼진 상태로 시작 → n2..로 반복 |
| 되돌리기 | 같은 순서로 옛 이미지. 크게 망가지면 `REDIS_URL` 빼고 `NODE_COUNT=1`(단일 모드) |

- `remote.sh`의 "점검 켜기 → 전체 판 0개 기다리기"는 깨지는 마이그레이션 때만 씀
- migrate는 `compose run backend` 한 번만

## 10. 확인 못 한 것

- `@socket.io/redis-adapter`·`ioredis`가 node_modules에 없음. 버전별 Redis 끊김 동작과 sharded adapter 지원 여부는 문서 기억 기준
- socket.io-client가 미들웨어 오류 뒤 자동 재접속을 안 하는 점, `socket.io.opts.query`를 바꾼 뒤 `connect()`할 때 반영되는 점 → 실측 필요
- nginx `proxy_pass http://$변수` + upstream `backup` + `resolve`(오픈소스 1.27.3+) 조합 `nginx -t` 안 해 봄. 이미지 태그 `nginx:1.27-alpine`의 실제 부 버전 미확인
- 화면에서 방 입장·초대 수락 실패를 처리하는 정확한 훅 위치. 보낸 곳 파일만 찾았고 훅은 안 읽음
- 성능 에이전트가 커밋하지 않은 다른 작업이 있는지(작업 트리에 backend 변경 없음만 확인). 그 뒤 바뀌면 줄 번호 다시 확인
- e2e 2031개 중 Node 2개에서 실제로 깨지는 수(돌려 봐야 앎). Windows에서 e2e용 Redis는 docker가 필요함
- 운영 MySQL `max_connections`·서버 코어 수·같은 기계의 DB/nginx CPU 몫(코어 수만큼 Node를 띄울 때 남는 여유)
- 결제 완료 소켓 알림: 지금은 없다고 봄(웹훅 경로 없음, emitToUser 부르는 곳 목록 기준)
- 기계 여러 대 단계: 앞단 LB 위치(클라우드플레어 LB 또는 nginx 하나), Redis 위치·TLS는 정하지 않음
