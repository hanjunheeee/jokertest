# 마이그레이션 적용·복구 절차

- 출처: 지운 `docs/requirements/2026-09-09-f01-migration-runbook.md`(git `HEAD`에 남아 있음)의 3·5절을 지금 구조에 맞게 줄임
- 지금 구조: 서버 시작 때 `sync()` 없음 → 표는 마이그레이션만 만듦. 백엔드 컨테이너가 `migrate` 먼저 돌리고 성공해야 서버 켬(`backend/Dockerfile` CMD)
- 명령: `node scripts/migrate-db.js <status|migrate|resolve-failure>` (컨테이너 안 경로, 저장소에선 `backend/scripts/migrate-db.js`)
- 이력 표: `schema_migrations` (이름·체크섬·상태 `running`/`applied`/`failed`·오류 문구), `GET_LOCK`으로 동시에 하나만 돎

## 1. 평소 적용 (새 마이그레이션 들어간 배포)

1. **백업 먼저**: `docker compose exec db sh -c 'mysqldump --single-transaction --routines --triggers -uroot -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE"' > backup-$(date +%Y%m%d%H%M%S).sql`
2. **판 없는 시간에**: 백엔드 교체 = 진행 중 판 사라짐(판이 메모리에 있음)
3. **상태 보기**: `docker compose run --rm backend node scripts/migrate-db.js status` → `failed`·`running` 있으면 아래 2장 먼저
4. **적용**: 백엔드 다시 켜면 CMD가 `migrate` → 서버 순서로 돎. 손으로 할 땐 `docker compose run --rm backend node scripts/migrate-db.js migrate`
5. **확인**: 다시 `status` → 전부 `applied`, 백엔드 로그 `[STARTUP] 성공`

## 2. 실패했을 때

`migrate`가 실패하면 그 마이그레이션이 `failed`(이력 쓰기도 실패면 `running`)로 남고, 다음 `migrate`는 그 이력 때문에 시작을 거부함(원인 확인 없이 다시 돌리는 것 막기). 백엔드 컨테이너도 서버를 안 켬 → `docker compose logs backend`로 오류 보기.

어느 길인지 애매하면 **늘 A**(데이터 잃을 걱정 없는 쪽).

### A. 전체 백업 복원 (기본)

- 언제: DDL 자체가 실패, 또는 실패 뒤 DB 상태를 못 믿을 때. MySQL DDL은 바로 확정돼서 열 하나만 추가된 반쯤 상태가 남을 수 있음
1. 1장에서 받은 백업으로 복원: `docker compose exec -T db sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE"' < backup-<시각>.sql` (관리형 DB면 스냅샷 복원)
2. 백업에 `schema_migrations`도 들어 있어 실패 이력도 같이 사라짐 → `resolve-failure` 필요 없음
3. `status`에서 그 마이그레이션이 `pending`인지 확인
4. 원인 고친 뒤 다시 `migrate`

### B. 이력만 정리 (`resolve-failure`)

- 언제: `status`의 오류 문구에 `[DDL은 성공, 이후 단계(verify 또는 이력 기록)에서 실패]`가 있을 때, 또는 `running`으로 멈춘 줄(동시 실행이 아니라 중간에 죽은 흔적)
1. 실제 DB에서 그 마이그레이션 변경이 다 들어갔는지 눈으로 확인 (`SHOW CREATE TABLE <표>`, `DESCRIBE <표>`)
2. 다 들어갔고 데이터 이상 없으면: `docker compose run --rm backend node scripts/migrate-db.js resolve-failure --name <마이그레이션 이름> --confirm` (`--confirm` 없으면 거부)
3. 원인(DB 연결·잠금 등) 고치고, 이미 들어간 변경을 다시 돌려도 괜찮은지 확인한 뒤 `migrate`

## 3. 새 DB

- 빈 DB면 `migrate`가 `0001` 기준선부터 전부 만듦. 서버가 먼저 표를 만드는 길(`sync()`)은 없어졌으니 순서 꼬임 걱정 없음
- 옛날에 `sync()`로 만든 DB를 가져오면 `0001` 구조 비교에서 거부될 수 있음 → 추측해서 이력 넣지 말고 새 DB에 데이터만 옮기기
