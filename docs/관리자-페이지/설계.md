# 관리자 페이지 설계

- 근거: `기획.md`·`스토리.md`(확정), `결정.md`, `docs/운영_받침_2026-11-09.md`, `reports/전수조사_2026-11-09/admin/src/build_admin_guide.py`(옛 관리자 서버 가이드: 장부·시간대·잠금·보안 규칙은 그대로 가져옴)
- 한 줄: 게임 서버 안에 `/admin-api/*`를 붙이고, 화면은 `frontend/src/admin/`을 따로 빌드해 `admin.<도메인>`에서만 엶
- 쓰는 사람: 관리자 둘(대표·CTO), 권한 같음
- 코드는 아직 없음. 단위·약속은 `경계.md`, 시험은 `테스트.md`, 순서·상태는 `진행.md`

## 1. 한눈에

```
관리자(대표·CTO) PC·휴대폰
  → 클라우드플레어 Access (문 1: 관리자 이메일 둘 + 메일 번호)
  → nginx admin.<도메인>
       ├─ /            관리자 화면 (frontend/dist-admin, 플레이어 화면 파일 없음)
       └─ /admin-api/* 게임 서버 Node 아무 곳
             → Access 표 다시 확인 (문 1 서버 쪽)
             → 우리 로그인 세션 확인 (문 2: 아이디·비번·OTP)
             → CSRF 확인 (쓰기만)
             → 영역 처리 → 같은 MySQL · 기존 서비스(끊기·공지·다시 읽기·지금 상황·장부·알림)
             → 쓰기마다 admin_audit_logs 한 줄
플레이어 화면 (example.com · m.example.com)
  → /inquiries (문의 창, 플레이어 로그인 그대로)
  → 소켓 maintenance_notice (점검 큰 안내)
```

## 2. 관리자 쪽 요구사항 5개 — 합침 / 더함

규칙: 이미 있는 기능(15개 계획·기존 코드)이면 합쳐서 하나로, 없는 것만 더함

| 요구사항 | 이미 있는 것 (합침) | 새로 더함 |
|---|---|---|
| 1 관리자 인증(대표·CTO, 관리자 외 막기) | 스토리 1 문 두 개, `admin_users` 표, 플레이어 토큰과 분리 | 관리자 계정 둘을 명령으로 만듦, Access 정책에 이메일 둘. 플레이어 토큰(`role=ADMIN` 포함)으로 `/admin-api` 전부 막힘 시험 |
| 2 운영 현황 | 스토리 2 첫 화면, 기존 `getClusterLiveSummary`(진행 판·접속 수, Node 합침) | 전체 가입자 수 · 오늘 총 판 수(오늘 끝난 판 + 지금 진행 중) 칸 |
| 3 공지(전체·특정 회원·발송 결과) | 기존 공지 서비스(`services/ops/announcements.js`: 'online'·'users', 결과 `recipientCount·created·duplicated·failed` 이미 돌려줌, 같은 id 한 번) | 결과를 화면에 보여 주기 + 관리자 기록(`ANNOUNCE`)에 제목·대상·결과 수 같이 저장 → 이력. 새 표 없음 |
| 4 회원 관리·제재 | 스토리 5(찾기·정지 풀기), `user_bans`(기간·영구 `is_permanent`·사유 `reason` 이미 됨), 기존 즉시 끊기 서비스 | UUID 찾기 · 접속 중 표시(`online_presence`) · 강제 접속 종료 버튼 · 정지 기간 바꾸기 · **해제 사유**: `user_bans`에 해제 칸이 없음 → 0031에 `lifted_at`·`lifted_by`·`lift_reason` 더함 |
| 5 처리 이력 | 스토리 9 관리자 기록 보기, `admin_audit_logs` | 기록 화면에 "공지 발송 이력"·"제재·해제 이력" 칸(동작 묶음으로 거름) + 회원으로 찾기. 새 표 없음 |

## 3. 스택

| 항목 | 고른 것 | 이유 | 버린 안 |
|---|---|---|---|
| 서버 | 게임 서버(Express 5) 안 `backend/admin/` | 기획 결정: 관리자 서버 따로 안 둠. 장부·끊기·다시 읽기 규칙을 한 곳에서 지킴 | 관리자 서버 따로 |
| 서버 경로 | `/admin-api/*` | 플레이어 경로·내부 통로(`/internal`)와 이름부터 갈림 | `/admin/*`(화면 주소와 헷갈림) |
| 화면 | 기존 `frontend` 안 `src/admin/` + 따로 입구 `admin.html` + `vite.admin.config.js` → `dist-admin/` | 사용자가 정함. 같은 도구(React 19·Vite 8·Tailwind 4), 설치 없음. 입구·빌드가 따로라 플레이어 묶음에 관리자 코드가 안 들어감 | `frontend-admin/` 새 프로젝트(사용자가 버림) · 한 빌드에 입구 둘(플레이어 `dist`에 `admin.html`·관리자 조각이 같이 나감) |
| 주소 | `admin.<도메인>` 한 곳에서 화면 + `/admin-api` (같은 출처) | 쿠키를 이 주소에만 묶음, CORS 필요 없음, Access를 주소 하나에 걺 | `api.<도메인>/admin-api`(플레이어 쿠키·CORS와 섞임, Access 걸면 플레이어 API도 막힘) |
| 클라우드플레어 확인 | 기존 `jsonwebtoken` + Node `crypto`(JWK → 공개키) + 기본 `fetch` | 설치된 것으로 됨 | 새 라이브러리 |
| OTP | Node `crypto`로 직접(RFC 6238, 30초, 6자리) | 40줄 안팎, 표준 시험 값으로 확인 | otplib 설치 |
| 비번 해시 | 기존 `utils/auth/credentials.js`(bcrypt 비용 10) | backend가 이미 쓰는 방식 | argon2 |
| 세션 | DB 표 `admin_sessions` + httpOnly 쿠키 | Node 여러 개 어디로 와도 같음, 바로 끊기 됨 | JWT(즉시 끊기 어려움) · Node 메모리 |
| 그래프 | 손으로 그린 SVG 막대 | 통계 하나뿐, 설치 없음 | 차트 라이브러리 |
| 시험 | 서버 `node --test`(+ `test:with-db`), 화면 `node --test`+jsdom, 브라우저 기존 `e2e/`(Playwright 1.62.1) | 지금 쓰는 틀 그대로 | 새 시험 도구 |

## 4. 폴더 구조

### 4-1. 서버 `backend/admin/` (기존 backend 모양 그대로)

```
backend/
 ├─ admin/                         ← 관리자 코드 전부
 │   ├─ index.js                   /admin-api 조립: 꺼짐 → no-store → Access → 요청 수 → /auth → 로그인 → CSRF → 영역들 → 오류
 │   ├─ config.js                  ADMIN_* 환경값 읽기·검사 (한 곳)
 │   ├─ routes/<영역>.routes.js     경로만 (뼈대가 빈 파일로 먼저 다 만듦)
 │   ├─ controllers/<영역>.controller.js   요청 모양 검사 → 서비스 → 응답
 │   ├─ services/core/             Access 표 확인·OTP·비밀 잠금·로그인·잠금·세션·기록·조회 줄 세우기·정리
 │   ├─ services/<영역>/            영역 일
 │   ├─ middlewares/               access·adminSession·csrf·adminError
 │   └─ scripts/admin-account.js   관리자 계정 명령 (npm run admin:account)
 ├─ routes/inquiry.routes.js · controllers/inquiry.controller.js · services/inquiry/   플레이어 문의 (플레이어 쪽이라 기존 자리)
 ├─ services/ops/maintenanceClock.js · maintenanceNotice.js   점검 시계·큰 안내 신호 (게임 쪽이라 기존 ops 자리)
 ├─ models/ops/                    새 모델도 여기
 └─ db/migrations/0031·0032        새 마이그레이션
```

- **모델·마이그레이션은 기존 자리**(`models/ops/`, `db/migrations/` + `scripts/migrate-db.js` 목록)
  - `models/index.js`는 `models/` 아래만 돌며 읽음 → `backend/admin/models`면 로더를 고쳐야 함
  - 마이그레이션 실행기는 `scripts/migrate-db.js`의 `MIGRATIONS` 목록 한 곳만 봄(체크섬·순서) → 표 구조 기록을 두 곳으로 가르지 않음
  - 관리자 표 모델은 이미 `models/ops/`에 있음 → 같은 자리
- 깊이: `backend/admin/services/core/x.js` = 4칸 (`check:depth` 6칸 안)

### 4-2. 화면 `frontend/src/admin/` (기존 src 모양 그대로)

```
frontend/
 ├─ admin.html                 관리자 입구 (index.html과 따로)
 ├─ vite.admin.config.js       입구 admin.html, 결과 dist-admin/, 개발 포트 5175, /admin-api → 4000 프록시
 ├─ src/admin/
 │   ├─ main.jsx
 │   ├─ app/                   AdminApp · adminRoutes(메뉴·경로 표) · AdminLayout(PC 왼쪽 메뉴 / 폰 위 막대+서랍) · index.css
 │   ├─ shared/api/            adminClient (같은 출처 /admin-api, CSRF 머리글, 401이면 로그인으로)
 │   ├─ shared/ui/             DataList(넓으면 표·좁으면 카드) · ConfirmDialog · Field · StatusNote · PageHeader
 │   ├─ shared/utils/          time(UTC → 한국 시각) · requestId(요청 번호)
 │   └─ domains/<영역>/         api · pages · components · hooks
 ├─ src/domains/inquiry/       플레이어 문의 창 (데스크톱)
 ├─ src/domains/maintenance/   플레이어 점검 큰 안내 (로직은 데스크톱·모바일 같이 씀)
 └─ tests/admin/…              src/admin과 같은 모양
frontend-mobile/src/domains/inquiry/ · maintenance/   모바일 화면 (관리자 코드는 안 들어감)
```

- **플레이어 묶음과 안 섞이게 (세 겹)**
  1. 입구 따로: 플레이어 `index.html → src/main.jsx`는 `src/admin`을 안 부름
  2. 빌드 따로: `vite.config.js`(그대로) → `dist/` / `vite.admin.config.js` → `dist-admin/` → 플레이어 사이트 폴더엔 관리자 파일이 없음
  3. 막기 규칙: `eslint.config.js`에서 `src/admin` 밖 → `@/admin/*` 금지, `src/admin` 안 → 플레이어 `@/domains/*`·`@/shared/*` 금지 + 빌드 결과 검사 시험(AD-045)
- **관리자 주소에서만 열림**: nginx `admin.<도메인>` 사이트만 `dist-admin`을 줌. 플레이어 사이트엔 `admin.html` 없음, `api.<도메인>`의 `/admin-api`는 nginx가 404
- 휴대폰: 같은 관리자 화면 반응형(768px 아래 표 → 카드, 메뉴 서랍). `frontend-mobile`엔 관리자 코드 안 넣음

## 5. 보안 설계

### 5-1. 문 1 — 클라우드플레어 Access (서버에서도 확인)

| 항목 | 정한 것 |
|---|---|
| 대시보드 | Zero Trust → Access → Application `admin.<도메인>`, 정책: 관리자 이메일 둘만, 로그인 방법 One-time PIN(메일 번호), 세션 24시간 |
| 서버 확인 | 머리글 `Cf-Access-Jwt-Assertion` JWT를 팀 공개키로 검증: RS256만, `aud` = `ADMIN_ACCESS_AUD`, `iss` = `https://<팀>.cloudflareaccess.com`, 만료, `email` 있음 |
| 공개키 | `https://<팀>.cloudflareaccess.com/cdn-cgi/access/certs`를 Node마다 받아 1시간 보관, 모르는 `kid`면 1분에 한 번까지 다시 받음, 3초 시간 초과 |
| 실패 | 표 없음·틀림 → `403 ADMIN_ACCESS_REQUIRED` / 키 못 받음 + 보관본 없음 → `503 ADMIN_ACCESS_UNAVAILABLE` (막히는 쪽) |
| 왜 서버도 | 클라우드플레어 설정이 꺼지거나 원본 주소로 바로 와도 서버가 막음 |
| 끄기(개발·시험) | `ADMIN_ACCESS_MODE=off` — `NODE_ENV=production`이면 무시. 운영에서 팀·AUD 값이 없으면 `/admin-api` 전체 꺼짐(404) |
| 기록 | 표의 `email` → 로그인 시도·세션·관리자 기록에 같이 남김 |

### 5-2. 문 2 — 우리 로그인

| 항목 | 정한 것 |
|---|---|
| 입력 | 아이디·비번·OTP 6자리 세 칸, `POST /admin-api/auth/login` 한 번 |
| 틀림 | 아이디 없음·비번 틀림·OTP 틀림 모두 같은 `401 ADMIN_LOGIN_FAILED`, 없는 아이디도 bcrypt 비교 한 번(시간으로 안 새게) |
| 이메일 맞추기 | Access 이메일 = `admin_users.email`이어야 통과, 아니면 `403 ADMIN_EMAIL_MISMATCH` → 두 문이 같은 사람 (Access 꺼진 개발·시험은 건너뜀) |
| 비번 | bcrypt 비용 10, 12자 이상, 명령으로만 정함 |
| OTP | RFC 6238 SHA-1 30초 6자리, 앞뒤 한 칸 허용, 쓴 칸 번호를 `totp_last_step`에 남겨 같은 번호 다시 못 씀 |
| OTP 비밀 저장 | AES-256-GCM, 열쇠 `ADMIN_TOTP_KEY`(16진수 64자), 모양 `v1:<iv>:<tag>:<암호문>` |
| 잠깐 막기 | 같은 아이디 15분 안 5번 틀림 → 15분 / 같은 IP 15분 안 20번 → 15분 → `429 ADMIN_LOGIN_LOCKED { retryAfterSec }`, 막힌 동안은 맞아도 막힘. 셈은 DB 표 `admin_login_attempts`(Node 여러 개도 같음) |
| 요청 수 제한 | 기존 `createRateLimiter`: 로그인 IP 1분 10번, `/admin-api` 전체 IP 1분 300번 |
| 관리자 계정 | 서버에서 `npm run admin:account -- create --login <아이디> --email <이메일>` → 비번 두 번 입력(안 보임) → OTP 비밀을 한 번만 보여 줌(앱에 직접 넣기 + `otpauth://` 주소). 대표·CTO 둘을 이렇게 만듦 |
| 계정 명령 | `create` · `reset-password` · `reset-otp` · `disable` · `enable` · `unlock` · `list`. 운영: `docker compose … exec backend npm run admin:account -- list`. 기존 `npm run admin`(내부 통로 점검)과 이름 안 겹침 |
| 권한 | 나누지 않음. `role` 칸은 두되 안 봄(만들 때 `SUPER`) |

### 5-3. 세션·자동 로그아웃·CSRF·플레이어 분리

| 항목 | 정한 것 |
|---|---|
| 쿠키 | `mmc_admin_sid` = 무작위 32바이트, `HttpOnly`·`SameSite=Strict`·`Path=/`·운영 `Secure`, Domain 없음 |
| DB | `admin_sessions.id` = 쿠키 값 sha256 (원문은 DB에 없음) |
| 자동 로그아웃 | 가만히 30분(`ADMIN_SESSION_IDLE_MIN`) 또는 로그인 뒤 12시간 → `401 ADMIN_SESSION_EXPIRED`. 활동 시각은 1분에 한 번만 고침 |
| 자동 새로고침 | 첫 화면·열린 방 30초마다, 머리글 `X-Admin-Background: 1` → 활동으로 안 셈 |
| CSRF | 쓰기 전부: `Origin` = `ADMIN_ORIGIN` + 머리글 `X-Admin-Csrf` = sha256(`csrf:` + 쿠키 원문)(로그인·`/auth/me` 응답으로 줌) + SameSite=Strict → 틀리면 `403 ADMIN_CSRF_FAILED` |
| 플레이어 분리 | 관리자 경로는 플레이어 `accessToken`을 아예 안 읽음, 플레이어 경로는 `mmc_admin_sid`를 안 읽음 → 플레이어 토큰(`role=ADMIN`이어도)으로 `/admin-api` 전부 401 |
| 응답 | `/admin-api` 전부 `Cache-Control: no-store` |

### 5-4. 관리자 기록 (admin_audit_logs)

- 남기는 것: 쓰기 전부 + 개인정보 보기 + 채팅 증거 보기 + 로그인·로그아웃
- 칸: 누가 · 무엇을(`action`) · 대상(`target_type`·`target_id`) · 전후 값 · 사유(`reason`) · IP · Access 이메일 · 요청 번호 · 시각
- DB 바꾸는 일은 **같은 트랜잭션**에서 기록. DB 밖 일(끊기·다시 읽기·공지 결과)은 `after_value`에 결과를 실음
- 비번·OTP·쿠키·Access 표 원문은 기록 도우미가 빼고 넣음. 기록 고치기·지우기 경로는 없음
- 동작 이름은 뼈대가 `admin/services/core/auditActions.js` 한 곳에 미리 다 적음

| action | 언제 | 이력 칸 |
|---|---|---|
| ADMIN_LOGIN · ADMIN_LOGOUT | 로그인 성공·로그아웃 (실패는 `admin_login_attempts`) | — |
| VIEW_PII · VIEW_EVIDENCE | 이메일 전체 보기 · 신고 채팅 증거 열기 | — |
| FORCE_DISCONNECT | 강제 접속 종료 | 제재·해제 |
| BAN · BAN_UPDATE · UNBAN | 정지(기간·영구) · 기간 바꾸기 · 해제(사유) | 제재·해제 |
| REPORT_RESOLVE · REPORT_DISMISS | 신고 처리(정지) · 기각 | 제재·해제(처리만) |

## 7. 돈 규칙 (옛 가이드 그대로)

| 일 | 장부 reason | 참조 id | 두 번 눌러도 |
|---|---|---|---|
| 골드·다이아 주기 | ADMIN_GRANT | `admin:<requestId>` | 같은 요청 번호면 처음 결과, 내용 다르면 409 |
| 뺏기 | ADMIN_REVOKE (음수) | `admin:<requestId>` | 같음 |
| 환불 | TOPUP_REFUND (다이아 음수) | `refund:<orderId>` | 주문당 한 번 |

- 요청 번호는 화면이 폼을 열 때 하나 만듦(UUID)

## 8. 점검 — 강제 종료 · 큰 안내 · 점검 순서

### 8-1. 시작 시각에 판 강제 종료

| 항목 | 정한 것 | 이유 |
|---|---|---|
| 누가 끝내나 | **Node마다 자기 시계로** 자기 판·방을 끝냄 (`services/ops/maintenanceClock.js`) | 판·방은 만든 Node 메모리에만 있어 그 Node만 끝낼 수 있음. 한 Node가 버스로 시키는 방식은 Redis down이면 다른 Node가 못 받고, 결국 Node마다 다시 해야 함. Node들은 같은 기계 시계를 씀(docker도 호스트 시계) |
| 시계 맞추기 | 점검 상태를 다시 읽을 때마다(관리자 저장 → `reloadEverywhere`, 버스, 60초 안전망, Redis 살아남, 서버 시작) 타이머를 지우고 다시 검: 켜짐 + 시작 시각 있음 → 그 시각에, 이미 지났으면 바로 | 늦게 받은 Node도 60초 안에 따라옴, 서버 다시 켜도 이어짐 |
| 취소 | 시작 전에 끄거나 시각을 미루면 다시 읽을 때 타이머가 지워짐 → 안 끝남 | |
| 끝내는 것 | 진행 중 판 전부(`phase`가 ENDED 아닌 것): 기존 `endGameSessionForPlayer(<첫 참가자>, 'MAINTENANCE', gameId)`(진행 중이면 판째로 지움) → 기존 `finalizeGameSessionEnd(io, session, 'MAINTENANCE', null, cleanupUuids)`(저장·타이머·대기방 정리·`game_ended` 방송·채널 떼기 그대로) | 판 끝내기 길을 새로 안 만들고 그대로 탐 |
| 무효 | 끝내기 전 `session.abortReason = 'MAINTENANCE'` → 전적 기록 `completed:false`·`winner:'NONE'`·`win_reason:'MAINTENANCE'`·나간 사람 없음 → 모두 `won:null`·통계 줄 없음. 전적 저장 뒤 업적 평가를 `abortReason`이 있으면 건너뜀 | 승패·보상·벌점·업적 없음. 기존 "깨진 판"은 나간 사람만 패라서 그대로 쓰면 안 됨 |
| 고치는 기존 파일 | `game-core/result/record.js`(win_reason 한 줄: `session.abortReason ?? ABORTED_WIN_REASON`) · `services/game/record/persist.js`(업적 평가 건너뛰기 한 줄) — 더하기만 | |
| 이미 끝난 판 | 결과 화면(`ENDED`)은 건드리지 않음 | 이미 승패 난 판 |
| 대기방 | 이 Node 대기방 전부 닫음: 방 채널에 기존 `room_deleted`에 `{ code:'MAINTENANCE', message }`를 더해 보내고 방 정리 → 화면은 로비로 | 기존 방 지우기 사건 그대로, 칸만 더함 |
| 기록 | Node마다 `MAINTENANCE_FORCE_END` 한 줄(끝낸 판 수·닫은 방 수·Node) | 관리자 기록에 남음 |
| 새 판 | 이미 점검 중이라 방 만들기·시작·입장 거절(기존) | |

### 8-2. 큰 안내 (실시간 신호)

| 신호 | 모양 | 언제 |
|---|---|---|
| 소켓 `maintenance_notice` (서버 → 플레이어) | `{ state: 'scheduled' \| 'active' \| 'cleared', message, startsAt, endsAt, serverNow, forceEndAtStart: true }` (시각은 ISO, UTC) | ① 접속할 때(켜짐이면) ② 상태가 바뀌어 이 Node가 다시 읽었을 때 → 이 Node 접속자에게 `io.local.emit` ③ 시작 시각(`active`) ④ 끄면 `cleared` |
| 기존 `game_ended` | `{ gameId, reason: 'MAINTENANCE' }` | 시작 시각 판 강제 종료 |
| 기존 `room_deleted` | `{ code: 'MAINTENANCE', message }` | 시작 시각 대기방 닫힘 |

- Node 여러 개: 관리자 저장 → `reloadEverywhere`·버스 `ops.reload`로 Node마다 다시 읽음 → Node마다 자기 접속자에게 보냄(`io.local`, 같은 안내 두 번 안 감). 버스를 못 받은 Node는 60초 안전망으로 따라옴
- 화면(데스크톱·모바일 같은 로직 `frontend/src/domains/maintenance/`):
  - `scheduled` → 화면 가운데 큰 안내: 점검 시각 · 남은 시간(1초마다 줄어듦, `serverNow`로 기기 시계 차이 고침) · "시각이 되면 진행 중 판이 강제로 끝나요" · 닫기
  - 닫아도 위쪽 작은 띠에 남은 시간 계속(판 화면을 안 가리는 높이)
  - 10분 전·1분 전에 큰 안내 다시
  - `active` + `game_ended MAINTENANCE` → 큰 안내 "점검으로 판이 끝났어요(승패 없음)" → 확인 누르면 로비
  - `cleared` → 큰 안내·띠 사라짐
  - 판 결과·전적 화면에서 `win_reason MAINTENANCE` → "점검으로 끝남"

### 8-3. 관리자 점검 화면 옆 "점검 순서" 안내

1. 미리 공지 (공지 화면 바로 가기, 예: 30분 전)
2. 점검 예약 (시작 시각·안내 문구·끝 안내 시각 → 켜기) → 플레이어 화면에 큰 안내
3. 시각이 되면 판 강제 종료 (자동, Node마다 결과 보임)
4. 진행 판 0개 확인 (열린 방·판 숫자 보여 줌)
5. 배포
6. 확인 (관리자 화면·게임 접속)
7. 점검 끄기
8. 끝 공지

- 화면은 지금 단계를 숫자로 보여 줌(예약 전 / 예약됨 / 점검 중·판 n개 남음 / 판 0개)

## 9. Node 여러 개일 때

- 관리자 요청은 nginx가 아무 Node로 보냄(`least_conn`) → 어느 Node로 와도 같게

| 일 | 어떻게 | 다시 쓰는 것 |
|---|---|---|
| 로그인 잠금·세션 | DB 표로 | `admin_login_attempts` · `admin_sessions` |
| 요청 수 제한 | 기존 제한기(Redis 카운터) | `rateLimit.middleware.js` |
| 정지·강제 종료 | 기존 즉시 끊기 → 전 Node 소켓, 못 물은 Node 있으면 `partial` | `services/ops/disconnect.js` |
| 접속 중 표시 | `online_presence` 줄 + 그 Node 살아 있음 | 공지 서비스와 같은 판단 |
| 점검·금지어 반영 | DB 고침 → **새 `reloadEverywhere(what)`** = `cluster.rpc.callAll('ops.reloadNow', {what})` → Node마다 `{node, ok, code?}` → 화면 "n2 반영 안 됨". 못 받은 Node는 기존 60초 안전망 | `services/ops/reloadSync.js`(함수 하나·RPC 처리기 하나 더함) |
| 점검 강제 종료·큰 안내 | Node마다 자기 시계·자기 접속자 (8장) | 기존 버스·안전망 |

| 문의 답 알림 | 알림 저장 + `emitToUser`(사용자 채널은 어댑터로 전 Node) | `services/notification` |
| 운영 현황·열린 방 | 기존 `getClusterLiveSummary`(RPC 합침, `partial`) | `services/ops/live.js` |
| 통계 최고 접속 | `concurrent_snapshots`를 분마다 Node 합 → 날마다 최고 | 0030 `server_id` |
| Access 공개키 · 조회 줄 | Node마다 따로 | — |

- 단일 모드(`REDIS_URL` 없음): `callAll`이 나만 → 그대로 맞음

## 10. 관리자 조회 부담 (짧게)

- 관리자는 많아야 둘 → 큰 장치 없이 **게임보다 뒤로**만
- 관리자 조회는 Node마다 한 번에 하나씩 줄 세움(`admin/services/core/queryQueue.js`, 기다림 10초 넘으면 `503 ADMIN_BUSY`)
- 조회마다 `/*+ MAX_EXECUTION_TIME(3000) */`(통계는 5000), 넘으면 끊고 `503 ADMIN_QUERY_TIMEOUT` "잠시 뒤 다시"
- 목록은 한 번에 50줄, 커서(`before=<마지막 id>`), OFFSET 안 씀
- 인덱스: 기존 것으로 됨(아래). 새 인덱스는 이력 거르기용 하나(`admin_audit_logs (action, created_at)`)뿐
  - 닉네임 앞부분·이메일·UUID → 기존 유일 인덱스 / 가입·판·주문 기간 → 0025 / 신고·문의 상태 → 0024·0032 / 회원별 판 → `game_result_players.user_id`
- 안 하는 것: 관리자 전용 연결, 숫자 저장해 두기, 통계 따로 표, 따로 부하 재기

| 서버 단위·통합 | 시험 안에서 `crypto.generateKeyPairSync('rsa')` → 공개키 묶음(JWK)을 `tests/helpers/fetchablePort.js`로 연 작은 HTTP 서버가 줌 → `ADMIN_ACCESS_CERTS_URL` → 같은 비밀키로 서명한 표를 `Cf-Access-Jwt-Assertion`에. 틀린 키·aud·만료 표도 같은 방법 |
| Access와 상관없는 영역 시험 | 도우미 `tests/admin/helpers/adminTestApp.js`가 `ADMIN_ACCESS_MODE=off` + 로그인 세션을 만들어 줌 |
| 브라우저(e2e) | `e2e/scripts/serve-front.js admin`이 관리자 빌드를 5275에서 주며 `/admin-api`를 4100으로 넘김. 브라우저에 쿠키 `e2e_access_email`이 있을 때만 그 이메일로 서명한 표를 머리글에 붙임(= 클라우드플레어 흉내). 공개키는 같은 서버 `/__e2e/access-certs` → 백엔드 `ADMIN_ACCESS_CERTS_URL`. 쿠키 없으면 403 화면 |
| 운영 | 시험용 값은 `NODE_ENV=production`에서 무시 → 진짜 팀 공개키만 |

## 12. 화면 방향

- 게임 꾸밈(가면·양피지) 안 씀 → 읽기 쉬운 업무 화면: 시스템 글꼴, 흰 바탕·회색 줄, 강조색 하나, 위험한 버튼(정지·영구 정지·강제 종료·환불·뺏기·점검 켜기)만 빨강
- PC: 왼쪽 메뉴 + 표 / 휴대폰(768px 아래): 위 막대 + 메뉴 서랍, 표는 카드, 누르는 곳 44px 이상
- 큰일은 확인 창에서 한 번 더(대상·금액·기간·사유를 다시 보여 줌), 사유 칸 비면 버튼 꺼짐
- 상태 셋 늘 보임: 불러오는 중 · 빈 목록 · 오류(코드별 쉬운 문구)
- 플레이어 점검 큰 안내는 게임 화면 꾸밈에 맞춤(데스크톱·모바일 각각)
- 만들 때 ui-check 스킬 "점검"대로

## 14. 코드 규칙 (이 작업에 맞춘 것)

| 규칙 | 내용 |
|---|---|
| 크기 | 파일 300줄 · 함수 50줄 · 파일 하나에 책임 최대 2개 |
| 사다리 | 새로 쓰기 전에: 이미 있는 코드(끊기·공지·다시 읽기·live·장부·알림·제한기·bcrypt·판 끝내기) → Node 기본 → 설치된 것 → 그래도 안 되면 묻기(설치는 사용자 확인 뒤) |
| 합치기 | 있는 기능이면 합치고 없는 것만 더함(2장). 기존 서비스 겉모양은 안 바꾸고 칸·함수만 더함 |
| 층 | 경로 → 컨트롤러(모양 검사 한 번) → 서비스. 그냥 넘기기만 하는 층 없음, 저장소 층 따로 안 둠(기존 ops처럼 모델 바로) |
| 실패 모양 하나 | 서비스는 `createError(문구, 상태, code)`로 던짐 → 관리자 오류 처리기가 `{ ok:false, code, message }` |
| 돈 | 장부 함수만, 지갑 직접 고치기 금지, 잠근 채 바깥 API 금지 |
| 기록 | 쓰기 서비스는 기록 도우미를 같은 트랜잭션으로. 빠지면 AD-300이 잡음 |
| 시간 | 서버 UTC, 화면만 한국 시각 |
| 주석 | 사용자 말투: 파일 머리 2줄, 개조식 명사형(~함/~음/~기), 이유만, 쉬운 우리말, 엮인 줄엔 출력값 예시 |
| 이름 | 사용자 말로(13장), `data`·`result`·`temp` 금지 |
| 깊이 | `check:depth` 6칸 안 |
