# 배포 설정 쓰는 법

- 구성: 서버 1대(네이버 클라우드) · 백엔드 Node 1개 이상(기본 코어 수, 7장) + Redis · 도메인 3개(데스크톱 `example.com`, 모바일 `m.example.com`, API `api.example.com`) + `www`는 앞 없는 주소로
- 길: 사용자 → 클라우드플레어(맨 앞, 기본) → nginx → Node(여럿, `?node=`로 고름) → MySQL·Redis (6장·7장)
- 근거 목록: `reports/전수조사_2026-11-09/deploy/배포_위험_목록.md` (DP-번호)

## 2. 왜 이렇게

- **nginx 한 이미지에 두 화면**(DP-003): 모바일 빌드가 데스크톱 `src`·`public`을 같이 읽어서 어차피 같은 빌드 자리가 필요함. 컨테이너·설정·포트가 하나라 단순하고, 모바일 이미지엔 화면 파일만 넣고 public 그림(약 300MB)은 데스크톱 폴더 것을 nginx가 같이 씀 → 그림 한 벌
- **API도 같은 nginx**: 서버 1대라 80·443을 잡는 건 하나뿐이어야 함. 백엔드는 `expose`만(바깥에 안 열림)
- **HTTPS는 조각 파일로**: 인증서 없는 로컬에서도 같은 `default.conf`로 켜지게. `include /etc/nginx/tls/*.conf`는 파일이 없으면 아무것도 안 함
- **env_file 통째로**(DP-004): 키를 하나씩 고르면 새 키(토스 `TOSS_LIVE_*`, `FRONTEND_MOBILE_URL` 등)가 또 빠짐. `required: false`라 파일 없어도 compose가 안 깨짐(compose 2.24 이상). `environment`엔 컨테이너 안에서 늘 같아야 하는 `NODE_ENV`(기본 production)·`PORT=4000`·`LOG_DIR`만
- **폰이면 `m.`으로 302**(DP-033·021): 같은 경로·쿼리 그대로 → 비번 재설정 메일 링크(`PASSWORD_RESET_APP_URL`=데스크톱 주소)도 폰에선 모바일 `/password-reset?token=…`으로. 모바일에도 데스크톱과 같은 경로가 다 있음. 태블릿(안드로이드 Mobile 없음·iPad)은 데스크톱 그대로

## 3. 로컬에서 docker로 보기

1. 루트 `.env`에 `MYSQL_*`·`DATABASE_URL`(호스트 `db`)·`JWT_SECRET`, 그리고 `FRONTEND_URL=http://localhost:8080`, `FRONTEND_MOBILE_URL=http://m.localhost:8080`, 로그인까지 보려면 `NODE_ENV=development`(production이면 쿠키가 Secure라 http에서 로그인 안 됨)
2. `docker compose up -d --build`
3. 데스크톱 `http://localhost:8080`, 모바일 `http://m.localhost:8080`, API `http://api.localhost:8080` (`VITE_API_BASE_URL` 기본값이 이 주소)
- DB는 `127.0.0.1:3306`으로만 열림 → 개발 PC에서 `localhost:3306` 접속은 그대로, 바깥 IP로는 안 됨(DP-016)

## 4. 운영 처음 올리기

1. **도메인 자리 바꾸기**: `nginx/default.conf`·`nginx/tls/ssl.conf`의 `example.com` 전부 실제 도메인으로
2. **DNS**: 클라우드플레어에 도메인 넣고 `도메인`·`www`·`m`·`api` 네 개 다 서버 공인 IP로(A 레코드, 주황 구름). 네이버 클라우드 ACG는 22(관리자 IP만)·80·443(클라우드플레어 IP만) → 6장
3. **인증서**: 클라우드플레어 Origin CA(권장, 6-2) 또는 Let's Encrypt. Let's Encrypt면 compose 켜기 전, 80 포트 비어 있을 때: `sudo certbot certonly --standalone -d example.com -d www.example.com -d m.example.com -d api.example.com` 그리고 `sudo mkdir -p /var/www/certbot` (ACG를 클라우드플레어 IP만으로 잠근 뒤엔 클라우드플레어를 거쳐 확인받음)
4. **`.env.production`** (compose 파일 옆):
   - `backend/.env.example`의 키 전부 채우기 — `NODE_ENV=production`, `FRONTEND_URL=https://example.com`, `FRONTEND_MOBILE_URL=https://m.example.com`(없으면 소켓 Origin 검사가 모바일을 거절), 구글·디스코드 콜백은 `https://api.example.com/auth/...`, 메일·`SIGNUP_EMAIL_HMAC_SECRET`·토스(`TOSS_LIVE_*`·`TOSS_TEST_*`)·`INTERNAL_API_KEY`·`LOG_RETENTION_DAYS`
   - `DATABASE_URL`은 호스트 `db`, `MYSQL_DATABASE`·`MYSQL_USER`·`MYSQL_PASSWORD`·`MYSQL_ROOT_PASSWORD`
   - `VITE_API_BASE_URL=https://api.example.com` (경로 없이, DP-009), 필요하면 `VITE_DISCORD_SUPPORT_URL`, 모바일 광고 `VITE_AD_PROVIDER`·`VITE_ADSENSE_*`
   - `GAME_DEV_MIN_PLAYERS`는 넣지 않기. 값에 `$`가 있으면 `$$`로 (compose가 `$`를 변수로 읽음)
5. **켜기**: `docker compose -f docker-compose.yml -f docker-compose.prod.yml --env-file .env.production up -d --build`
   - `--env-file`이 있어야 `VITE_*`(빌드 값)·`MYSQL_*`(db)가 같은 파일에서 들어감
   - 백엔드는 `migrate` 성공해야 서버를 켬 → `docker compose logs backend`에서 `[STARTUP] 성공` 확인
6. **확인**: 폰으로 `https://example.com/password-reset?token=x` 열면 `m.`으로 가는지, 소켓이 `101`인지, `/assets/` 응답에 `immutable`인지

## 5. 다시 배포 · 인증서 갱신

- 다시 배포: 4-5 명령 그대로. 판 없는 시간에(판이 메모리에 있어 백엔드 재시작 때 사라짐). `VITE_*`를 바꾸면 꼭 `--build`(빌드 때 박힘)
- 인증서 갱신(cron 하루 한 번): `certbot renew --webroot -w /var/www/certbot --deploy-hook "cd <저장소 폴더> && docker compose -f docker-compose.yml -f docker-compose.prod.yml exec -T frontend nginx -s reload"` → nginx를 안 끄고 갱신(소켓 안 끊김)
- 화면 새 버전 안내: 이미지 안엔 `.git`이 없어 버전이 `nogit-빌드시각` → 빌드마다 달라져 안내는 그대로 됨
- 로그인 앞단 제한: nginx가 `/auth/login`을 IP당 1분 10번(+5번 여유)으로, 넘치면 429 (클라우드플레어 뒤에서도 진짜 사용자 IP 기준, 6-5)
- 관리자 통로(`/internal`, 대소문자 안 가림): API 사이트에서 허용 ip만 통과, 기본은 전부 403 → 관리자 서버 공인 ip를 `nginx/snippets/internal-allow.conf`의 `deny all;` 위에 `allow <ip>;`로 넣고 `--build` (설정 확인: 저장소 루트에서 `docker run --rm --add-host backend:127.0.0.1 -v "$PWD/nginx/default.conf:/etc/nginx/conf.d/default.conf:ro" -v "$PWD/nginx/snippets:/etc/nginx/snippets:ro" nginx:1.27-alpine nginx -t`). 클라우드플레어를 거쳐도 진짜 IP로 검사함(6-5), 부르는 길은 서버 안 권장(6-7)

## 6. 클라우드플레어 (맨 앞, 기본)

- 길: 사용자 → 클라우드플레어(프록시, 주황 구름) → nginx → Node → MySQL
- 붙이는 까닭: 정적 파일을 클라우드플레어가 대신 내줘 원본 트래픽 요금이 줄고(무료 요금제는 전송량 요금 없음), 디도스(DDoS, 몰려드는 공격) 막기·원본 IP 숨기기가 같이 됨
- 서버 쪽은 저장소에 다 들어 있음. 사람이 할 일은 대시보드 설정(6-1~6-4)과 네이버 ACG(6-4)

### 6-1. DNS · SSL 모드

- DNS: `example.com`·`www`·`m`·`api` 네 개 A 레코드 → 서버 공인 IP, **주황 구름(Proxied)**. 회색이면 클라우드플레어를 안 거침
- SSL/TLS → Overview → **Full (strict)**
  - Flexible 금지: 원본에 http로 감 → `ssl.conf`가 https로 돌려보내 무한 반복, `$scheme`이 http라 HSTS·302 주소도 틀어짐
  - Full(strict 아님)은 원본 인증서를 안 따져 중간 가로채기 가능 → strict로
- SSL/TLS → Edge Certificates → **Always Use HTTPS 켬**, Minimum TLS 1.2
- Network → **WebSockets 켬**(기본 켜짐). 소켓이 이 길로 감

### 6-2. 원본 인증서 (nginx/tls)

- 둘 중 하나, `nginx/tls/ssl.conf`에 두 가지 줄이 다 적혀 있음
- **① Cloudflare Origin CA (권장)**: 클라우드플레어만 믿는 원본 인증서, 15년·갱신 없음 → ACG로 원본을 잠가도 갱신 걱정 없음
  1. SSL/TLS → Origin Server → Create Certificate → 이름 `example.com`, `*.example.com`, RSA, 15년
  2. 나온 인증서·개인 키를 서버 `<배포 폴더>/nginx/tls/origin.pem`·`origin.key`로 저장(`chmod 600 origin.key`). git엔 안 올라감(`nginx/tls/.gitignore`), 배포 때 `nginx/`를 풀어도 안 지워짐
  3. `ssl.conf`에서 ① Let's Encrypt 두 줄 지우고 ② 두 줄 켜기 → 커밋 → 배포
  - 원본 IP로 브라우저가 바로 가면 인증서 경고 → 정상(클라우드플레어 거치는 길만 씀)
- **② Let's Encrypt**: 4장 3번대로, 90일마다 갱신(5장 cron). 클라우드플레어를 거쳐도 확인 파일(`/.well-known/acme-challenge/`)은 nginx가 그대로 줌
- HSTS(브라우저가 https만 쓰게 하는 머리말)와 Always Use HTTPS가 같이 도는 법
  - Always Use HTTPS: 클라우드플레어가 http 요청을 https로 301 → 원본은 사용자 http 요청을 거의 안 받음
  - HSTS: nginx가 https 응답에 1년(`includeSubDomains`) 붙임(`snippets/security-headers.conf`). Full (strict)라 원본까지 https → `$scheme`이 https라 붙고, 클라우드플레어가 그대로 넘김
  - 대시보드 HSTS는 켜지 않기(머리말 두 번). preload는 도메인 굳힌 뒤 몇 달 지나서
  - 순서: 첫 방문 http → 클라우드플레어 301 → https 응답에 HSTS → 다음부터 브라우저가 바로 https

### 6-3. 캐시

- 원본(nginx)이 이미 나눠 둠

| 응답 | 원본 Cache-Control | 클라우드플레어 |
| --- | --- | --- |
| `/assets/*` (이름에 해시) | `public, max-age=31536000, immutable` | 저장 |
| 그림·영상·소리(png·webp·mp4·ogg 등) | `public, max-age=604800` (7일) | 저장 |
| `index.html`·화면 주소(`/lobby` 등) | `private, no-cache` + `Vary: User-Agent` | 저장 안 함 |
| `version.json` | `no-store` | 저장 안 함 |
| 폰 → `m.` 302 | `no-store` + `Vary: User-Agent` | 저장 안 함 |
| API·socket.io | 백엔드 응답 그대로 | 아래 규칙 1로 저장 안 함 |

- 폰 302가 저장되면 PC도 `m.`으로 가 버림 → 302엔 `no-store`가 꼭 있어야 함. 클라우드플레어는 `Vary: User-Agent`로 따로 저장해 주지 않음 → 막는 건 `no-store`/`private`, `Vary`는 브라우저·다른 중간 캐시용
- **Cache Everything·"HTML도 캐시" 규칙 금지** (302·HTML이 섞여 저장됨)
- 대시보드 Caching → Cache Rules (세 개, 이 순서)
  1. `API 저장 안 함`: `(http.host eq "api.example.com")` → **Bypass cache**
  2. `화면 정적 파일 저장`: `(http.host in {"example.com" "m.example.com"} and (starts_with(http.request.uri.path, "/assets/") or http.request.uri.path.extension in {"png" "jpg" "jpeg" "webp" "gif" "svg" "ico" "mp4" "webm" "ogg" "mp3" "wav"}))` → **Eligible for cache**, Edge TTL **Use cache-control header if present**, Browser TTL **Respect origin**
  3. `화면 나머지 저장 안 함`: `(http.host in {"example.com" "m.example.com"} and not starts_with(http.request.uri.path, "/assets/") and not http.request.uri.path.extension in {"png" "jpg" "jpeg" "webp" "gif" "svg" "ico" "mp4" "webm" "ogg" "mp3" "wav"})` → **Bypass cache**
- Caching → Tiered Cache → **Smart Tiered Cache 켬**(무료): 거점끼리 먼저 나눠 받아 원본까지 오는 요청 줄음
- 배포 뒤: `/assets/`는 이름이 바뀌어 비울 일 없음. 그림·영상을 **같은 이름으로** 바꿨으면 Caching → Purge Cache → Custom Purge로 그 주소만 비우기

### 6-4. 원본 보호 · WAF와 봇

- **네이버 클라우드 ACG** (Server → ACG → 서버에 붙은 ACG → Inbound)
  - 22: 관리자 PC·CI 러너 IP만
  - 80·443: `nginx/snippets/cloudflare-realip.conf`의 범위 22개(IPv4 15·IPv6 7)만, `0.0.0.0/0` 줄은 지우기
  - 넣기 전 규칙 수 한도 확인. 범위를 다시 받으면(6-6) ACG도 같이 맞추기
  - 이러면 원본 IP를 알아도 클라우드플레어를 안 거치고는 못 들어옴(WAF 우회 막기)
  - nginx `allow`로 막는 조각은 안 둠: 진짜 IP 조각이 `$remote_addr`를 사용자 IP로 바꿔서 `allow 클라우드플레어 범위`는 모든 사람을 막음 → 막기는 ACG 한 곳에서
- 선택: Authenticated Origin Pulls(원본이 클라우드플레어 인증서만 받기)는 nginx `ssl_verify_client` 설정이 더 필요 → 지금은 안 함
- **WAF·봇 (무료 요금제 기본값)**
  - Security → WAF: 무료 관리 규칙(Free Managed Ruleset) 켜진 그대로
  - Security Level: 기본(Medium) 그대로
  - **Bot Fight Mode: 끔으로 시작** — API·소켓 요청에도 확인 화면을 띄울 수 있고 무료판은 예외 규칙을 못 걺 → 배포 뒤 바깥 확인(smoke)·바깥 관리자 서버 호출·부하 시험이 막힐 수 있음
  - Browser Integrity Check: 켜진 그대로. smoke가 403이면 이것부터 보기
  - Under Attack 모드: 공격 받을 때만 잠깐. 켜면 API 호출·소켓이 확인 화면에 막힘
  - 로그인 요청 제한은 nginx(IP당 1분 10번, 진짜 IP 기준)가 이미 함 → 클라우드플레어 Rate limiting 규칙은 선택

### 6-5. 진짜 사용자 IP

- 클라우드플레어를 거치면 nginx가 보는 `$remote_addr`는 클라우드플레어 서버 IP → 그대로면 로그인 제한이 많은 사람을 몇 개 IP로 묶어 같이 막고, `/internal` 허용 목록이 안 맞음
- 고친 곳
  - `nginx/snippets/cloudflare-realip.conf`: 클라우드플레어 범위에서 온 요청만 `CF-Connecting-IP`를 믿음 → `$remote_addr` = 진짜 사용자 IP. 데스크톱·모바일·API 세 사이트가 include
  - 범위 밖에서 온 요청(클라우드플레어 없이 바로·위조)은 머리말 무시, 바로 붙은 주소 그대로 → 클라우드플레어 없이도 안 깨짐
  - nginx → 백엔드 `X-Forwarded-For`는 `$remote_addr` 하나만(사람이 넣은 줄은 버림)
  - 백엔드 `trust proxy` = `TRUST_PROXY_HOPS`(1, nginx 하나) → `req.ip` = 그 값. 백엔드는 `expose`만이라 nginx 말고는 못 붙음
  - 소켓: `socket.handshake.address`는 nginx 컨테이너 IP → `utils/request.js`의 `getSocketClientIp`가 `req.ip`와 같은 규칙으로 읽어 `socket.data.clientIp`에 둠(`socket/socket.js`, 인증 앞)
  - 로그: nginx 접속 로그 맨 앞(`$remote_addr`), 백엔드 요청 로그 맨 앞(`:client-ip`) 둘 다 진짜 IP
- 확인 결과 (2026-11-09, `bash deploy/scripts/cloudflare-ip-check/run.sh`, CI `docker-build.sh`에도 넣음)

| 경우 | 결과 |
| --- | --- |
| 클라우드플레어 아닌 IP가 `CF-Connecting-IP: 203.0.113.7`·`X-Forwarded-For: 6.6.6.6` 위조 | 백엔드 `req.ip`·소켓 IP·nginx 로그 전부 바로 붙은 주소, 백엔드가 받은 `X-Forwarded-For`도 그 주소 하나, `/internal` 403 |
| 클라우드플레어 서버에서 옴 (시험 망을 믿을 범위에 더해 흉내) | `req.ip`·소켓 IP·nginx 로그·백엔드 요청 로그·소켓 로그 전부 `203.0.113.7`, IPv6 `2001:db8::7`도 그대로 |
| `/internal` 허용 목록 `allow 203.0.113.7` | 그 IP는 200, 다른 IP 403 |
| 로그인 한 사람 20번 | 7번째부터 429, 다른 사람은 200 (사람마다 따로 셈) |
| 폰 UA `/lobby?x=1` | 302 `m.` 같은 경로·쿼리, `no-store`·`Vary: User-Agent`, 보안 머리말 그대로 · PC는 200 `private, no-cache` |

- 단위 시험: `backend/tests/utils/clientIp.cloudflare.test.js` (Express `req.ip`와 소켓 IP가 같은 규칙인지, 진짜 socket.io 손잡기)

### 6-6. IP 범위 갱신

- 클라우드플레어 범위는 드물게 바뀜 → 배포 전·석 달에 한 번
- `bash deploy/scripts/update-cloudflare-ips.sh` → `nginx/snippets/cloudflare-realip.conf` 다시 씀(받은 날짜 주석) → `git diff`로 보고 커밋
- 이 조각은 화면 이미지 안에 들어감 → **이미지 다시 빌드·배포**해야 반영. ACG 80·443 목록도 같이
- 안 맞추면: 새 범위로 들어온 사람이 클라우드플레어 IP로 보여 로그인 제한을 같이 맞음(ACG를 안 맞추면 아예 못 들어옴)

### 6-7. 관리자 통로 (`/internal`, `npm run admin`)

- 권장: **서버 안에서 부르기** `docker compose -f docker-compose.yml -f docker-compose.prod.yml exec backend npm run admin -- check` (`ADMIN_CALL_BASE_URL` 비움 → `http://localhost:4000`). nginx·클라우드플레어를 안 거쳐 허용 목록·봇 확인과 상관없음. 배포 스크립트(`remote.sh`)도 이 길
- 관리자 서버가 같은 docker 망이면 `ADMIN_CALL_BASE_URL=http://backend:4000`
- 바깥 관리자 서버에서 꼭 불러야 하면 `https://api.도메인` + `internal-allow.conf`에 그 서버 공인 IP. 클라우드플레어를 거쳐도 진짜 IP로 검사함. Bot Fight Mode를 켜면 막힐 수 있음
- 원본 IP로 바로 부르기는 ACG(80·443 클라우드플레어만)에 막힘 → 안 씀

### 6-8. 소켓 · 유휴 시간

- 클라우드플레어는 오가는 것 없는 웹소켓을 약 100초 뒤 끊음
- socket.io 서버 ping 기본값 그대로(`backend/socket/socket.js`에 `pingInterval`·`pingTimeout` 안 넣음) → 25초마다 ping, 20초 안에 답 없으면 끊음 → 100초에 안 걸림
- nginx `/socket.io/` `proxy_read_timeout`·`proxy_send_timeout` 120초 > 25초 → 안 걸림
- 클라우드플레어 거점 정비 때 웹소켓이 끊길 수 있음 → 화면은 socket.io 자동 다시 접속 기본값 그대로(`frontend/src/shared/socket/connection.js`)
- 소켓·API는 캐시 안 됨 → 그 트래픽은 원본 요금에 그대로 들어감

### 6-9. 확인 방법 (배포 뒤)

```bash
# 클라우드플레어 거침: server: cloudflare, cf-ray 끝 세 글자 = 응답한 거점(ICN 인천·NRT 도쿄 등)
curl -sI https://example.com/ | grep -iE '^(server|cf-ray|cf-cache-status|cache-control)'
# 정적 파일: 두 번째부터 cf-cache-status: HIT
curl -sI https://example.com/assets/<파일 이름>.js | grep -i cf-cache-status
# HTML·API: DYNAMIC 또는 BYPASS (HIT면 규칙 잘못)
curl -sI https://example.com/lobby | grep -iE 'cf-cache-status|cache-control'
curl -sI https://api.example.com/health | grep -i cf-cache-status
# 폰 302: no-store, 몇 번 불러도 HIT 안 나옴 / PC는 200
curl -sI -A "Mozilla/5.0 (Linux; Android 14; Pixel 7) Mobile" https://example.com/lobby | grep -iE '^(location|cache-control|cf-cache-status)'
curl -sI -A "Mozilla/5.0 (Windows NT 10.0)" https://example.com/lobby | head -1
# 원본 바로 막힘 (ACG): 시간 초과면 정상
curl -sk --max-time 5 -o /dev/null -w '%{http_code}\n' -H 'Host: example.com' https://<서버 공인 IP>/
```

- 진짜 IP: 내 공인 IP를 알아 둔 뒤 사이트 한 번 열고 서버에서
  - `docker compose ... logs --tail 20 frontend` → 줄 맨 앞이 내 IP
  - `docker compose ... logs --tail 20 backend` → 요청 로그 맨 앞이 내 IP
- 배포 바깥 확인(`deploy/ci/scripts/deploy/smoke.sh`): 폰 302 `no-store`는 늘 봄, `SMOKE_EXPECT_CLOUDFLARE=1`이면 `cf-ray`도 봄
- 한국 응답 거점: 무료 요금제는 통신사 사정으로 일본 등 해외 거점에서 응답하는 일이 잦다고 알려짐 → `cf-ray` 끝 글자로 보고, 첫 화면·소켓 지연을 배포 전 실제로 재기(느리면 요금제·구성 다시 판단)

## 7. Node 여러 개

- 한 기계에서 백엔드를 여러 프로세스(Node)로 띄워 코어를 다 씀. Node끼리는 Redis로 신호·위치를 나눔
- 계획·약속: `docs/노드_여러개_계획_2026-11-09.md` (8장 운영), 서버 쪽 API: `backend/cluster/README.md`
- 규칙 하나: **방·판은 만든 Node에서 돎**. 다른 Node 방에 들어갈 때 화면이 `?node=<SERVER_ID>`를 붙여 그 Node로 다시 붙고, nginx가 `$arg_node`로 그 Node를 고름
- 화면을 먼저 배포해야 함 (옛 화면은 `WRONG_NODE` 뒤 다시 안 붙음)

### 7-1. 띄우기 (docker)

| 무엇 | 값 |
| --- | --- |
| Node 이름(`SERVER_ID`) | n1, n2, … (다시 만들어도 같음, 컨테이너 이름 안 씀). n1 = `backend` 서비스, n2.. = `backend-n2`.. |
| Node 수 | `.env.production`의 `NODE_COUNT` (비면 코어 수). 서버 코드는 안 읽고 생성기·배포만 읽음 |
| nginx | `proxy_pass http://$mmc_upstream;` — `?node=n2`면 n2 먼저(죽었으면 다른 Node가 backup), 없거나 모르는 값이면 덜 바쁜 Node(`least_conn`) |
| 컨테이너가 꺼져 있어도 | upstream `server … resolve` + docker DNS(127.0.0.11)라 nginx가 켜지고, 다시 만든 컨테이너 IP도 따라감 (nginx 1.27.3 이상) |

손으로 켜기 (운영 서버, 저장소 폴더에서):

```bash
NODE_COUNT=4 node deploy/scripts/gen-nodes.js            # nginx/snippets/mmc-upstreams.conf · docker-compose.nodes.yml
docker compose -f docker-compose.yml -f docker-compose.prod.yml -f docker-compose.nodes.yml --env-file .env.production up -d --build
docker compose ... exec -T frontend nginx -s reload       # 조각 폴더가 붙어 있어 다시 읽기만
```

- 레지스트리 이미지로 켤 땐 `--registry`를 붙여 만듦 (backend-n2..도 같은 이미지 이름·태그). 배포 스크립트는 늘 이렇게 함
- 로컬에서 해 볼 땐 저장소 파일이 바뀜 → 끝나면 `node deploy/scripts/gen-nodes.js --count 1`로 되돌리기 (커밋하지 말 것)
- 설정 확인: `bash deploy/scripts/nginx-nodes-check.sh 4` (진짜 `default.conf` + Node 4개 upstream으로 `nginx -t`)
- 클라우드플레어 진짜 IP 규칙은 그대로: `cloudflare-realip.conf` include, 백엔드로는 `X-Forwarded-For $remote_addr` 하나, 백엔드 trust proxy 1 (upstream으로 바꾼 뒤에도 `deploy/scripts/cloudflare-ip-check/run.sh` 통과)

docker 없이 pm2:

- `backend/.env`(또는 셸)에 `REDIS_URL`이 있어야 여러 개로 띄움. 없으면 예전처럼 `mmc-backend` 하나
- 여러 개면 `mmc-backend-n1`.. · 포트 4001.. · `SERVER_ID` n1.. (fork, cluster 모드 안 씀: 포트를 같이 쓰면 nginx가 Node를 못 고름)
- nginx upstream: `node deploy/scripts/gen-nodes.js --target pm2 --count 4` → `127.0.0.1:4001..` (resolve 없음)
- 로그 파일은 `logs/app-<SERVER_ID>-날짜.log`로 Node마다 따로

### 7-2. Redis

- compose `redis` 서비스 (`redis:7.4-alpine`): 디스크에 안 남김, 최대 256MB, 수명 있는 키부터 뺌, 포트는 밖으로 안 엶
- 비번: `.env.production`의 `REDIS_PASSWORD` **꼭 넣기** (없으면 `docker-compose.prod.yml`이 멈춤). URL(`redis://:비번@redis:6379`)에 들어가서 **영문·숫자만**, 32자 이상 권장 (예: `openssl rand -hex 24`)
- 로컬은 비우면 로컬 전용 기본값으로 켜짐 (운영에 쓰면 안 됨)
- Redis가 죽으면: 판은 그대로 돎, 세션·정지 캐시를 끄고 DB로 감, 다른 Node 방 입장만 "잠시 후". 살아나면 각 Node가 스스로 다시 맞춤 (`/health`의 `redis`: up·down·off)
- 키 앞머리 `REDIS_KEY_PREFIX`(기본 `mmc`): 한 Redis를 여러 환경이 같이 쓸 때만 바꿈

### 7-3. Node 하나씩 바꾸기 (배포)

`deploy/ci/scripts/deploy/remote.sh deploy <태그>`가 Node 2개 이상이면 자동으로 이 순서 (`DEPLOY_ROLLING=auto`):

| 순서 | 할 것 |
| --- | --- |
| 0 | 이미지 pull → `gen-nodes.js --registry`로 생성 파일 다시 만들기 → DB 백업 → migrate(`compose run` 한 번) |
| 1 | n1: `POST /internal/nodes/n1/drain` → n1이 새 로비 접속·방 만들기를 다른 Node로 보냄 (판·방은 계속) |
| 2 | `/internal/cluster`에서 n1 판+방 0개까지 기다림 (최대 `DRAIN_MAX_MINUTES`, 기본 40분. 넘으면 멈춤 → 그 Node만 점검 안내 뒤 `DRAIN_FORCE=1`) |
| 3 | n1을 새 이미지로 다시 만들기(SIGTERM → 그 Node 사람에게만 점검 안내) → `/health` ok + redis down 아님 |
| 4 | 새로 켠 Node는 드레인이 꺼진 채 시작 → n2..로 반복 |
| 5 | `NODE_COUNT`를 줄였으면 빠진 Node도 드레인 → 끔. 마지막에 화면(nginx) 새 이미지 + upstream 다시 읽기 |

- 점검 모드는 안 켬. **마이그레이션은 앞뒤 버전이 같이 돌 수 있는 것만**(넓히기 → 다음 배포에 좁히기)
- 깨지는 마이그레이션 · 처음 Node 여러 개로 바꾸는 배포(옛 버전엔 드레인 통로가 없음): `DEPLOY_ROLLING=0` → 예전 순서(점검 켜기 → 전체 판 0개 → 한 번에 바꾸기)
- 되돌리기(`remote.sh rollback`)도 같은 순서. 크게 망가지면 `.env.production`에 `NODE_COUNT=1`, `docker-compose.yml` backend의 `REDIS_URL` 줄 빼고 `DEPLOY_ROLLING=0`으로 배포 → 예전 단일 Node
- 배포 뒤 확인: `SMOKE_EXPECT_NODES=4 bash deploy/ci/scripts/deploy/smoke.sh` → Node마다 `/health?node=nX`가 그 Node에서 답하는지·redis up·소켓 101

### 7-4. NODE_COUNT · DB_POOL_MAX · MySQL max_connections 맞추기

- DB 연결은 Node마다 풀이 따로 → **합 = NODE_COUNT × DB_POOL_MAX**. 여기에 migrate·관리자 스크립트·백업 몇 개가 더 붙음
- 규칙: 합이 MySQL `max_connections`의 80% 이하 (서버가 켤 때 넘으면 `[STARTUP] 경고` 한 줄, 한도는 `DB_MAX_CONNECTIONS`로 알려 줌, 기본 151)
- 확인: `docker compose ... exec -T db sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "SHOW VARIABLES LIKE \"max_connections\"; SHOW STATUS LIKE \"Max_used_connections\""'`

| 코어(Node 수) | DB_POOL_MAX | 합 | max_connections 151(80% = 120)이면 |
| --- | --- | --- | --- |
| 2 | 10(기본) | 20 | 그대로 |
| 4 | 10 | 40 | 그대로 |
| 8 | 10 | 80 | 그대로 |
| 12 | 10 | 120 | 딱 한도 → DB_POOL_MAX=8(96) 권장 |
| 16 | 7 | 112 | DB_POOL_MAX를 7로 줄이거나 max_connections를 늘림 |

- max_connections를 늘리려면 db 서비스에 `command: ["--max-connections=300"]`을 붙이고 `DB_MAX_CONNECTIONS=300`도 같이 (연결 하나에 메모리 몇 MB → 서버 메모리 보고 정하기)
- 같은 기계에서 MySQL·nginx·Redis도 CPU를 씀 → 코어가 4개 이하면 `NODE_COUNT`를 코어 수 - 1로 두는 것도 생각하기

| 보안 머리글 | `nginx/snippets/admin-security-headers.conf` — CSP `default-src 'self'`·`frame-ancestors 'none'`, `X-Robots-Tag noindex`, `Referrer-Policy no-referrer` |
| 화면 이미지 | `frontend/Dockerfile`: 플레이어 빌드 뒤 `npm run build:admin`(끝에 섞임 검사) → `/usr/share/nginx/html/admin`. 플레이어 `desktop`·`mobile` 폴더엔 `admin.html` 없음 |
| 확인 | CI `docker-build.sh`가 `admin-site-check.sh`와 이미지 폴더 검사까지 돎. 손으로는 `bash deploy/ci/scripts/admin-site-check.sh` |
| 로컬 docker | `http://admin.localhost:8080` (`.env`에 `ADMIN_ACCESS_MODE=off`·`ADMIN_TOTP_KEY`·`ADMIN_ORIGIN=http://admin.localhost:8080`, `NODE_ENV=development`) |

### 8-2. 처음 올리기 순서

1. **도메인 자리**: `nginx/default.conf` admin 사이트의 `admin.example.com`도 실제 도메인으로 (4장 1번과 같이)
2. **DNS**: 클라우드플레어에 `admin` A 레코드 → 서버 공인 IP, **주황 구름(Proxied)**. 회색이면 Access를 안 거침
3. **인증서**
   - Origin CA(6-2 ①, 권장): `*.<도메인>`이라 그대로 됨
   - Let's Encrypt(6-2 ②): 받을 때 `-d admin.<도메인>` 더함. Access가 확인 파일까지 막으므로 아래 4-6번(확인 파일만 통과)을 꼭
4. **클라우드플레어 Access** (대시보드 순서, 8-3)
5. **`.env.production`** 에 아래 값 (이름 설명은 루트 `.env.example` 맨 아래)

| 이름 | 넣을 값 |
| --- | --- |
| `ADMIN_ORIGIN` | `https://admin.<도메인>` (끝 `/` 없이) |
| `ADMIN_TOTP_KEY` | 서버에서 `openssl rand -hex 32` 결과 (16진수 64자). **한 번 정하면 안 바꿈**(바꾸면 만든 OTP를 못 풂), 따로 안전한 곳에도 적어 둠 |
| `ADMIN_ACCESS_TEAM_DOMAIN` | `<팀 이름>` (또는 `<팀 이름>.cloudflareaccess.com`) |
| `ADMIN_ACCESS_AUD` | Access 앱의 AUD 값 (8-3 5번) |
| `ADMIN_ACCESS_MODE` | 비움 (= 켬). 운영에선 `off`를 넣어도 무시됨 |
| `ADMIN_SESSION_IDLE_MIN` | 비움 (= 30분) |

   - 운영에서 팀 이름·AUD·`ADMIN_TOTP_KEY` 중 하나라도 비면 `/admin-api` 전체가 꺼짐(404) → 관리자 화면 로그인이 안 되면 이것부터
6. **배포**: 4장 5번 명령 그대로 (`--build`, 마이그레이션 `0031`·`0032`는 백엔드가 켤 때 같이 돎)
7. **관리자 계정 둘 만들기** (8-4)
8. **점검** (8-5)

### 8-3. 클라우드플레어 Access 대시보드

1. **Zero Trust 켜기**: 대시보드 왼쪽 **Zero Trust** → 처음이면 팀 이름(`<팀 이름>`) 정하기 → 요금제 **Free**(50명까지 무료, 결제 수단을 물을 수 있음) → 팀 주소 `https://<팀 이름>.cloudflareaccess.com`
2. **로그인 방법**: Zero Trust → Settings → Authentication → Login methods → **One-time PIN** 추가 (이메일로 번호 받기). 다른 로그인 방법은 안 넣음
3. **앱 만들기**: Access → Applications → **Add an application** → **Self-hosted**
   - 이름 `MMC 관리자`, Session Duration **24 hours**
   - Application domain: 하위 도메인 `admin`, 도메인 `<도메인>`, 경로 비움 (사이트 전체)
   - Identity providers: **One-time PIN만**, Instant Auth 켬
4. **정책** (같은 화면 Policies → Add a policy)
   - 이름 `관리자 둘`, Action **Allow**
   - Include → **Emails** → `<대표 이메일>`, `<CTO 이메일>` 두 개만
   - `Everyone`·이메일 도메인(`@회사.com`)·다른 Include는 넣지 않음. 사람이 바뀌면 이 목록과 관리자 계정 이메일(8-4)을 같이 바꿈
   - 이 이메일은 관리자 계정 `--email`과 글자 그대로 같아야 함 (다르면 로그인 `403 ADMIN_EMAIL_MISMATCH`)
5. **AUD 값**: 저장 뒤 Applications → `MMC 관리자` → Overview(또는 Basic information)의 **Application Audience (AUD) Tag** 복사 → `.env.production` `ADMIN_ACCESS_AUD`. 팀 이름은 `ADMIN_ACCESS_TEAM_DOMAIN`
6. **Let's Encrypt만**: 앱을 하나 더 → Self-hosted, 도메인 `admin.<도메인>`, 경로 `.well-known/acme-challenge/` → 정책 Action **Bypass**, Include **Everyone** (확인 파일만 통과, nginx도 이 경로는 파일만 줌)
7. **캐시·끼워 넣기 끄기** (관리자 화면 CSP가 바깥 스크립트를 막음)
   - Caching → Cache Rules에 `관리자 저장 안 함`: `(http.host eq "admin.<도메인>")` → **Bypass cache** (6-3 규칙 1 다음에)
   - Rules → Configuration Rules: `(http.host eq "admin.<도메인>")` → Rocket Loader 끔, Email Obfuscation 끔. Web Analytics 자동 넣기를 켰다면 admin 주소는 뺌
   - Bot Fight Mode는 6-4대로 끔 유지

### 8-4. 첫 관리자 계정 만들기 (운영 서버에서)

- 저장소 폴더에서, 대표·CTO 한 명씩. 비번은 두 번 묻고 화면에 안 보임(12자 이상)

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml exec backend \
  npm run admin:account -- create --login <관리자 아이디> --email <관리자 이메일>
```

- 끝나면 OTP 비밀과 `otpauth://` 주소를 **한 번만** 보여 줌 → 그 사람 OTP 앱(구글 OTP 등)에 바로 넣기. 화면 기록·채팅·메일로 옮기지 않기
- 비밀이 새거나 폰을 잃으면: `... npm run admin:account -- reset-otp --login <관리자 아이디>`
- 그 밖: `list`(계정 목록) · `reset-password` · `disable` · `enable` · `unlock` (모두 `--login <관리자 아이디>`)
- `.env.production`의 `ADMIN_TOTP_KEY`가 없으면 만들기가 멈춤 → 5번 먼저

### 8-5. 점검 순서 (배포 뒤)

| 순서 | 할 것 | 맞으면 |
| --- | --- | --- |
| 1 | 로그인 안 한 브라우저(시크릿 창)로 `https://admin.<도메인>` | 클라우드플레어 Access 화면(이메일 넣기) — 관리자 화면이 바로 보이면 Access 설정 잘못 |
| 2 | 목록에 없는 이메일로 번호 받기 | 번호 안 옴·통과 못 함 |
| 3 | 원본 IP로 바로: `curl -sk --max-time 5 -o /dev/null -w '%{http_code}\n' -H 'Host: admin.<도메인>' https://<서버 공인 IP>/admin-api/auth/me` | 시간 초과(ACG) — 혹시 닿아도 서버가 `403`(Access 표 없음) |
| 4 | `curl -s -o /dev/null -w '%{http_code}\n' https://api.<도메인>/admin-api/auth/me` | `404` |
| 5 | `curl -s https://<도메인>/admin.html \| grep -c admin-root` | `0` (플레이어 주소엔 관리자 화면 없음) |
| 6 | 대표 이메일로 Access 통과 → 아이디·비번·OTP 로그인 | 관리자 첫 화면. CTO도 같은 순서 |
| 7 | 응답 머리글: 브라우저 개발자 도구 → 네트워크 → `admin.html` | `content-security-policy: default-src 'self'; …`, `x-robots-tag: noindex, nofollow` |
| 8 | 가만히 30분 뒤 아무 버튼 | 다시 로그인 화면 |

- 바깥 확인(smoke): `SMOKE_ADMIN_URL=https://admin.<도메인>`을 CI 변수에 넣으면 `smoke.sh`가 봄 — `SMOKE_EXPECT_CLOUDFLARE=1`이면 Access 로그인으로 302인지, 아니면 200·`noindex`, 그리고 api 주소 `/admin-api` 404·데스크톱 `/admin.html`에 관리자 화면 없음
- 관리자 로그인 실패가 이어지면: `docker compose ... logs --tail 50 backend`에서 `ADMIN_ACCESS_*` 오류(팀·AUD 값, 공개키 못 받음 `503`) 먼저 보기
