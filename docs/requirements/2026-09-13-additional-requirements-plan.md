# Joker 추가 요구사항과 구현 계획

작성일 2026년 9월 13일   2026년 9월 14일 DB 상품 계약 보완. Word v2 이후 변경은 이 문서와 별도 DB 상품 계약을 따른다.

회원가입 이메일 인증 정책을 확정하고, 마이페이지 피의 기록을 전체 판수·승률 두 항목으로 바꾼다. 명성은 사용자 화면에서 제거한다. 토스페이먼츠 테스트 결제로 다이아만 충전하고, 다이아로 골드를 구매할 수 있게 한다. 이 문서는 이전 초안의 삭제 범위와 재화 선택 미정안을 대체한다.

### 요구사항 요약

| 관리 ID | 확정된 요구 | 기존 작업과 연결 |
| --- | --- | --- |
| ADD01 | 회원가입 시 이메일 인증 | F02 회원가입 및 F05 소셜 계정, F29 메일 복구 |
| ADD02 | 피의 기록은 전체 판수·승률만 표시하고 명성 제거 | F10 전적과 랭킹, 마이페이지 및 공통 배너 |
| ADD03 | 토스 테스트 다이아 충전 및 다이아로 골드 구매 | F08 지갑과 원장, F09 상점, F28 통합 검증 |
### 착수 방향

ADD ID는 이 문서의 관리 번호다. 2026-09-13 사용자 승인에 따라 기존 배치에 ADD02=F30/BO, ADD01=F31/BP, ADD03=F32/BQ로 등록했다. 전체 32개이며 마지막 순서는 F29 → F30 → F31 → F32 → F28이다. 추가 작업도 계획 심사와 테스트 및 Chrome 검증을 거친다. 최신 실행 기준은 [추가 요구사항 확정과 최종 검증 순서](2026-09-13-additional-execution-approved.md)를 따른다.

### 현행 코드에서 확인한 연결점

- 회원가입은 signup에서 계정과 통계 및 기본 지갑·장비 지급을 한 트랜잭션으로 처리한다. 이메일 인증 추가 후에도 이 원자성을 유지한다.
- 현재 피의 기록은 전체 판수·생존 횟수·단두대 처형 세 행이다. 이를 전체 판수·승률 두 행으로 교체한다. 별도 프로필 배너에 있는 명성도 제거한다.
- 경제 서비스에 지갑 조회와 거래 원장 기반 지급 경로가 존재한다. 충전은 별도 잔액 체계 대신 기존 지갑·원장의 트랜잭션 계약에 연결한다.
### 공통 완료 기준

기능별 인수 조건, 서버 상태 전이, 영향 파일, 실패 복구 시험을 먼저 확정한다. 구현 후 관련 테스트 → 승인된 격리 DB → 전체 시험과 빌드 → 독립 심사 → 실제 Chrome 순으로 검증하며, 수행하지 않은 검증은 미완료로 남긴다.

## ADD01 회원가입 이메일 인증

이메일 소유 확인을 통과한 주소로만 일반 이메일 회원가입을 완료한다. 화면의 인증 완료 표시를 조작하거나 가입 API를 직접 호출해도 서버 검증을 우회할 수 없어야 한다.

### 사용자 흐름

이메일 입력 → 인증번호 발송 → 메일 수신 → 번호 입력 및 확인 → 나머지 가입 정보 제출 → 가입 완료. 인증 후 이메일을 바꾸면 인증 상태를 해제하고 새 주소를 다시 확인한다. 재발송·만료·발송 실패는 화면에 구분해 표시한다.

### 확정 정책과 운영 초깃값

| 항목 | 적용 정책 |
| --- | --- |
| 인증 수단 | 메일로 받는 6자리 번호 |
| 유효 기간 | 10분, 재발송 간격 60초 |
| 시도 제한 | 인증 건당 오입력 5회 이후 새 인증 필요 |
| 재발송 처리 | 이전 번호 무효화. 이메일당 시간당 5회·하루 10회, IP당 시간당 30회·하루 100회 |
| 기존 계정 | 기존 계정은 추가 인증 강제 없이 유지. 실제 미인증 주소를 인증 완료로 허위 변경하지 않음 |
| Google 및 Discord | 서버가 제공자의 이메일 인증 사실을 확인하면 추가 인증 생략. 확인되지 않으면 메일 인증 적용 |
사용자가 제안 정책을 승인하고 초깃값 설정을 위임했다. 가입 증명 유효시간도 10분으로 시작하며 발송량 제한은 운영 설정으로 조절한다. 발송 서비스·발신 주소·테스트 수신함은 별도 준비한다.

### 구현 계획

- 발송·확인 API와 인증 상태 저장소를 추가한다. 인증 목적, 정규화 이메일, 만료 시각, 시도 횟수, 사용 여부를 서버가 관리한다. 번호 원문은 저장하지 않고 서버 비밀값을 이용한 검증값을 저장한다.
- 인증 성공 시 짧은 수명의 가입 증명을 발급한다. 가입 제출 때 이메일·목적·유효 기간을 재검증하고, 계정 생성 및 기본 지급과 함께 증명을 한 번만 소비한다. 가입 실패 시 복구와 재시도가 가능해야 한다.
- 사용자가 보낸 email_verified 값은 신뢰하지 않는다. 발송 실패를 인증 성공으로 표시하지 않고, 번호와 가입 증명을 로그에 노출하지 않는다.
- F29 비밀번호 찾기와 메일 전송 기반을 공유하되 인증 목적과 증명은 분리한다. 정확한 테이블·함수 이름은 실제 착수 시점의 코드와 대조해 결정한다.
### 인수 기준

정상 메일 수신 후 가입 성공, 인증 없이 직접 가입 거부, 번호 만료·오입력·재발송 처리, 인증 후 주소 변경 시 재인증, 같은 증명 동시 제출의 단일 가입을 검증한다. Chrome과 승인된 테스트 메일함에서 실제 발송·수신·가입까지 확인하고 기본 지급 및 중복 계정 방지 회귀 시험을 통과한다.

## ADD02 피의 기록 두 항목과 명성 제거

마이페이지의 피의 기록에는 전체 판수와 승률만 표시한다. 현재 세 행을 두 행으로 바꾸고, 생존 횟수·단두대 처형 행과 빈 구분선을 제거한다. 명성은 로비·마이페이지 공통 프로필 배너를 포함한 사용자 화면에서 제거한다.

### 삭제 범위와 유지 범위

| 구분 | 적용 내용 |
| --- | --- |
| 피의 기록 | 전체 판수 유지 및 승률 추가. 생존 횟수와 단두대 처형 표시 삭제 |
| 명성 | 화면의 명성 이름·숫자·아이콘·빈 자리 및 전용 표시 가공 제거 |
| 집계 데이터 | 전체 판수·승수와 업적·랭킹에 필요한 생존·처형 원본 집계 보존 |
| 명성 저장값 | 미사용 계산·API 필드는 소비처 확인 후 정리. 기존 DB 컬럼의 물리 삭제는 보호 규칙에 따라 별도 이관 검토 |
승률은 특정 직업의 최고 승률이 아닌 계정 전체 전적 기준이다. 구현 기본안은 기존 서버의 유효 종료 판수·승리 판정을 재사용한 승수 ÷ 전체 판수 × 100이며, 소수 첫째 자리와 0판의 0.0%를 표시한다. 별도 게임 승패 규칙은 새로 만들지 않는다.

### 구현 계획

- useMyProfile과 myPageAssets의 통계 구성을 전체 판수·승률로 맞춘다. 서버가 전체 승수를 제공하지 않으면 기존 집계 계약을 확장하고, 브라우저가 다른 직업의 승률을 대신 쓰지 않게 한다.
- BloodRecordFrame, BloodRecordStatsPanel, BloodRecordStatRow와 관련 스타일을 검토해 두 행에 맞게 간격을 조정한다. 이미지 자체에 삭제 문구가 포함됐는지도 확인한다.
- 프로필 데이터가 없을 때 다른 계정의 값이나 정적 예시 숫자를 실제 전적으로 보이지 않게 한다. 숫자가 0인 계정도 0을 정상 표시한다.
- 공통 프로필 배너의 명성 표시와 관련 속성·스타일을 제거한다. 닉네임·칭호·프로필 장비는 유지하고, 업적·랭킹·운명의 가면의 원본 집계를 훼손하지 않는다.
### 인수 기준

피의 기록은 항상 전체 판수·승률 두 항목으로 구성한다. 정상·0판·계정 전환·새로고침에서 값과 반올림이 정확하고 명성이 다시 나타나지 않아야 한다. 조회 실패를 실제 0판으로 위장하지 않는다. 확대 글자·좁은 화면의 배치를 확인하고 업적·랭킹·운명의 가면 회귀 시험을 통과한다.

## ADD03 다이아 충전과 골드 구매

토스페이먼츠 테스트 결제로 다이아만 충전한다. 충전된 다이아로 골드를 구매할 수 있다. 화면에 테스트 결제임을 표시하며 실제 결제수단에서는 금액이 차감되지 않는다. [1]

### 범위와 상품 정책

초기안은 카드·간편결제 통합결제창의 일회성 결제다. 결제 충전 대상은 DIAMOND로 고정하고, 골드는 다이아를 지불하는 상점 상품으로 제공한다. 상품 가격·지급량·보너스·골드 구매 조건은 별도 백엔드가 DB에 등록한다. 게임 서버가 DB를 조회해 화면과 신규 주문에 반영하며, 최종 숫자 확정을 기다리지 않고 구현한다. 상세 책임·스키마·갱신·인수 기준은 [F32 DB 상품 계약](2026-09-14-f32-db-product-contract.md)을 따른다. 서버 상품 목록을 기준으로 금액·수량 변조를 거부한다. [2]

### 결제와 지급 흐름

다이아 상품 선택 → 서버 주문 생성 → 토스 테스트 결제창 → 인증 복귀 → 주문자·금액 대조 및 서버 승인 → 다이아 지급 → 잔액 재조회. 이후 골드 상품 선택 → 다이아 차감과 골드 지급을 함께 확정한다. 성공 URL만으로 지급하지 않고 서버가 paymentKey·orderId·amount를 확인한다. [2][3]

### 구현 계획

- 새 충전 주문에 소유 계정, 상품 버전, 금액, 지급량, 상태 및 고유 주문번호를 저장한다. 테스트 클라이언트 키와 시크릿 키는 같은 세트를 사용하며 시크릿은 서버에만 둔다. 라이브 키가 들어오면 테스트 실행을 차단한다. [1]
- 결제 승인과 로컬 DB 저장은 하나의 분산 트랜잭션이 될 수 없으므로, 승인 성공 후 지급 실패를 별도 상태로 남긴다. 외부 API 대기 동안 DB 행 잠금을 오래 유지하지 않는다.
- 결제 승인 응답을 잃으면 즉시 새 주문이나 새 지급을 만들지 않고 같은 주문의 결과를 조회·복구한다. 외부 API 멱등키와 내부 주문·결제키·원장 유일 제약을 함께 사용한다. [4]
- 지갑 증액·충전 원장 기록·지급 완료 표시를 로컬 트랜잭션으로 확정한다. 승인 후 서버 중단 또는 DB 실패 시 재처리로 정확히 한 번 지급되도록 한다. 취소된 결제는 지급 대상에서 제외한다.
- 골드 구매는 기존 상점·원장을 사용해 다이아 차감과 골드 증가를 같은 트랜잭션으로 처리한다. 잔액 부족은 전부 취소하고 재시도는 같은 구매 ID로 한 번만 반영한다. 골드로 다이아를 되사는 경로는 추가하지 않는다.
### 인수 기준

DB에 별도 연결로 상품을 등록·수정·판매 중지한 뒤 서버 재시작 없이 다음 조회에 반영되는지 확인한다. 기존 주문의 가격·지급량은 상품 변경 후에도 유지한다. 실제 테스트 결제 → 다이아 증가 → 다이아로 골드 구매 → 양쪽 잔액 및 원장 → 새로고침을 확인한다. 금액 변조·타인 주문·잔액 부족은 거부하고 중복 호출·응답 유실·DB 실패에도 한 번만 반영한다. 실패·취소 결제는 지급하지 않는다. 유료 운영 전환·정기결제·운영 환불은 별도 범위다.

### 확정된 범위와 남은 결정

- 확정: 새 이메일 가입 인증, 기존 계정 추가 인증 강제 없음, Google·Discord의 검증된 이메일 추가 인증 생략. 인증 제한 초깃값은 위임에 따라 문서에 설정했다.
- 확정: 마이페이지 피의 기록은 전체 판수·승률만 표시하고 명성은 제거한다. 토스 충전은 다이아만 제공하며 다이아로 골드를 구매할 수 있다.
- 상품 가격·지급량·골드 구매 조건·보너스는 별도 백엔드가 DB에 입력하는 값이다. 이를 지금 사용자에게 확정받는 절차는 필요하지 않다. 필요한 외부 설정: 메일 발신 환경·테스트 수신함·토스 테스트 상점 키. 키는 문서나 저장소에 기록하지 않는다.
### 기존 작업과 검증 운영

기존 F19 진행 중 소스를 덮어쓰지 않는다. ADD02는 마이페이지 변경이 안정된 뒤, ADD01은 F29 메일 공통 기반과 충돌 여부를 확인한 뒤, ADD03은 기존 지갑·상점 계약을 확인한 뒤 착수한다. 기존 배치에 추가 등록은 완료됐으며 총32개, F29→F30→F31→F32→F28 순서다.

DB 검증은 승인된 pluto_f01_20260909_al 및 _restore_check에서만 수행한다. 구현·전체 DB 검사·Chrome QA를 동시에 실행하지 않는다. 관련 실패를 먼저 재현하고 전체 검사 및 독립 심사를 수행한다. 추가 세 건의 정상 병합 후 F28에서 통합 인수한다.
