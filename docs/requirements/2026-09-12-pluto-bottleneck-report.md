## 병목 판단과 책임 구분

1. 계획·구현의 소비처 완전성 부족: 설정store만이 아니라 실제글자소비처, cqi, 임의variant까지 뒤늦게 발견. 작은 보정마다 검증/심사 고리가 다시 시작됨. 실제 제품 누락이며 단순심사과잉으로 처리할 수 없다.
2. 검증 결과 인계 부족: 코드가 그대로인 사용자 담당 예외 변경에도 전체테스트가 다시 실행. DB검사약9–10분+심사 반복. operator의 늦은예외정리도 비용을 늘렸다.
3. 범위 식별자·파생제한 반복: 변경없는 코드까지 재색인된ID로 다시 걸림. 수동감사·rescope·예약대기 반복. DB/제품정확성 문제와 구분해야 한다.
4. 작업자 실행권한과 operator환경 불일치: 코드수정가능하지만 테스트명령이거절되어 operator에게 넘김. 거절을모델품질실패로세면안된다.
5. operator 단계전환처리: IMPLdone/VERIFYtodo 자동실행관계를 잘못가정해 todo정체와 추가kick이 반복. 요청성공을실행시작으로성급히기록한부분도있어정정했다.
6. 실제Chrome을늦게수집: 첫심사전에봤다면입력16px/미리보기CSS결함을더일찍발견할수있었다. 재로그인·6인게임준비·정리비용도누적.
