# Pluto 개선 과제 — Joker 실작업 근거

2026-09-12. 이 문서는 제품 요구사항과 별개인 Pluto 개선안이다. **아래 개선은 제안이며 Pluto에 구현 완료된 기능이 아니다.** 원본 실행 기록은 삭제·대체하지 않는다. 모델 성능과 실행 환경 실패를 구분한다.

## 1. 요구사항과 실제 소비처를 계획에서 대조 (우선)

- 사례: F15 설정 store와 설정 탭 계획은 통과했지만 App·채팅 소비처가 빠졌다. 후속 글자 크기 변환도 마이페이지의 cqi 단위 5곳을 놓쳤다.
- 근거: `.pluto/slices/AZ/runs/CODEX-1.json`, `CODEX-3.json`, `.pluto/monitor/AZ-cqi-red.log`, `AZ-D2-CONSUMER-AUDIT.json`.
- 원인: 함수 존재 확인만으로 연결 완전성을 판단했다. 검색 정규식이 px/rem/em만 다뤄 cqi를 누락했다.
- 변경안: Function DB에 입력→저장→구독/이벤트→실제 소비처→검증 근거를 요구사항 ID와 함께 연결한다. 호출 그래프뿐 아니라 React 구독, CSS 변수·단위, 소켓 생산자/수신자 관계의 지원 여부를 먼저 조사한다. 인덱스 대상 커밋과 신선도를 기록한다.
- 완료 기준: 의도적으로 연결을 끊은 소비처와 cqi 소비처가 계획 대조에서 누락으로 검출된다. 제외 경로에는 구체적인 이유가 있고 테스트와 실제 화면 증거로 뒷받침된다. 정적 분석의 미확인 영역은 완전성 PASS로 처리하지 않는다.

## 2. 테스트 이름 대신 사건 순서·확인값 검증 (우선)

- 사례: F13은 B 저장이 끝난 뒤 A의 늦은 응답을 보내는 테스트로 B 저장 **도중**의 문제를 검증했다고 판단해 반려가 반복됐다. 일부 재접속 테스트는 실제 소켓 처리 없이 같은 입력을 재호출했다.
- 근거: `.pluto/slices/AX/runs/CODEX-2.json`, `CODEX-5.json`, `CODEX-6.json`, `CODEX-7.json`, `CODEX-9.json`.
- 변경안: 계획에 사건 순서, 보류할 응답, 중간 상태와 최종 서버값을 명시한다. 반려 버그의 회귀 테스트는 가능한 경우 수정 전 실패와 수정 후 통과를 함께 저장한다.
- 완료 기준: A 요청→편집 닫기/재열기→B 저장 중→A 성공/실패/재조회 완료의 각 분기에서 B의 저장 상태와 최종 서버값을 확인한다. 같은 데이터의 재호출은 재접속 증거로 분류하지 않는다.

## 3. 실제 Chrome 증거를 최종 심사 전에 수집 (우선)

- 사례: F13 사망 후 재접속 증거 부족으로 마지막 심사가 반복됐다. F15의 예상 글자 크기 곱셈 함수는 CSS 계산을 실행하지 않았다. Chrome에서 채팅 메시지는 변했지만 입력칸은 16px로 관측됐다(원인 조사 중).
- 근거: `.pluto/slices/AX/runs/CODEX-10.json`, `.pluto/slices/AZ/runs/CODEX-3.json`, `.pluto/monitor/f15-browser-evidence/text-size-measurements.json`, `chat-size-color.json`.
- 변경안: 커밋 확정→격리 QA 준비→실제 Chrome 시나리오→화면·계산 스타일·서버 결과 증거→최종 심사 순서. 커밋, 빌드, URL, 테스트 계정 식별자, 시나리오, 실행 시각을 증거에 묶는다. 인증 비밀은 기록하지 않는다.
- 완료 기준: 스타일 연결을 제거하면 실제 computed style 검증이 실패한다. 브라우저 연결 실패·로그인 대기·제품 결함·사용자 직접 확인을 별도 상태로 처리한다. 코드 변경 후 영향받은 증거는 다시 수집한다. QA와 동일 DB 전체 테스트는 동시에 실행되지 않는다.
- 사용자 예외: F15 전체화면은 사용자가 직접 확인하기로 했다. 미검증·사용자 담당으로 남기고 자동 실행을 반복하지 않으며 PASS로 바꾸지 않는다.

## 4. 실행 인프라 실패를 구현 재시도와 분리

- 사례: Windows 모델 실행 래퍼의 stdin EOF와 공백 포함 allowedTools 인자 분리로 데몬이 종료되거나 `--test`가 알 수 없는 옵션으로 처리됐다. 이후 작업자 node 실행 권한 거부로 코드 수정 후 검증을 수행하지 못했다.
- 근거: `.pluto/monitor/daemon-recovery.stderr.log`, `implementation-model-routing.jsonl`, `.pluto/slices/AZ/runs/IMPL-3.json`~`IMPL-7.json`; operator 대행 결과 `AZ-consumers-recovery-fulltest.log`.
- 변경안: 실제 인자 배열·stdin 종료·자식 오류를 검증하는 실행 어댑터 계약을 둔다. 실행 전 허용된 테스트 runner의 사용 가능 여부를 확인하고, 환경 차단이면 이미 승인된 operator 검증 경로에 넘긴다. 승인 거부를 다른 실행 형태로 우회하지 않는다.
- 완료 기준: 잘못된 인자·조기 종료로 데몬이 죽지 않고 정확한 실행 오류를 남긴다. 인프라 실패가 모델의 코드 반려 횟수나 구현 재시도 예산을 소비하지 않는다. 라우팅 의도 로그와 실제 모델 실행/완료 증거를 구분한다.

## 5. 단계 전환을 원자적이고 재실행 안전하게 만들기

- 사례: operator가 IMPL done 후 VERIFY todo를 연달아 요청했다. 첫 전환이 자동으로 검증을 시작했는데 두 번째 요청이 running을 todo로 덮어썼다.
- 근거: `.pluto/monitor/checks.jsonl`의 `verify_todo_transition_race_recovered`, `advance-az-consumers-verified.mjs`, `kick-az-verify.mjs`.
- 변경안: 완료 및 다음 작업 예약을 한 명령에서 수행하고 예상 revision/state를 검사한다. 이미 running인 단계에 오래된 todo 요청이 도착하면 거부하거나 기존 실행 상태를 반환한다.
- 완료 기준: 중복·역순 전환 요청에도 검증은 한 번만 실행되고 멈춘 todo나 중복 프로세스가 생기지 않는다. state.json 직접 수정을 복구 수단으로 요구하지 않는다.

## 6. 범위 확장과 정확성 심사를 분리

- 사례: F15 소비처 추가 후 범위 오류가 반복됐다. 118건은 독립된 제품 버그 118개가 아니라 기존 계획 밖 엔티티와 파생 변경 제한이었다. 전체 파일을 비교해 원래 글자 크기를 보존하는 변환임을 감사한 뒤 공식 rescope를 수행했다.
- 근거: `.pluto/monitor/AZ-SCOPE-AUDIT-D2.json`, `AZ-D2-CONSUMER-AUDIT.json`.
- 변경안: 계획에서 승인한 소비처 확장을 최신 인덱스와 연결하고 식별자 변경을 추적한다. 범위 확인을 기능 PASS와 별개로 기록한다.
- 완료 기준: 동작이나 원래 크기를 바꾼 변환은 자동 허용되지 않는다. 단순 재인덱싱은 불필요한 구현 재시도로 보내지 않는다. 범위 승인 후에도 정상 테스트·심사가 그대로 실행된다.

## 7. 기존 배치에 후속 요구사항을 안전하게 반영

- 사례: F23의 사망자 관전/나가기 후속 승인은 문서에 반영했지만 기존 BH의 requirement snapshot을 갱신하는 공식 RPC가 없어 AC/계획 생성 시 별도 반영이 필요하다.
- 근거: `docs/requirements/2026-09-12-f23-dead-player-choice.md`, `.pluto/monitor/AY-CURRENT-HANDOFF.md`.
- 변경안: 요구사항 revision과 후속 승인 내역을 공식 갱신 API로 저장하고, 영향받는 AC·계획·증거의 재검토 필요성을 표시한다. 실행 중 변경은 충돌 검사와 적용 시점을 갖는다.
- 완료 기준: 중복 배치나 state 직접 편집 없이 후속 요구가 실제 작업 지시서와 최종 인수에 포함된다. 구버전과 최신 지시가 충돌하면 최신 승인 근거가 명확히 보인다.

## 비교 지표

기능별 최초 계획 반려, 범위 조정, 제품 결함 반려, 증거 부족, 실행 인프라 실패, 실제 구현 시간, 검증/대기 시간을 별도 집계한다. Opus/Sonnet 비교에서는 이전 코드·구체적 심사 피드백을 물려받은 조건을 기록한다. 단순 토큰 사용량이나 테스트 개수만으로 성능 우위를 결론내리지 않는다.

## 기록 보존 및 후속 정정 (2026-09-12)

사용자가 중요하다고 지정한 Pluto 개선 근거다. 원본 실행 로그·심사 결과·브라우저 증거를 보존하고, 요약에는 원본 경로와 커밋을 함께 적는다. 관측 사실, 원인 가설, 보정 내용, 재검증 결과, 남은 미확인을 구분한다. 이전 판단은 원본을 지워 맞추지 않고 정정 기록을 덧붙인다. 개선 제안과 구현 완료를 구분한다.

- 3번 후속: 입력칸의 생성 CSS에 clamp 규칙이 있음을 확인했다. 같은 clamp를 textarea의 inline fontSize에 적용한 수정 `884c3555` 이후 실제 게임에서 보드 입력 7.581/12.635px, 클로즈업 입력 12.288/20.48px(설정 0/100)을 확인했다. 기존 CSS 적용 실패의 정확한 원인은 미확정이며 수정 후 동작 확인과 구분한다. 증거 커밋 `ccc9bfc9`, AZ 워크트리 `docs/test-evidence/f15/README.md`, `input-css-reproduction.json`, `06-input-actual-fixed.json`, `07-closeup.json`. 메시지가 없던 클로즈업 화면은 메시지 글자 크기 검증으로 간주하지 않는다. 전체화면은 계속 사용자 담당·미검증이다.
- 5번 정정(14:29 KST): 앞선 기록의 “IMPL done만으로 자동 VERIFY 시작”은 현재 상태에서 재현되지 않았다. 실제 IMPL done에 머물렀고, 공식 VERIFY todo 전환 및 위반 없는 result/rescope 호출 후 VERIFY running을 확인했다. 앞선 자동 전환·경합 설명을 모든 실행의 확정 원인으로 일반화하지 않는다. 근거: `.pluto/monitor/checks.jsonl`의 `explicit_final_verifier_dispatch_confirmed`, `.pluto/monitor/start-az-final-verification.mjs`. 파이프라인 개선에는 요청 성공과 실제 작업 시작을 각각 확인하는 기준이 필요하다.

- 추가 개선 근거(2026-09-12): F15 전체화면은 사용자가 직접 확인하도록 이관했지만 result/manual API가 PASS/FAIL만 지원하여 미검증·사용자 담당 예외를 표현할 수 없었다. 허위 PASS 대신 공식 acceptance/set으로 자동 회귀 테스트와 사용자 담당 실제 검증을 분리하고 정상 테스트·심사를 다시 실행했다. 근거: .pluto/monitor/AZ-FULLSCREEN-USER-EXCEPTION.json, apply-az-user-fullscreen-exception.mjs. 개선안: 사용자 승인 근거·담당자·미검증 범위를 보존하는 별도 이관 상태와, 인수 조건 변경의 영향에 따른 재검증 범위를 지원한다. 완료 기준: 이관을 기능 PASS로 표시하지 않으면서 승인 범위 밖의 대기 때문에 배치가 막히지 않고, 영향받는 테스트·심사는 유지된다.
