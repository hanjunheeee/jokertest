## 고친 것 (모두 `C:/dev/pluto/packages/daemon`, 미커밋)

1. **상한 1회 연장** — `retry {id, reason(30자+), overrideCap:true}`. 정확히 상한(6)에 선 작업을 사유와 함께 한 번만. 이력에 `[절대 상한 1회 연장 — 사람 사유]` 표식이 남아 두 번째는 거절. 통과 기준(두 심사관 yes)은 그대로.
2. **읽기 허용 Claude 심사의 대체 경로** — 읽기 도구를 준 심사가 턴을 읽기에 다 쓰고 판정을 못 내는 일이 BR에서 두 번 연속 났다(12턴, 20턴). 한도(limit)가 아닌 실패면 같은 자료로 도구 없는 한 턴 판정을 한 번 더 받는다. 프롬프트에 "읽기는 8번까지, 마지막은 반드시 판정 JSON" 추가, 턴 12→20.
3. **분할 계약의 성공 조건 문구 교정** (`src/split-amend.ts`, `split.ts amendSplit`, RPC `pluto/slices/split/amend {parentId, reason, items:[{from,to}]}`)
   - 분할은 조각의 성공 조건을 부모 원문과 글자 그대로 잠근다. 그 잠금은 풀지 않았다. 사람이 승인한 `from→to` 치환 기록을 `.pluto/split-amendments/<부모>.json`에 남기고, 계약 해시와 원문 대조는 교정을 **되돌린** 글자로 계산한다.
   - 기록 없는 임의 변경·약화는 여전히 거부. 교정 뒤에는 옛 문구로도 통과할 수 없다.
   - 여러 조건을 한 호출로 원자적으로 교정한다(첫 교정 직후 재심이 시작돼 다음 교정을 막지 않게).
   - 멈춰 선 조각(VERIFY human/error)은 같은 후보를 새 문구로 재심한다. 교정된 조건의 옛 반려는 승계하지 않고 "새 문구로 처음부터 판정하라"는 한 줄로 바뀐다.
   - 실수 기록: 처음에 기록 파일을 `.pluto/splits/`에 뒀다가 분할 모듈이 모르는 `.json`을 "unrecognized manifest file"로 거부해 분할 관련 RPC가 전부 막혔다. 별도 폴더로 옮겼다.
4. **성공 조건 교정 후 1회 구현** — 교정 뒤 구현 회차가 아직 없으면 새 계약 아래 한 번(사유 30자+, 표식 `[성공 조건 교정 후 1회 구현 — 사람 사유]`). 한 번 돌면 닫힌다.
5. **교정된 조건이 열려 있으면 delta가 아니라 전체 patch** — 새 문구는 조각 전체를 근거로 판정해야 하는데 delta에는 이번에 안 바뀐 시험 파일이 없어 두 심사관이 "delta에서 확인되지 않는다"로 반려했다. 직전 반려 사유에 교정된 조건이 남아 있으면 전체 patch로 심사한다.
6. **사람 승인 추가 회차** — `retry {id, reason(80자+), extraRound:true}`. 상한과 1회 연장을 다 쓴 작업이라도 구체적인 긴 사유로 명시 요청하면 한 번 돈다. 매 회차가 `[사람 승인 추가 회차]` 표식과 사유 전문으로 이력에 남는다. 자주 쓰게 되면 분할·요구 변경의 신호다.

7. **교정 문구의 경로 오류와 재심 조건** — 내가 교정한 SPLIT-1에 `app/routes/index.jsx`(frontend/src 기준 상대 경로)라고 적었는데, Pluto는 성공 조건 문장 속 경로의 존재를 기계로 확인한다(`pathsIn`·`checkPaths`). 저장소 루트에 없어 "없다"로 SPLIT-1이 FAIL 났다. 코드·시험·두 심사관 판정은 전부 통과 상태였다. 같은 교정 경로로 경로만 `frontend/src/app/routes/index.jsx`로 바로잡았다. 이때 BR이 자동 재시도 소진으로 `IMPL human · VERIFY error`였어서, 교정이 재심을 다시 거는 조건을 `IMPL done`뿐 아니라 `human`도 받도록 넓혔다(reverify와 같은 조건, 구현은 이미 커밋돼 있다). **교훈: 성공 조건 문장에 경로를 적을 때는 저장소 루트 기준 실제 경로로 적는다.**

8. **빈 번호가 있는 배치에 삽입 불가** — `insertBatchItems`가 배치 번호를 1부터 빈틈없이 요구했다. 조커 배치는 F-22가 취소돼 22번이 비어 있어(31개·total 32) 어떤 삽입도 "Batch ordering inconsistent"로 거부됐다. 번호는 엄격 증가·total 동일만 요구하고, 빈 자리는 보존한 채 삽입 지점 뒤만 밀도록 고쳤다. `test/batch-insert.test.ts`에 빈 번호 사례와 중복 번호 거부 사례 추가(9개 통과).

## 개발 DB를 현재 기준으로 정렬 (사용자 지시 2026-09-19 12:49~)

화면 확인 스크립트가 로그인에서 500으로 멈추면서 드러났다. **Pluto나 BR의 문제가 아니라 개발 환경 문제**다.

- 개발 DB(`joker`)에 F-01 이후의 마이그레이션 13개가 하나도 적용돼 있지 않았다. 서버 기동 시의 `sync({force:false})`가 없는 **테이블**은 만들어 와서 테이블은 29개였지만, 마이그레이션이 추가하는 **컬럼**(`user_sessions.refresh_token_hash` 등 5개)은 없었다. 그래서 현재 코드로는 메인 브랜치에서도 로그인이 500이었다. 자동 시험은 격리 DB(`pluto_f01_20260909_al`)를 써서 드러나지 않았다.
- 사용자가 직접 `migrate`를 돌리자 기준선 0001이 "기존 DB 구조가 F-01 기준선과 다릅니다"로 거부했다(설계된 동작, 데이터 변경 없음).

수행한 절차 (`docs/requirements/2026-09-09-f01-migration-runbook.md` 순서):

1. **백업** — `docker exec jokertest-db-1 … mysqldump --single-transaction --routines --triggers joker` → `tmp/db-backups/joker-before-baseline-align-20260919-124941.sql` (243,739바이트 · 테이블 29 · 정상 종료 표시 확인 · gitignore 대상). 비밀번호는 컨테이너 환경변수를 그대로 써서 값을 보지 않았다.
2. **기준선과의 차이 정렬** — 8개 시간 컬럼의 기본값을 `CURRENT_TIMESTAMP`로(`account_find_requests.created_at`, `password_reset_tokens.created_at`, `user_sessions.connected_at`, `user_bans.created_at`, `login_history.login_at`, `online_presence.last_active_at`, `friend_requests.created_at`, `traffic_logs.accessed_at`), `friendships.created_at·updated_at`을 NOT NULL로(NULL 행 0개 확인 후). 데이터 행은 건드리지 않았고 행 수 전후 동일.
3. `resolve-failure --name 0001-legacy-baseline --confirm` → `migrate`: 0001~0012 적용.
4. **0013 실패 — "Cannot add foreign key constraint"**. 원인: 개발 DB의 `friend_requests` 외래키 두 개가 옛 sync 기본값인 `ON UPDATE CASCADE`였다.
