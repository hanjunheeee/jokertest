## 2. 공통 완료 기준

- 현재 UI의 그림·양피지·버튼·모달·프로필 리소스를 우선 재사용한다. 새 디자인 전체 교체는 하지 않는다.
- 서버가 계정 신원, 가격, 잔액, 소유권, 승패, 업적 달성을 판정한다. 클라이언트가 보낸 잔액·보상량·승리 여부를 신뢰하지 않는다.
- 재로그인·새로고침·다른 브라우저에서 재화, 소유품, 장착 상태, 업적이 복원된다. 로그아웃·계정 전환 시 이전 계정 캐시는 초기화한다.
- 구매·보상은 중복 클릭, 네트워크 재시도, 동시 요청에서도 한 번만 처리된다. 차감만 되거나 아이템만 지급되는 부분 성공이 없다.
- 기존 계정·경기 기록을 보존하고 기본 지급품을 중복 없이 이관한다. 기존 테이블 변경에는 명시적 마이그레이션·재실행 안전성·복구 절차를 마련한다. `sync({ force: false })`만으로 기존 컬럼이 바뀐다고 가정하지 않는다.
- 역할 정보·밤 행동 비밀은 서버에서 수신자별로 제한한다. 숨긴 UI 뒤의 payload에 비밀 정보를 넣지 않는다.
- 정상·로딩·빈 상태·실패·재시도 화면을 구현한다. 성공하지 않았는데 완료 토스트만 표시하는 기능은 완료로 인정하지 않는다.
- 신규 API·DB·소켓 동작 테스트, 프론트 상태/훅 테스트, production build, 실제 브라우저 시나리오 검증이 모두 필요하다. 실행하지 못한 검증은 미검증으로 남긴다.
- 예전 UI 이식 배치의 ‘백엔드·DB·인증 변경 금지’는 이번 배치에 적용하지 않는다. 대신 이번 승인 범위에 필요한 변경만 허용한다.
- 모든 사운드·영상·설정 작업에 AUDIO-01의 음악 사용 금지와 무음 유지 조건을 적용한다. 볼륨 조절, 설정 초기화, 새 영상 추가로 음악이 다시 재생되면 완료로 인정하지 않는다.

## 3. 로그인·회원가입·계정관리

### AUTH-01 소셜 로그인

- 기존 Google·Discord 버튼을 실제 인증 시작·콜백·로그인 세션 생성까지 연결한다. **두 제공자 모두 사용자 선택으로 확정했다.** 계정 연결은 기존 계정 로그인 후 명시적으로 수행한다. 실제 앱 키·콜백 준비 여부만 외부 검증 조건으로 남긴다.
- 최초 로그인은 계정 생성과 닉네임·필수 정보 보완으로 이어지고, 재로그인은 같은 외부 계정 식별자로 기존 계정을 찾는다.
- 외부 계정 식별자는 제공자와 subject 조합으로 유일하게 저장한다. 동일 이메일이라는 이유만으로 기존 비밀번호 계정에 자동 연결하지 않는다. D-01에 따라 기존 계정 로그인 후 명시적으로 연결한다.
- 인증 취소, 만료·위조된 state, 재사용된 콜백, 이메일 미제공, 닉네임 중복을 처리한다. 외부 비밀키는 서버 환경설정으로 주입한다.
- `users.password_hash`가 현재 NOT NULL이므로 비밀번호 없는 소셜 계정의 스키마 및 계정관리 동작을 명시적으로 설계한다. 임의 공용 비밀번호를 발급하지 않는다.
- 완료: 각 제공자의 신규 가입·재로그인·취소·잘못된 콜백·기존 이메일 충돌 흐름을 확인한다. 실제 제공자 검증은 앱 등록·클라이언트 키·콜백 URL 준비 후 수행한다.

### AUTH-02 로그인 유지

- 선택 시 D-03의 유지 기간 동안 브라우저 재시작·토큰 만료 후에도 정상적으로 세션을 복구한다. 미선택은 영속 쿠키를 발급하지 않는 세션 방식으로 동작한다.
- 현재 30일 쿠키와 1일 JWT 만료의 불일치를 수정한다. 단순 체크박스 저장으로 끝내지 않는다.
- 로그아웃, 계정 정지, 비밀번호 변경에 따른 세션 폐기를 적용한다. 기존 HTTP 인증과 소켓 인증이 같은 유효 세션을 사용한다.
- 완료: 선택/미선택 쿠키 차이, 1일 경과, 유지 기간 만료, 로그아웃 후 재접속, 세션 폐기 후 API·소켓 거부를 검증한다. 브라우저의 세션 복원 기능이 있으므로 ‘창을 닫는 즉시 서버 세션 폐기’와 구분한다.

### AUTH-03 가입 입력과 검증

- 가입 입력: 이메일, 비밀번호, 비밀번호 확인, 닉네임, 생년월일. 전화번호는 선택 입력으로 둔다. 생년월일은 필수 입력 기준이다.
- 실제 DB에는 `phone varchar(20)`, `birth_date datetime`이 존재한다. 생년월일은 `input type="date"`로 받고 달력 날짜를 검증하여 시간대에 따라 하루가 이동하지 않게 저장·복원한다.
- 닉네임 최소·최대 길이와 허용 문자를 프론트·서버에서 동일하게 검사한다. 한글 입력 중 IME 조합을 깨뜨리지 않는다. 최대 8자는 사용자 확정이며, 기존 최소 2자·한글/영문/숫자 기준을 유지한 2~8자로 정리한다. 비밀번호는 기존 권장 8~64자·bcrypt 72바이트 한도와 확인 입력을 적용하며, D-02의 최소 연령 제한은 미지정이다.
- 현재 `users.nickname`은 50자, `game_result_players.nickname_snapshot`은 30자로 다르다. 기존 긴 닉네임을 임의로 자르지 않고 기록 저장이 실패하지 않도록 호환 조치를 설계한다.
- 이메일 형식·길이·정규화 정책을 통일한다. 입력 단계 중복 확인과 가입 최종 단계의 중복 검사를 모두 제공한다. 확인 이후 이메일을 바꾸면 이전 확인 결과는 무효화한다.
- 동시 가입은 DB 유일 제약으로 막고 사용자에게 중복 오류를 보여준다. 기존 409 처리와 계정·통계 생성 트랜잭션을 유지한다.
- 사용자가 입력할 수 있는 필드만 허용한다. `role`, `status`, `email_verified`, 재화 등 관리 필드를 가입 폼에 노출하거나 요청 그대로 저장하지 않는다.
- 완료: 길이 경계, 공백·잘못된 날짜·미래 날짜, 비밀번호 불일치, 중복 확인 후 수정, 동시 중복 가입, 가입 후 DB 저장·재로그인을 확인한다.

### AUTH-04 닉네임·비밀번호 변경

- 기존 `/user/me/nickname`, `/user/me/password` API와 계정관리 UI를 보완한다. 같은 목적의 두 번째 API를 만들지 않는다.
- 닉네임 변경에도 가입과 동일한 검증·중복 정책을 적용한다. 로비·마이페이지·친구/랭킹 현재 닉네임을 갱신하되 과거 경기의 닉네임 스냅샷은 보존한다.
- 현재 비밀번호 확인 → 새 비밀번호·확인값 검증 → 해시 저장 → D-03의 세션 정책을 적용한다. 비밀번호 분실 복구는 새 AUTH-06/F-29에서 구현하고 세션 폐기 계약을 공유한다.
- 소셜 전용 계정은 존재하지 않는 현재 비밀번호를 요구하지 않는다. 비밀번호 추가 발급은 D-01에서 별도 선택하지 않으면 제공자 관리 안내로 처리한다.
- 완료: 타인 계정 변경 거부, 중복 닉네임·잘못된 현재 비밀번호 거부, 변경값 재조회, 이전 비밀번호 로그인 실패, 새 비밀번호 로그인 성공을 확인한다.

### AUTH-05 아이디 찾기·마스킹 이메일 안내

- 로그인 화면에 아이디 찾기 진입을 추가하고 기존 인증 UI·입력·버튼·배경 리소스를 재사용한다. 로그인 전 접근 가능한 화면/라우트를 제공한다.
- 현재 로그인 아이디는 이메일이다. 사용자 확정 방식은 닉네임과 생년월일의 일치 확인 후 마스킹된 이메일 힌트만 안내하는 것이다. 별도 SMS 인증은 이번 범위에 추가하지 않는다.
- 닉네임은 서버의 동일 정규화 기준, 생년월일은 달력 날짜 기준으로 대조한다. 기존 긴 닉네임을 가진 계정의 찾기도 가능해야 하므로 신규 가입 8자 제한을 기존 계정 조회에 잘못 적용하지 않는다.
- 서버에서 이메일을 마스킹한 결과만 반환한다. 전체 이메일·사용자 UUID·전화번호·추가 개인 정보를 응답/숨겨진 payload에 넣지 않는다. 짧은 이메일에서도 원문 전체가 드러나지 않도록 마스킹 규칙을 테스트한다.
- 불일치·계정 없음·생년월일 미등록은 구체적으로 어느 입력이 맞았는지 노출하지 않는 공통 안내를 사용한다. 생년월일이 없는 기존 계정의 정보를 임의로 채우거나 다른 입력으로 우회하지 않는다.
- 이 결과는 계정 식별 힌트이며 로그인·비밀번호 재설정 권한을 부여하는 본인인증으로 사용하지 않는다.
- IP와 정규화한 조회 대상 기준으로 요청 빈도·연속 시도를 제한하고 입력 형식·날짜·길이를 서버에서도 검증한다. 결과 없음·요청 제한·통신 실패·재시도·뒤로 가기 상태를 표시한다.
- account_find_requests는 현재 email NOT NULL인 미연결 로그 모델이므로 이메일 없는 조회 요청에도 기록 가능한 구조로 보완한다. 필요한 최소 사건 정보만 기록하고 생년월일 원문·전체 이메일을 불필요하게 로그에 남기지 않는다.
- 완료: 올바른/잘못된 조합, 짧은 이메일 마스킹, 기존 긴 닉네임, 생년월일 미등록, 조회 제한, 응답에 전체 이메일 없음, 힌트로 인증/비밀번호 변경 불가를 확인한다.

### AUTH-06 비밀번호 찾기·일회용 링크 재설정

- 로그인 화면의 미연결 비밀번호 찾기 버튼을 이메일 입력→재설정 요청→메일 링크→새 비밀번호/확인→완료·로그인 이동까지 실제 기능으로 연결한다. 로그인 전 접근을 지원한다.
- 계정 존재 여부와 관계없이 같은 형태의 요청 완료 안내를 사용한다. 메일 서비스 장애와 재시도 상태는 계정 존재를 드러내지 않는 방식으로 처리하며 실제 발송/수신 여부는 별도 검증한다.
- 가입 이메일 주소로만 암호학적으로 안전한 일회용 재설정 링크를 보낸다. 링크의 앱 주소는 서버의 허용된 설정을 사용하고 클라이언트가 지정한 임의 목적지로 만들지 않는다.
- password_reset_tokens 기존 모델을 재사용·마이그레이션한다. 토큰 원문은 DB·애플리케이션 로그에 저장하지 않고 해시, 만료 시각, 사용/폐기 상태를 저장한다. 기존 토큰 형식이 있으면 안전하게 무효화하고 계정 데이터는 보존한다.
- 유효기간은 구현 기본값 30분으로 설정 가능하게 하고 새 재설정 요청 시 이전 미사용 링크를 폐기한다. 링크를 여는 GET이나 메일 미리보기만으로 토큰을 사용 처리하지 않는다.
- 새 비밀번호는 가입/변경과 동일한 8~64자·bcrypt 72바이트 한도와 확인 입력을 검사한다. 현재 비밀번호를 요구하거나 기존 비밀번호를 복호화·메일 발송하지 않는다.
- 토큰 검증·사용 처리·비밀번호 해시 갱신·기존 세션 폐기를 하나의 일관된 처리로 수행한다. 동시에 같은 토큰을 제출해도 한 번만 성공하고 실패하면 변경 일부만 남지 않게 한다.
- 재설정 완료 후 HTTP·Socket.IO의 모든 기존 세션과 남은 재설정 토큰을 폐기하고 다시 로그인하게 한다. 계정 정지·권한 상태는 복구 과정에서 바꾸지 않는다.
- 비밀번호 없는 Google/Discord 전용 계정은 제공자 로그인/복구를 안내한다. 이 경로로 새 로컬 비밀번호를 임의 발급하거나 이메일 일치 계정을 자동 병합하지 않는다.
- 요청·재발송·토큰 검증에 서버 빈도 제한을 적용한다. 유효하지 않음·만료·이미 사용·동시 요청·새 링크 발급 후 옛 링크·메일 실패를 처리한다.
- 메일 발송은 설정 가능한 서버 어댑터와 테스트용 대체 어댑터를 사용한다. 실제 서비스 계정·발신 주소·앱 기본 URL은 외부 설정이며 비밀값을 문서/프론트에 넣지 않는다.
- 완료: 실제 테스트 수신함 링크로 새 비밀번호 로그인 성공·이전 비밀번호 실패, 만료/재사용/동시 제출 거부, 세션 폐기, 소셜 전용 계정, 미존재 이메일 공통 응답·발송 장애·토큰 비노출을 검증한다. 실제 발송 환경이 없으면 제공 대기·미검증으로 명시한다.

## 4. 로비·통합 설정·알림·Discord

### SET-01 설정 통합과 실제 적용

- 로비의 설정과 관련 진입 경로를 ‘설정’으로 정리한다. D-04에 따라 `/account` 계정관리는 별도로 유지한다.
- 일반 설정: 전체화면, 텍스트 크기, 친구 초대/게임 초대/시스템 알림, 도움말 다시 보기, 초기화.
- 알림 항목 중 ‘귓속말’을 제거한다. 다른 채팅 채널이나 알림 전체 삭제로 확대하지 않는다.
- 사운드: Master·배경음·효과음 설정을 공통 저장소로 통합한다. AUDIO-01에 따라 현재 배경음은 사용 중지·무음 상태를 유지한다. 음악이 포함된 영상도 무음으로 재생한다. AUDIO-02의 허용된 효과음은 Master×SFX로 조절한다. 음악 컨트롤은 비활성 상태를 유지하고 자산이 없는 효과음은 무음·미준비로 표시한다.
- 일반 텍스트 크기와 인게임 채팅 크기의 적용 범위를 구분하고 실제 표시 크기를 변경한다. 전체화면은 브라우저 권한·현재 상태와 동기화한다.
- 값 저장 위치는 확정된 D-04에 따라 기기 로컬 저장을 사용한다. 초기화는 확인 후 기본값·실제 음량·화면에 반영한다.
- 완료: 페이지 이동·새로고침 후 값 유지, 문자 크기 변경, 설정 초기화, 전체화면 실패/해제, 도움말 열기·닫기를 확인한다. 사운드 설정 조작과 초기화 후에도 금지 음악이 무음이며, 비활성 컨트롤과 실제 재생 상태가 일치해야 한다.

### SET-02 알림 모달

- 기존 모달 셸·버튼·폰트·그림으로 알림 진입 버튼과 목록 모달을 만든다. 목록·미확인 표시·읽음 처리·빈 상태·닫기·알림 대상 이동을 제공한다.
- D-05 확정 범위는 친구 요청, 게임 초대, 업적/보상 획득, 시스템 안내다. 게임 초대 생성·수락까지 포함하며 웹 푸시·메일 발송은 제외한다.
- 알림 설정은 표시/알림음 정책에 반영하며, 비활성화했다고 친구 요청이나 보상 자체를 소실시키지 않는다.
- 게임 초대는 대기방의 기존 친구 탭에서 발송하고 생성·수신·수락·거절·만료와 가득 찬 방/시작된 방/없어진 방 처리까지 구현한다. 단순 방 코드 복사와는 별개다.
- 완료: 실제 발생 이벤트가 중복 없이 표시되고 읽음 상태가 복원된다. 계정 변경 시 이전 계정 알림이 보이지 않는다.

### UI-01 로비 프로필과 고객센터

- **삭제 대상은 로비 오른쪽에 크게 표시되는 독립 Discord 버튼이다.** `LobbyPage`의 별도 `LobbyDiscordButton` 배치를 제거한다.
- **왼쪽 메뉴 목록 아래 고객센터 자리에 있는 Discord 버튼은 유지하며, 이 버튼이 고객센터 역할을 대신한다.** D-06에서 받은 Discord 초대/지원 채널 URL에 연결한다. 별도 고객센터 버튼이나 페이지를 추가하지 않는다. 소셜 로그인용 Discord 인증 URL과 구분한다.
- 로비에서 프로필 수정 버튼을 누르면 마이페이지와 같은 프로필 편집 모달을 열고 저장 결과를 즉시 표시한다. 현재 배너의 톱니는 `/account`로 이동하므로 계정관리와 프로필 편집 진입점을 명확히 구분한다.

## 6. 상점

### SHOP-01 실제 구매와 표시용 이모티콘 탭

- 기존 스킨·플레이어 카드·프로필 테두리·인게임 재화 카테고리를 유지하고 이모티콘 탭을 추가한다. 카탈로그 원형은 스킨 9종·카드 8종·테두리 6종·재화 패키지 8종이다.
- 스킨·카드·테두리의 상품명·이미지·가격은 기존 리소스 기반 임시 카탈로그를 사용하되 구매·차감·소유권은 서버/DB에서 실제 처리한다. 기존 가격 숫자는 골드 기준으로 사용한다.
- **이모티콘은 탭과 표시용 더미 상품만 만든다.** 구매 요청·재화 차감·소유권 지급·일괄 구매 선택·장착/사용을 연결하지 않는다. 카드에 구매 가능해 보이는 활성 동작을 두지 않고 준비 중 상태를 표시한다. 서버도 표시용 이모티콘 ID의 구매 요청을 거부한다.
- 실제 판매 상품에는 안정된 ID·유형·이름·이미지·가격 재화/수량·판매 여부를 정의한다. 서버가 가격·잔액·소유권을 검증한다.
- **개별 구매:** 한 상품의 차감·소유권 지급·거래 기록을 하나의 트랜잭션으로 처리한다. 잔액 부족·미판매·기보유·잘못된 상품·검증 실패·커밋 전 DB 오류이면 해당 구매의 골드/다이아 차감 0, 지급 0, 성공 거래 기록 0이어야 한다.
- **일괄 구매:** 선택한 실제 판매 상품 전체를 한 트랜잭션으로 처리한다. 한 품목이라도 실패하거나 총액이 부족하면 묶음 전체를 실패 처리하여 모든 재화 차감 0, 모든 상품 지급 0, 성공 거래 기록 0으로 되돌린다. 일부 상품만 성공하거나 이미 보유한 상품을 임의로 건너뛰지 않는다.
- 여러 개의 개별 구매는 각각 독립 거래다. 뒤의 개별 요청 실패가 이미 성공한 다른 개별 거래를 취소하지 않는다.
- **응답 유실/타임아웃:** 서버 커밋 여부를 모르는 상태를 확정 실패로 표시하지 않는다. 개별/일괄 모두 같은 요청 식별자로 결과 조회·재시도하여 기존 성공을 복원하고 다시 차감하지 않는다.
- 구매 전 총액·사용 재화·보유 상태를 표시하고 성공 후 지갑·소유품을 갱신한다. 기존 일괄 구매 모달을 재사용한다. 현금 충전과 재화 패키지 판매는 보류하고 무료 충전 경로를 만들지 않는다.
- 완료: 개별 성공/실패, 일괄 전체 성공/한 품목 실패/두 재화 중 한 재화 부족, 커밋 전 오류와 커밋 후 응답 유실을 구분하여 검증한다. 일괄 구매의 골드+다이아 혼합 검증은 격리 fixture로 수행하며 운영 가격을 임의로 바꾸지 않는다. 이모티콘 클릭·조작된 구매 요청에서도 차감/지급이 없고, 실제 구매한 테두리·외형은 재로그인 후 보존된다.

## 7. 기억의 서고·전적·업적

### STAT-01 직업별 전적·랭킹

- 경기 종료 기록을 기반으로 계정·직업별 판수, 승리 수, 승률, 생존 수를 계산한다. 기존 종료 기록 저장의 중복 방지를 유지한다.
- UI↔서버 직업 대응을 고정한다: 귀족 `noble ↔ CITIZEN`, 광대 `clown ↔ JOKER`, 주치의 `doctor ↔ DOCTOR`, 경비원 `guard ↔ GUARD`, 마녀사냥꾼 `witchHunter ↔ WITCH_HUNTER`.
- 초대받은 자들에서 선택한 직업의 내 전적과 전체 사용자 랭킹을 표시한다. 랭킹은 판수·승률이 보이고 정렬·최소 판수·동률·기간을 확정된 D-10대로 적용한다.
- 전적이 없는 사용자는 0판·승률 없음으로 표시한다. 더미 랭킹·개발용 완료 상태를 실서비스 데이터 경로에서 제거한다.
- 중단 경기·이탈자·개발용 소인원 경기·기존 경기 소급 반영은 확정된 D-09를 따른다. `won=null`을 패배나 승리로 임의 변환하지 않는다.
- 서고의 직업별 랭킹을 구현한다. 별도 `/podium` 명예의 전당은 로비 진입을 제거하고 UI 코드만 보존하며 데이터 연결·확장은 이번 범위에서 제외한다.

## 8. 마이페이지·프로필

### MY-01 운명의 가면

- 현재 최다 플레이 직업(`most_played_role`)을 사용하는 문구를 계정의 최고 승률 직업으로 변경한다.
- 승률과 판수는 STAT-01과 같은 집계 기준을 사용한다. 동률·최소 판수·전적 없음은 D-10을 따른다.
- 완료: 최다 플레이 직업과 최고 승률 직업이 다른 계정에서 최고 승률 직업이 표시되고, 경기 종료 후 갱신된다.

### MY-02 프로필 수정·테두리 장착

- 프로필 수정 모달에서 기본 제공품과 구매/업적 획득품을 선택한다. 프로필과 테두리는 별도 탭·별도 장착값이다.
- 미리보기 후 확인 시 저장하고 취소하면 이전 상태를 유지한다. 저장 실패를 성공처럼 처리하지 않는다.
- 로비·마이페이지·친구 목록·서고 랭킹에서 동일 계정의 장착값을 표시한다. 스킨·카드도 D-08에 따라 실제 소유권 검증·장착·인게임 반영을 포함한다.
- **마이페이지 이모티콘은 진입 버튼만 유지/추가한다. 버튼을 누른 뒤 나오는 UI는 사용자가 직접 제작한다.** Pluto는 빈 탭 내용·모달·준비 화면·장착 슬롯·보유 목록을 만들지 않는다. 추후 사용자 UI를 연결할 진입점만 마련하며 미제공 상태의 버튼 동작은 미연결로 명시한다.
- 상점 표시용 이모티콘을 마이페이지 보유품에 추가하지 않는다. 이모티콘 구매·장착·인게임 전송/재생은 후속 범위다.
- 사용자 이미지 업로드/파일 저장 서비스는 기본품·획득품 선택 기능과 별도 범위다.
- 완료: 미보유 장착 거부, 획득 즉시 반영, 취소/실패/저장/재접속, 계정 전환, 타인이 보는 프로필을 확인한다. 사용자가 제작할 이모티콘 후속 UI를 임의 생성하지 않는다.

### MY-03 계정 프로필 이미지 인게임 적용

- 마이페이지/로비에서 선택해 서버에 저장한 프로필 이미지를 게임 대기방과 인게임의 플레이어 초상에 반영한다.
- 계정 장착값→방 참가자→게임 시작 payload→상태 갱신/재접속 payload→클라이언트 모델→플레이어 카드까지 같은 이미지 식별자를 전달한다. 기존 슬롯별 preview 이미지는 미설정·유효하지 않은 자산의 기본 대체에만 사용한다.
- 본인과 다른 참가자, 생존/사망/연결 끊김 상태에서 계정 이미지가 유지된다. 필수 상태 오버레이와 역할 비밀성은 보존한다.
- 프로필 초상과 직업 스킨·프레임 표시를 혼동하지 않게 연결한다. 게임 시작 시 장착값을 스냅샷으로 사용하고 같은 판 재접속에서도 유지한다. 경기 중 다른 화면에서 변경한 외형의 즉시 방송은 이번 기본 범위에서 제외한다.
- 완료: 서로 다른 계정 이미지가 대기방·인게임에서 올바르게 보이고 새로고침/재접속으로 preview 이미지로 되돌아가지 않는다. 다른 참가자의 역할/진영 필드를 추가로 노출하지 않는다.

## 9. 대기방·인게임 설정

### ROOM-01 대기방 설정 변경

- 기존 방 생성 설정 UI를 편집 모드로 재사용한다. 현재 방 값을 불러오며 새 방을 생성하지 않는다.
- 방장만 저장하고 서버에서 현재 방·방장·대기 상태를 재검증한다. 정원은 현재 인원보다 작게 할 수 없다.
- 후보 항목: 공개/코드 입장 방식, 정원, 자동/수동 직업 구성, 광대 및 특수 직업 수, 토론·투표·전체/직업별 밤 시간, 투표 공개 여부.
- 저장한 값은 모든 참가자 및 방 목록에 반영하고 준비 상태를 해제하여 새 설정에 다시 동의하도록 한다. 저장과 시작 요청이 경합하면 서로 다른 설정으로 시작하지 않게 한다.
- 새로고침·재접속·방장 변경 후에도 서버의 최신 설정을 사용한다. 게임 시작 후 해당 판의 직업·제한시간은 소급 변경하지 않는다.
- ‘불이 꺼진 무도회’, ‘영혼의 베팅’은 현재 UI·설정 저장만 확인되고 게임 규칙의 소비는 확인되지 않았다. 골드·다이아와 영혼석을 같은 재화로 취급하지 않는다. D-12 채택에 따라 이들 추가 모드의 실제 규칙 구현은 이번 범위에서 제외하고 기존 엔진이 지원하는 설정 편집을 우선한다.

### GAME-01 개인 채팅·사운드 설정

- 채팅 글자 크기, 시간 표시, 닉네임 색상 표시를 실제 메시지 목록에 연결한다. 닉네임 색상으로 숨겨진 진영·역할이 노출되지 않는다.
- 사운드는 SET-01과 동일한 값·저장소를 사용한다. AUDIO-01의 음악 사용 금지와 연출 영상 무음을 유지하며, 인게임 설정이 이 차단을 해제하지 못하게 한다.
- 완료: 패널 열기/닫기·새로고침 후 설정 복원, 실제 채팅 표시 변경, 음악 무음 유지, 다른 계정·플레이어의 설정과 독립 동작을 확인한다.

### GAME-02 방관리

| 기존 UI 항목 | 구현해야 할 동작 | 경계 |
|---|---|---|
| 플레이어 추방 | 실제 참가자 대상, 확인, 서버 권한 검사, 대상 퇴장, 전원 상태 동기화 | 대기방/진행 중 허용, 사망·승패·보상 처리 D-13 |
| 다음 게임 동일 설정 유지 | 다음 방 생성에 현재 설정을 복원 | 같은 멤버 재대결까지 포함할지 D-13 |
| 방 코드 보기/복사 | 현재 방 코드 확인과 복사 결과 안내 | 진행 중 새 참가 제한과 기존 참가자 재접속 D-13; 관전 입장 없음 |
| 게임 강제 종료 | 방장 확인, 서버 종료, 타이머·소켓 정리, 전원 종료 안내 | 중단 사유·전적·보상 D-13 |

- **관전자 항목은 최신 지시로 전면 제거한다.** 나머지 항목은 확정된 D-13을 적용하며 진행 중 추방은 이탈 사망 규칙을 사용하고 다음 방에는 설정만 복사한다. 강제 종료는 무효 경기·업적/재화 보상 없음이다.
- 완료: 비방장의 직접 API/소켓 호출 거부, 오래된 방 요청 거부, 같은 요청 재전송, 대상 이탈 경합, 비참가자 접근 거부, 종료 후 방 입장 복구를 확인한다.

### GAME-03 관전자 기능 전면 제거

- 기존 F-23 관전자 구현 요구사항을 폐기하고 제거 작업으로 대체한다. 인게임 방관리의 관전자 허용 체크박스와 대기방/방 생성/다음 게임 설정 복원의 관련 항목을 모두 제거한다.
- 관전 버튼·입장 경로·라우트·모달·문구·상태·저장 키·API/소켓 계약을 조사하여 실제 존재하는 관전자 전용 코드를 제거한다. 현재 없는 관전자 서버 기능을 새로 만들지 않는다.
- 오래된 저장 설정의 allow-spectators 등은 읽기/복원 때 제거하여 새 설정에 다시 나타나지 않게 한다. 서버가 클라이언트의 관전자 관련 임의 필드로 접근 권한을 부여하지 않게 한다.
- 방 코드·게임 초대·직접 URL·API/소켓으로 별도 관전자 입장이나 공개 상태 구독을 할 수 없게 한다. 기존 게임 참가자 여부를 서버에서 검증하고 허용되지 않은 가입 요청을 거부한다.
- 이미 게임에 참가한 사망자는 기존 참가자 신분을 유지한다. 앞서 승인된 사망자 공개 결과 수신·의사 치료 가능성·대상자 성공 영상 수신을 별도 관전자 기능으로 오인하여 제거하지 않는다. 생존 여부에 따른 행동 제한과 기존 재접속 자격도 유지한다.
- 완료: 모든 설정/진입/저장·복원에 관전자 기능이 없고, 오래된 설정·직접 요청으로도 관전 입장이 되지 않는다. 정상 참가·준비·시작·재접속과 사망 참가자의 허용된 결과/밤 영상 수신은 정상 동작한다.

## 10. 밤 성공 영상과 전환 순서

### NIGHT-01 성공 정의와 수신자

| 사건 | 현재 엔진 의미 | 적용 영상 트리거 |
|---|---|---|
| 킬 | 기존에는 보호 대조 후 실제 사망을 확정 | 광대 턴 공격 성공 시 킬 연출. 이후 의사 치료로 생존 가능 |
| 경비원 | 살아 있는 대상 직업 조사(INVESTIGATE) | 유효한 조사 결과 생성 시 |
| 주치의 | 기존에는 밤 끝에 암살 차단 | 같은 밤 광대에게 죽은 대상을 살리면 치료 연출, 최종 생존 |
| 마녀사냥꾼 | 사망자 직업 확인(CONFIRM) | 유효한 확인 결과 생성 시 |

- 경비원을 보호 직업으로, 마녀사냥꾼을 처형 직업으로 임의 변경하지 않는다. ‘성공’의 다른 의미가 필요하면 D-14에서 게임 규칙 변경으로 명시한다.
- 현재 의사는 개인 성공 결과를 받지 않는다. 치료 성공을 서버가 판정하여 사용자와 대상자에게 전달하는 계약을 추가한다.
- **사용자 확정 수신자: 성공한 능력을 사용한 주체와 능력 대상자 모두.** 다른 참가자에게 개인 성공 영상을 보내지 않는다. 복수 인원 중 해당 성공에 유효 행동을 제출한 사용자만 수신하고 기권자는 사용자 영상 수신에서 제외한다.
- 대상자가 영상을 보는 것과 능력 사용자의 신원·조사 결과 전체를 보는 것은 구분한다. 확정안은 대상자에게 능력을 받았다는 연출만 제공하고, 조사 결과와 사용자 신원은 노출하지 않는 것이다. 조사된 역할 결과는 기존 권한이 있는 사용자에게만 제공한다.
- 실패·기권·대상 없음·합의 실패에는 성공 영상을 재생하지 않는다. 암살 실패 안내는 새 순차 판정에서 실제 실패한 경우와 치료로 회복된 경우를 구분한다.

### NIGHT-02 밤중 재생

- **사용자 확정 순서: 광대 능력 → 성공 시 사용자·대상자 영상 → 의사 능력 → 성공 영상 → 경비원 능력 → 성공 영상 → 마녀사냥꾼 능력 → 성공 영상 → 다음 낮/최종 결과.** 각 직업의 능력 처리와 영상 구간을 마친 후 다음 직업 화면으로 이동한다.
- **광대에게 죽은 대상이 의사에게 살아나면 킬 영상과 치료 영상 두 개를 모두 보고, 최종 결과는 생존이다.** 앞선 킬 영상을 치료 성공 때문에 취소하거나 생략하지 않는다.
- 밤 전체 판정 뒤 한꺼번에 영상을 보여주는 방식은 요구사항을 충족하지 않는다. 서버의 직업별 판정·연출 상태를 도입하고 기존 밤 끝 공동 판정 경로와 중복 사망·중복 보상이 발생하지 않게 정리한다.
- 연출 중 다음 직업 행동 시간이나 낮 투표 시간이 먼저 흐르지 않는다. 비수신자는 같은 구간 동안 비밀 정보 없는 대기 화면을 본다. 존재하지 않거나 행동할 수 없는 직업은 건너뛰되 상태가 멈추지 않는다.
- 광대 공격 직후에는 의사의 회복 가능성을 남겨 둔다. 치료 구간이 끝나기 전 최종 사망·승패·전적을 확정해 게임을 종료하지 않는다. 임시 사망/회복 대기 상태와 최종 사망을 구분하여 모델링한다.
- 의사가 같은 밤 공격당해 회복 대기 상태이면 자기 치료를 허용한다. 회복된 특수 직업은 같은 밤 자신의 후속 턴에 행동할 수 있다. 사망한 대상자도 연결 중이면 본인에게 허용된 영상을 수신한다. 같은 사용자가 사용자·대상자이면 동일 사건 영상은 한 번만 재생한다.
- 영상 완료·오류·건너뛰기·미응답 상한 이후 진행한다. 한 명의 재생 실패가 전원 게임을 무한히 막지 않게 한다.
- 게임 ID·밤 번호·사건 ID로 중복 재생을 막고 새로고침·재접속 복구 정책을 둔다. 여러 사건은 승인된 순서로 큐 처리한다.
- 게임이 끝나는 밤에도 필요한 치료 가능성·연출이 잘리지 않고 최종 결과로 이동한다. 낮 재판 처형 영상은 유지하고 같은 밤 사건을 다음 낮에 다시 재생하지 않는다.
- 로컬 public에서 킬 영상 2경로만 확인됐다. 경비원·의사·마녀사냥꾼 전용 영상은 사용자가 제공하기로 했다. 연결 구조·누락 처리까지 준비하되 실제 제공 파일 연결과 최종 재생 검증은 자료 수령 후 수행한다. 임시 연출을 최종 영상 완료로 간주하지 않는다.
- 완료: 각 역할 성공·실패, 킬→치료 두 연출 후 생존, 미치료 최종 사망, 복수 역할, 중복 이벤트, 재접속, 영상 오류·시간 초과, 마지막 밤 종료, 다음 역할/낮 타이머 시작 시점을 서버/브라우저 양쪽에서 확인한다.

## 12. Pluto 작업 분할·전달 절차

- 검토 문서는 배치 입력으로 직접 사용하지 않는다. Pluto는 `##` 제목을 전부 작업으로 해석하여 정책 표나 승인 안내까지 실행하려 할 수 있다.
- 별도 JSON 초안에는 `slices`만 두었다. 아직 실행 가능한 `requirements` 배열이 없으므로 실수로 batch에 넘겨도 유효 입력으로 파싱되지 않는다.
- 승인 순서: 경계 답변 반영 → 최종 명세/승인 범위 제시 → 사용자 실행 승인 → 실행용 JSON 확정 → daemon 상태·기존 작업 확인 → 배치 등록.
- 실행용 JSON은 각 작업에 공통 계약·선행 산출물·완료 기준을 포함한다. 문서 머리말에만 중요한 규칙을 두지 않는다.
- 번호는 기존 참조를 보존한다. 새 계정 복구는 F-29이며 최종 인수 F-28보다 먼저 실행한다. 기본은 F-01~F-27 → F-29 → F-28의 의존 순서로 직렬 실행한다. 지갑→소유권→구매/보상→프로필, 경기 집계→업적→보상, **순차 밤 판정 규칙→임시 사망/치료→직업별 이벤트→영상/전환**을 순서대로 연결한다.
- 미확정 정책이 영향을 주는 작업은 실행용 입력에서 보류한다. 임의 값으로 가짜 성공을 만들거나 전체 작업을 승인된 것처럼 처리하지 않는다.
- 2026-09-09 확인 시 Pluto CLI 상태는 `stopped`. 이전 UI 배치는 RESULT done, 별도 L(DB3)·U(QA5)는 완료되지 않은 상태 파일이 남아 있다. 이번 조사에서는 시작·재개·등록·상태 수정하지 않았다.
- Pluto의 `batch`는 큐 등록 후 자동 실행·검증·merge까지 이어지고, 데몬이 없으면 자동 시작한다. 따라서 등록 자체가 실행 승인 대상이다.
- 예정 명령: `node C:/dev/pluto/packages/daemon/dist/src/cli.js batch C:/Users/minsa/jokertest <승인된-실행용-json>`.
