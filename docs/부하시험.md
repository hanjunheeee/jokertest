# 부하 시험 쓰는 법

가짜 사용자가 화면과 같은 순서로 움직임: 로그인 → 소켓 접속 → 방 만들기·코드 입장 → 준비 → 시작 → 낮 채팅·투표 → 재판 표 → 밤 행동 → 판 끝 → 판 나가기.
코드: `backend/scripts/loadtest/` (run.js 입구, bot.js 사용자 한 명, game.js 판 하나, accounts.js 계정, target.js 주소 검사, stats.js 숫자)

## 1. 로컬에서 작게 (먼저 이것부터)

```bash
# 터미널 1: 서버 (로그인 요청 수 제한 늘리고, 서버 숫자 보게 내부 열쇠 넣기)
cd backend
INTERNAL_API_KEY=<32자 넘는 아무 글자> LOGIN_IP_MAX=1000 PORT=4711 node index.js

# 터미널 2: 판 2개 × 5명
cd backend
LOADTEST_INTERNAL_KEY=<같은 글자> node scripts/loadtest/run.js --target http://127.0.0.1:4711 --games 2 --players 5
```

- 로컬은 계정을 스크립트가 직접 만듦: `loadtest+1@example.test` … , 비번은 실행 때 무작위(화면·파일에 안 남음), 가입처럼 기본 아이템 지급까지 해 둠, 끝나면 지움 (지난번에 덜 지운 것도 같이)
- 로컬 DB(`DATABASE_URL` 호스트가 localhost·127.0.0.1)일 때만 만듦, `NODE_ENV=production`이면 거부
- 사용자 50명 넘게 돌릴 땐 서버를 `LOGIN_IP_MAX`를 크게 해서 켜기 (로그인은 IP 하나당 10분에 50번 제한)

## 2. 설정값

| 설정 | 기본 | 뜻 |
|---|---|---|
| `--target` | `http://127.0.0.1:4000` | 대상 주소 |
| `--mode` | `fixed` | `fixed` 판 N개 한 번에 / `step` 단계 올리기 |
| `--games` `--rounds` | 2 · 1 | fixed: 동시 판 수 · 몇 바퀴 |
| `--players` | 5 | 판당 인원 (4~10, 운영 규칙은 5~10) |
| `--stages` `--hold-min` | `1,5,10,20,50` · 3 | step: 단계별 동시 판 수 · 단계마다 유지 분 |
| `--max-p95-ms` `--max-error-rate` | 500 · 0.01 | step: 이 기준 넘으면 멈춤 |
| `--poll-ms` | 1000 | 판 상태 다시 묻는 간격 (화면 새로고침 흉내) |
| `--chat-chance` | 0.5 | 낮마다 채팅할 확률 |
| `--ramp-ms` | 50 | 사용자 접속 사이 간격 |
| `--timeout-ms` | 10000 | 답 기다리는 시간 (넘으면 오류) |
| `--game-max-min` | 15 | 판 하나 최대 시간 |
| `--accounts` | 없음 | 계정 목록 파일 (실서버용) |
| `--internal-key` | `LOADTEST_INTERNAL_KEY` | 서버 `INTERNAL_API_KEY`, 있으면 서버 메모리·이벤트 루프 지연·접속 수도 같이 봄 |
| `--frontend-origin` | `LOADTEST_FRONTEND_ORIGIN` | 소켓 Origin 헤더. 로컬 대상은 안 붙임, 로컬 아닌 대상은 안 주면 대상 주소를 붙임 |
| `--json` | 끔 | 마지막에 JSON 결과도 |

방 설정은 가장 짧은 시간(토론·투표·밤 30초), 광대 1명. 판 하나 대략 3~4분.

## 3. 결과 읽기

- **접속 성공률**: 로그인+소켓 접속 성공 / 시도
- **응답 시간 평균·95%·최대**: 답 받는 요청(방 만들기·준비·시작·투표·채팅·스냅샷 …) 왕복 시간
- **오류**: 시간 초과·500·접속 실패·`INTERNAL_ERROR` (서버 문제) → 오류율에 셈
- **규칙 거절**: 늦은 표·차례 아님 같은 정상 거절 → 오류율에 안 셈
- **끊김**: 내가 끊지 않았는데 끊긴 수
- **서버**: `/health`(내부 열쇠)·`/internal/live`를 5초마다 읽은 최대값

## 4. 실서버(시험 서버)에 돌릴 때

```bash
node scripts/loadtest/run.js --target https://api.staging.example.com \
  --i-know-this-is-not-production --accounts ./loadtest-accounts.json --mode step \
  --frontend-origin https://staging.example.com
```

- 대상은 **API 주소**(nginx API 사이트), 화면 주소는 `--frontend-origin`으로 (운영 모드 서버는 Origin 없는 소켓 거절)
- nginx 로그인 앞단 제한(IP당 1분 10번)에 봇 로그인이 걸림 → 시험 서버에서만 잠깐 늘리거나(`rate`·`burst`, 끝나면 되돌림) `--ramp-ms 6500`으로 천천히 로그인(250명이면 약 27분). 백엔드 `LOGIN_IP_MAX`도 크게
- 서버 숫자(`/internal/live`)는 nginx가 막음(허용 ip만) → 시험 PC 공인 ip를 시험 서버 `internal-allow.conf`에 잠깐 넣거나 `/health`(내부 열쇠) 숫자만 봄

- 로컬 아닌 주소는 `--i-know-this-is-not-production` 깃발 **그리고** `--accounts` 파일이 있어야 돎
- `LOADTEST_BLOCKED_TARGETS`(backend/.env, 쉼표로)에 운영 주소를 넣어 두면 깃발이 있어도 거부
- 실서버 계정은 스크립트가 안 만듦: 미리 가입해 둔 계정을 `[{"email":"…","password":"…"}]` 파일로. 파일 이름 `loadtest-accounts*.json`은 gitignore
- 운영 서버엔 돌리지 않음 (사용자 판에 영향)
- `NODE_ENV=production` 서버는 Origin 없는 소켓을 거절함 (DP-034). 화면 주소가 API 주소와 다르면 `--frontend-origin https://화면주소`(서버 `FRONTEND_URL`·`FRONTEND_MOBILE_URL` 중 하나)를 줘야 접속됨

## 5. 단계 올리기 (`--mode step`)

동시 판 1 → 5 → 10 → 20 → 50 … 단계마다 `--hold-min`분 동안 판을 계속 이어 돌림. 단계마다 표 한 줄:
동시 판 · 요청 수 · 평균/95%/최대 ms · 오류율 · 끊김 · 판 끝/실패 · 서버 rss · 이벤트 루프 지연 95%.
기준(95% > 500ms 또는 오류율 > 1%)을 넘으면 멈추고 **버틴 최대 동시 판 수**와 **판당 서버 메모리 대략**(rss 증가 ÷ 동시 판)을 출력.

## 6. 네이버 클라우드 서버 사양 정하는 법

1. **작은 사양 하나로 시작** (예: 2 vCPU · 4GB). 운영과 같은 방식(docker compose)으로 시험 서버를 띄움
2. 시험 서버에 `--mode step --stages 1,5,10,20,30,50 --hold-min 5`로 돌림 → **버틴 최대 동시 판 수(A)** 와 **판당 메모리(M)** 를 적음
3. 예상 동시 접속(사람 수 P)을 판 수로 바꿈: 필요 판 수 = P ÷ 판당 인원(보통 8). 대기실·로비 사람도 있으니 넉넉히
4. **여유 2배**: 필요 판 수 × 2 ≤ A 이면 그 사양으로 충분. 모자라면 한 단계 위 사양으로 다시 2번
5. 메모리: 판당 메모리 M × 필요 판 수 × 2 + 기본 사용량(빈 서버 rss, 보통 100MB 안팎) + DB(같은 서버면 1GB 이상)

주의:
- **Node는 한 프로세스가 CPU 1코어만 씀**. 게임 판 상태가 프로세스 메모리에 있어서 프로세스를 여러 개로 못 나눔 → 코어 수보다 **1코어 성능(클럭)** 이 중요. vCPU 2개면 하나는 Node, 하나는 DB·OS 몫으로 보면 맞음
- 이벤트 루프 지연 95%가 50ms를 자주 넘으면 CPU가 한계 (응답 시간보다 먼저 올라감)
- 시험하는 컴퓨터도 한계가 있음: 사용자 수백 명이면 시험 쪽 CPU를 같이 보고, 모자라면 다른 컴퓨터 여러 대에서 나눠 돌림
- 판당 메모리는 위 측정값을 씀 (아래 표에 적어 둠)

| 날짜 | 서버 | 판당 인원 | 버틴 동시 판 | 판당 메모리 | 메모 |
|---|---|---|---|---|---|

## 7. 2026-11-09 로컬 docker 구성

- 구성: `docker compose`(운영과 같은 nginx 이미지·백엔드 이미지·MySQL 8.4 컨테이너), 봇은 nginx 거쳐 `http://api.localhost:8080`(로그인·소켓 다 nginx 통과)
- 운영과 다른 점: `NODE_ENV=development`(http 로그인), 시험 동안만 nginx 로그인 앞단 제한을 늘린 설정 끼움(봇 수백 명이 IP 하나), 백엔드 `LOGIN_IP_MAX` 크게. 나머지 nginx 설정은 저장소 그대로
- 덧붙임 compose 파일은 저장소 밖에만 둠(키는 `backend/.env`, DB 주소는 루트 `.env` 호스트 `db`), DB 컨테이너는 안 건드림(`up --no-deps backend frontend`)
- 방식: `--mode step --players 5 --hold-min 2.5`, 단계마다 판을 처음부터 동시에 시작(가장 나쁜 몰림), 봇은 1초마다 판 상태 물음

- 결론: **이 PC 기준 버틴 최대 동시 판 50판(250명)**. 다만 판을 동시에 여럿 차리면 입장·준비가 20판부터 1초 넘게 늦어짐. 게임 중(투표·채팅·밤 행동·상태 묻기)은 50판에서도 95% 170ms 아래
- 숫자가 실서버와 다를 수 있음: 봇·DB·백엔드가 같은 PC(docker는 WSL2 가상 머신 안). 이번엔 PC CPU가 남아서 봇 쪽이 막은 건 아님. 반대로 이 PC 코어 하나(Ryzen 5700X)가 클라우드 vCPU 하나보다 빠를 수 있어 실서버가 더 낮게 나올 수도 있음 → 배포 직전 실서버에서 꼭 다시(10번)

- **로그 파일 쓰기는 동기**(`utils/logFile.js` `fs.writeSync`), console 출력이 전부 파일로도 감 + 줄마다 비밀값 가리기 정규식 4개

- 문제 2: 소켓이 웹소켓 말고 polling(`transport=polling`)도 받음(200). 화면은 웹소켓만 씀

### 줄일 수 있는 후보 (효과 큰 순)

1. **sequelize 질의 로그 끄기**(운영 `logging: false`, 필요하면 느린 질의만) → 포함 7.8% + 표준 출력 쓰기 몫, 로그 양도 크게 줆

## 9. 메모리 8GB 서버면 몇 판까지 (2026-11-09 측정값으로 계산)

- 판(5명)당 메모리: 판 상태 rss 0.8MB + 사람 5명 × 0.21MB ≈ **약 2MB**로 넉넉히(힙만 보면 판당 약 0.5MB)
- 빈 백엔드 약 100MB, nginx 약 25MB(측정 22MB), MySQL 컨테이너 약 1GB(측정 1.01GiB, 기본 버퍼)

| 경우 | 8GB에서 빼는 것 | Node가 쓸 수 있는 것 | 메모리로 되는 판 |
|---|---|---|---|
| (a) DB 같은 서버 | OS·docker 1GB + nginx 0.05GB + MySQL 1.5GB + 여유 20% 1.6GB | 약 3.8GB | 약 1,900판(9,500명) |
| (b) DB 따로 | OS·docker 1GB + nginx 0.05GB + 여유 20% 1.6GB | 약 5.3GB | 약 2,600판(13,000명) |

- Node 힙 한도: 따로 안 주면 V8이 기계 메모리로 정함(이 PC는 20GB 보여서 4,144MB, 8GB 서버면 대략 2GB). 판당 힙 0.5MB면 2GB로도 약 3,500판이라 메모리보다 CPU가 훨씬 먼저 막힘
- 그래도 정해 두기 권함: (a) `NODE_OPTIONS=--max-old-space-size=2048`, (b) `--max-old-space-size=3072` (rss는 힙보다 크게 나와서 남는 메모리의 60% 안쪽)
- **CPU로는**: 게임 중 백엔드 CPU 중간값 50판 35%(코어 하나 기준) → 판당 약 0.7% → 코어 하나 다 쓰면 대략 100~140판. 판을 한꺼번에 차릴 때는 20판부터 코어 하나를 잠깐 다 씀(114%), 70판 동시 시작에서 무너짐. 여유 30% 두면 **안정 약 50~70판**
- (줄인 뒤 새 숫자로 다시 한 계산은 11번) **결론: CPU가 먼저 막힘**(약 50~70판, 메모리는 약 1,900판까지 남음) → 8GB보다 **코어 하나 빠른 서버**가 중요, 메모리는 2~4GB로도 충분. 8번 후보 1·2를 고치면 CPU 몫 크게 줆
- 이 PC 숫자의 한계: 봇이 같은 PC(이번엔 PC CPU 남아 봇이 막진 않음), docker가 WSL2 안, 봇이 1초마다 상태를 물어 실제 화면보다 사건 수가 많을 수 있음(세션 확인 질의도 그만큼 많음) → CPU 숫자는 비관적일 수 있음, 실서버에서 다시 재서 고침

### 어디가 무거운가 (줄인 뒤)

- CPU 프로파일(`reports/전수조사_2026-11-09/perf/cpu-after-70games-setup.cpuprofile`, 70판을 한꺼번에 차리는 90초): 바쁜 시간 **12%**(전 50판 게임 중 42%). sequelize 0.9%·lodash 0.2%·mysql2 0.2%(전 15%·5.5%·1.8%), 질의 로그·로그 파일 쓰기는 목록에서 사라짐
- 남은 큰 몫: 판 상태 묻기 답(봇이 1초마다 물음) 보내기 약 5% — 소켓 쓰기(writev)·socket.io 인코딩. 게임 규칙 계산은 여전히 1% 안팎
- DB 질의: 사람·판이 늘어도 판당 초당 약 0.7~0.8개(전 10~16개), 노는 접속자 몫(사람마다 5초에 2개)은 5초에 1개(전원 한 번에)로
- 남은 느린 곳
  - 코드 입장 95%: 50판 약 1초·100판 1.5초 (전 5.3초). 입장마다 계정 읽기 + 기본 아이템 확인(장부·보유·장착 3질의)을 사람마다 따로 함 → 판 여럿 동시에 차리면 DB 줄이 섬
  - 시작 95%: 50판 1.7초·100판 2.9초 (전 50판 1.6초, 거의 그대로). 시작 때 5~10명 장착·통계 읽기·판 기록 쓰기가 한꺼번에 몰림
  - 판 차리기 몰림은 "동시에 시작"이라는 시험 방식의 가장 나쁜 경우. 실제로는 판 시작이 흩어짐
  - 70판 동시 시작에서 전엔 실패한 판이 방 만들기를 퍼부어 무너졌음(시험 도구가 실패 뒤 안 쉼) — 이번엔 실패가 안 나서 그 길을 안 탐, 도구 문제는 그대로

### 8GB 서버 계산 다시 (줄인 뒤 숫자)

- 메모리: 100판·500명에서 백엔드 rss 약 340MB(빈 서버 약 140MB) → 판(5명)당 약 2MB, 9번 계산 그대로 (a) DB 같은 서버 약 1,900판 · (b) DB 따로 약 2,600판
- CPU: 게임 중 백엔드 CPU 중간값 100판·500명에서 코어 하나의 약 14% → 판당 약 0.14%. 코어 하나 70%까지 쓰면 어림 **약 500판(2,500명)**, 판을 한꺼번에 차릴 때 잠깐 94%까지 오름 → 여유 두면 **약 300~400판**(전 계산 50~70판)
- 결론: CPU 한계가 크게 밀려 메모리·CPU 둘 다 이 PC로 잰 100판보다 훨씬 위. 실제 한계는 시험 서버에서 봇을 다른 컴퓨터 여러 대로 나눠 다시 재야 앎(10번). 8GB면 CPU 2코어로도 수백 판 어림, DB는 따로 두는 게 판 차리기 몰림(DB 줄)에 유리
- 이 PC 숫자의 한계는 9번과 같음 (봇·DB·백엔드가 같은 PC, docker가 WSL2 안, 봇이 1초마다 상태를 물음)
