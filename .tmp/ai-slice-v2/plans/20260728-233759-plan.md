# GameSession 종료 및 새 방 재진입 복구

## 기준점

- 브랜치: `game-session-exit-recovery`
- 기준 커밋: `29ab080`
- 현재 정책상 참가자 한 명의 Socket disconnect는 전체 GameSession을 즉시 종료한다.
- 브라우저 수동 테스트에서 한 계정이 인게임 화면에서 뒤로 가면 모든 참가자의
  프런트는 게임 종료 상태가 되지만 이후 새 방 생성 흐름이 정상적으로 동작하지 않았다.

## 목표

한 참가자가 인게임에서 명시적으로 이탈하거나 연결이 끊기면 전체 GameSession을
정확히 한 번 종료하고 관련 서버·Socket·프런트 상태를 완전히 정리한다. 종료된 모든
사용자는 로비에서 새 방을 직접 생성하거나 다른 방에 즉시 참가할 수 있어야 한다.

## 확정 정책

- 한 참가자의 이탈 또는 disconnect는 전체 게임을 즉시 종료한다.
- 모든 참가자는 일반 로비로 돌아간다.
- 이전 대기방을 자동으로 복원하거나 기존 참가자를 자동 재결합하지 않는다.
- 사용자는 종료 직후 새 방을 직접 만들거나 참가한다.
- 명시적 이탈과 disconnect는 같은 core 종료 계약을 공유한다.
- 명시적 이탈 직후 뒤늦게 도착한 disconnect는 멱등한 no-op이어야 한다.
- 이전 세션의 늦은 종료 요청이 같은 사용자가 참여한 새 세션을 종료하면 안 된다.

## 먼저 확인할 실제 원인

현재 코드를 읽어 다음 상태가 게임 시작·종료 과정에서 어떻게 변하는지 추적한다.

- GameSession registry
- player-to-session registry
- room-to-session registry
- matchmaking의 `gameRooms`
- matchmaking의 `playerRoom`
- matchmaking queue
- Socket.IO GameSession channel과 대기방 channel
- 프런트 ingame store와 로비/방 store
- `game_ended` 수신 후 라우팅과 상태 초기화

추측으로 새 정리 코드를 중복 추가하지 말고, 새 방 생성을 막는 실제 잔존 상태를
테스트로 먼저 고정한다.

## 서버 계약

### 명시적 이탈

필요하다면 인증된 Socket 이벤트를 추가한다.

```text
leave_game_session
payload: { gameId }
ack success: { ok: true }
ack failure: 기존 정규화된 { ok: false, code, message } 계약
```

- UUID는 payload에서 받지 않고 `socket.data.user.uuid`만 사용한다.
- 요청 gameId는 타입과 trim을 검증한다.
- 실제 registry의 canonical session ID와 일치해야 한다.
- payload의 roomId, role, team, nickname 등은 신뢰하지 않는다.
- callback 존재 여부 및 payload 검증 순서는 기존 Socket 계약과 일치시킨다.
- 성공 및 이미 동일 세션이 종료된 경쟁 상황을 안전하게 멱등 처리한다.

### 세션 종료

- GameSession 관련 registry를 참가자 전원 기준으로 정리한다.
- 활성 GameSession 참가자의 create_room·코드/공개방 join·queue 진입은 현재
  계약대로 계속 허용한다(`backend/socket/__tests__/matchmaking.test.js:1308-1317`
  유지, 진입 가드는 도입하지 않는다). 대신 세션 종료 core가 참가자 전원의 현재
  matchmaking 소유 상태를 필수로 정리한다. Room 항목 자체는 소유자 UUID만으로
  통째로 삭제하지 않는다 — 그 Room에는 세션과 무관한 다른 사용자가 이미 참가해
  있을 수 있으므로, 종료된 참가자만 기존 방 퇴장 경로
  (`backend/socket/matchmaking.js:789-814`의 `removeFromRoom`/host 이전 로직)로
  제거하고 queue 등록을 취소한다. 비세션 참가자가 남아 있으면 기존 계약대로
  Room과 설정을 보존하고 host를 이전한다. 게임 시작 시 기존 Room 매핑이 이미
  삭제되므로(`backend/socket/matchmaking.js:741-743`), 이 정리로 끊어지는
  playerRoom 연결은 그 세션이 진행되는 동안에만 새로 생성된 것이다. 이 정리는
  종료 core 실행과 동일한 동기 구간에서만 수행해, 종료 처리가 끝난 뒤에 생성된
  Room B를 건드리지 않게 하고 `pendingRoomTransitions`와의 경쟁을 테스트한다.
  이 정리는 참가자별 현재 roomId와 인증된 소유 Socket을 먼저 스냅숏한 뒤,
  참가자 전원의 registry(`gameRooms`/`playerRoom`/queue) 정리를 모두 완료하고,
  그다음 각 참가자의 Socket `leave(roomId)`와 host 변경·퇴장·공개 목록 emit을
  참가자별로 독립적으로 격리해 실행한다. 한 참가자의 leave/emit 실패가 다른
  참가자나 registry 정리를 막지 않는다.
- 참가자 Socket을 종료된 GameSession channel과 matchmaking Room channel 모두에서
  제거한다.
- 참가자 전체에 `game_ended`를 정확히 한 번 전달한다.
- 알림 emit 또는 channel 정리가 실패해도 registry 정리는 완료한다.
- 정리 이후 동일 사용자의 새 방 생성과 참가가 즉시 가능해야 한다.
- 종료된 세션 A의 늦은 요청이 새 세션 B를 건드리지 않도록 canonical gameId로
  ABA를 방지한다. 게임 시작 시 각 참가자 Socket에 canonical gameId를
  결합해 두고(예: `socket.data.activeGameId`), 명시적 이탈이 성공해도 이 결합은
  지우지 않고 A를 가리킨 채로 둔다. 같은 Socket이 이후 새 세션 B를 시작할 때만
  결합값을 B로 덮어쓴다. 결합이 없는 Socket의 disconnect는 종료 core를 호출하지
  않는다.

### disconnect

- 기존 disconnect 즉시 전체 종료 정책을 유지한다.
- 명시적 이탈과 동일한 종료 core를 호출한다.
- disconnect는 UUID만으로 세션을 조회하지 않고, Socket에 결합해 둔 canonical
  gameId를 `expectedGameId`로 종료 core에 전달한다. 세션 A를 명시적으로 종료한
  Socket의 disconnect가 지연되어 같은 UUID가 다른 Socket으로 세션 B에
  재참가한 뒤 도착해도, 결합값이 A를 가리키므로 B를 잘못 종료하지 않는다.
  동일 Socket에서 A 종료 후 B가 시작되면 결합이 B로 갱신되므로 그 이후
  disconnect는 정상적으로 B를 종료한다.
- 기존 `matchmaking.onDisconnect`도 UUID만으로 `playerRoom`을 조회해 제거하므로
  같은 ABA에 노출된다(`backend/socket/socket.js:49-56`이 모든 disconnect에서
  무조건 호출하고, `backend/socket/matchmaking.js:95-98`, `789-814`의
  `removeFromRoom`이 현재 `playerRoom`을 읽어 삭제한다). 이 경로도 Socket ID
  또는 결합된 방 세대·`roomId`로 조건부 정리하도록 범위에 포함한다.
- 명시적 이탈과 disconnect가 연속 또는 중첩되어도 종료·방송은 한 번뿐이다.
- 이미 종료된 사용자의 disconnect는 조용한 no-op이다.

## 프런트 계약

- `InGameTopControls`(`frontend/src/domains/game/ingame/components/controls/InGameTopControls.jsx`)에
  명시적 나가기 버튼을 추가해 확인 후 `leave_game_session`을 전달한다.
- `InGamePage` 라우트에 머무는 동안의 앱 내부 뒤로가기(라우터 history back, POP
  네비게이션)는 같은 확인 후 동일 이벤트를 전달하도록 가로챈다. 이 차단
  predicate는 POP 이탈만 가로채며, 성공 ack·`game_ended`에 따른 로비 이동
  (PUSH/REPLACE)은 차단하지 않는다. 실제 탭 종료·새로고침처럼 가로챌 수 없는
  이탈은 별도 처리하지 않고 기존 disconnect fallback에 맡긴다.
- 성공 ack를 받은 뒤 로비로 이동하는 것을 기본으로 한다.
- timeout·Socket 종료 경쟁에서도 로컬 상태가 과거 게임으로 복구되지 않는다.
  늦은 ack 판별은 서버 응답이 아니라 요청 전송 시점에 캡처해 둔 정규화된
  gameId와 현재 store gameId를 비교해 수행한다(ack는 `{ ok: true }`만 포함하고
  canonical gameId를 담지 않는다).
- 서버의 `game_ended`가 먼저 도착해도 동일하게 한 번만 초기화하고 로비로 이동한다.
- 다른 참가자도 `game_ended` 수신 후 인게임 상태를 비우고 로비로 이동한다.
- 이전 gameId의 늦은 ack/event가 새 방 또는 새 게임 상태를 지우지 않는다.
- 실제 브라우저 탭 종료처럼 ack를 기다릴 수 없는 경우 disconnect 종료가 fallback이다.
- 자신의 Socket이 disconnect되는 경우 다른 참가자와 달리 `game_ended`를 받지
  못하므로 별도로 처리한다. 리스너는 자신이 등록될 때(effect 실행 시점)의 Socket
  인스턴스와 gameId를 함께 캡처해 두고, disconnect 발생 시 (1) 그 Socket이 여전히
  현재 활성 Socket인지(`getSocket() === socket`)와 (2) 캡처한 gameId가 현재 store
  gameId와 일치하는지를 모두 확인한 뒤에만 인게임 store를 비우고 `/multiplay`로
  replace 이동한다. Socket이 이미 교체된 뒤 오래된 리스너에 지연 도착한
  disconnect는 store gameId만 비교하면 이미 바뀐 현재 값과 우연히 같아 보일 수
  있으므로, Socket 신원 확인 없이 gameId 비교만으로 판단하지 않는다.
- 명시적 이탈 ack 성공, `game_ended` 수신, 자신의 disconnect 정리는 모두 같은
  종료 finalizer를 거쳐 인게임 store뿐 아니라 matching store
  (`frontend/src/domains/game/matching/store/matchingStore.js`)의 `isInRoom`·
  `roomId`·참가자 목록·검색 상태도 함께 초기화한다. 서버가 활성 세션 중 만든
  Room B에서 참가자를 이미 제거했다면, 클라이언트에 남은 matching 상태가
  `useMatchmakingSearch.js`의 라우팅 판단과 어긋나지 않게 한다.
- 새 방 생성·참가를 커밋하는 `useGameSetupPage.js`(방 만들기)·
  `useRoomInvitePage.js`(코드 참가)·`usePublicRooms.js`(공개방 참가)의 `setRoom`
  호출은 matching store를 설정하기 전에 인게임 store의 이전 gameId를 먼저
  무효화(null)한다. 두 store 설정 사이의 창에서 이전 세션 A의 지연 ack나
  `game_ended`가 도착해도 ingame gameId 비교가 더 이상 A와 일치하지 않으므로,
  방금 커밋한 Room B의 matching 상태를 지우지 않는다.
- 기존 조커 채팅, 밤 행동, 역할 정보의 listener cleanup을 회귀시키지 않는다.

## 자동 테스트

### Core

- 참가자 한 명 종료 시 참가자 전원의 GameSession registry 정리
- 반복 종료 멱등성
- 세션 A 종료 후 세션 B 생성 가능
- 세션 A의 늦은 종료 요청이 세션 B에 영향 없음
- 잘못된 gameId와 registry 불일치에서 상태 불변

### Socket

- 인증 UUID만 사용하는 명시적 이탈
- payload UUID/role/team/roomId 위조 무시 또는 거부
- 성공 ack는 `{ ok: true }`만 반환(canonical gameId는 서버 내부 로그·비교에만 사용)
- `game_ended` 정확히 한 번
- 명시적 이탈과 disconnect 중첩 시 정확히 한 번
- 세션 A 명시적 종료 → 다른 Socket으로 세션 B 시작 → A의 지연 disconnect가 B의
  registry·broadcast에 영향 없음(Socket 결합 기반 ABA 방지)
- 동일 Socket에서 세션 A 종료 → 세션 B 시작 → 이후 disconnect가 B를 정상 종료
- 기존 `matchmaking.onDisconnect` 경로에서 오래된 Socket A의 disconnect가 새 방 B,
  새 queue 항목, `pendingRoomTransitions`를 변경하지 않음
- callback throw, broadcast throw, channel cleanup throw 격리
- raw Error/message/stack과 비밀 역할 정보 로그 비노출
- 종료 직후 참가자별 새 방 생성 가능
- 종료 직후 새 방 코드 참가 가능
- 세션 종료 core의 matchmaking 정리는 세션 진행 중 생성된 Room/queue만 제거하고,
  종료 처리 이후 생성된 Room이나 다른 세션·`pendingRoomTransitions`에는 영향
  없음
- 세션 A 참가자가 만든 Room B에 비참가자 Q가 참가한 상태에서 A 종료 시 Q와
  Room B가 보존되고 host가 이전됨(방 전체 삭제 금지)
- 세션 A 참가자를 Room B에서 제거할 때 해당 참가자의 Socket도 Room B channel에서
  leave됨(Map 정리만으로 끝나지 않음)
- 한 참가자의 Room leave/emit 실패가 다른 참가자·registry 정리를 막지 않음(격리)
- 다른 활성 세션에 영향 없음

### Frontend

현재 프런트 테스트는 DOM 없는 `node --test`만 사용한다(jsdom·Testing Library
없음). 아래 항목 중 이탈 요청·stale 판단·라우트 차단 로직은 순수 함수/컨트롤러로
추출해 `node:test`로 검증하고, 실제 버튼 클릭·JSX 렌더링·라우터 전환 배선은
자동 테스트 대상에서 제외해 브라우저 테스트로만 확인한다.

- 나가기 컨트롤러 호출 시 `leave_game_session` 전송
- 인게임 라우트 이탈 판단 로직이 뒤로가기 상황에서 확인 후 `leave_game_session`
  전송을 트리거함
- 현재 gameId 요청만 종료 결과를 반영
- 늦은 이전 요청 ack 무시(요청 시점에 캡처한 gameId와 현재 store gameId 비교)
- `game_ended`와 명시적 이탈 ack 경쟁에서 초기화 한 번
- 자신의 Socket disconnect 시 `game_ended` 없이도 인게임 store 정리 및 로비 이동
- 이전 Socket A의 리스너가 아직 살아있는 채로 Socket B와 게임 B로 전환된 뒤 A의
  지연 disconnect가 도착해도 Socket 신원 불일치로 B의 상태를 지우지 않음
- gameId 변경·Socket 교체·disconnect·unmount 방어
- 로비 전환 후 인게임 store 초기화
- `game_ended`·이탈 ack·자신의 disconnect 정리 각각에서 matching store의
  `isInRoom`·roomId·참가자 목록·검색 상태도 함께 초기화됨
- 새 방 생성·참가로 matching store를 Room B로 설정한 직후 도착한 이전 세션 A의
  지연 leave ack/`game_ended`가 matching store·라우팅을 변경하지 않음

## 브라우저 테스트

1. 4개 계정으로 게임을 시작하고 NIGHT까지 진입한다.
2. 한 계정에서 애플리케이션 뒤로가기 또는 나가기를 실행한다. 확인 대화상자를
   취소하면 인게임 화면에 남고 아무 이벤트도 전송되지 않는지 확인하고, 다시
   실행해 확인을 누르면 나가기 버튼과 뒤로가기(POP) 양쪽 모두 `leave_game_session`
   전송 후 ack를 받아 로비로 이동하는지 확인한다.
3. 네 계정 모두 로비로 이동하고 동일 게임 화면이 남지 않는지 확인한다.
4. 종료 방송이나 오류 메시지가 중복 표시되지 않는지 확인한다.
5. 기존 방이 자동 복원되지 않는지 확인한다.
6. 이전 방장 계정이 새 방을 직접 생성한다.
7. 나머지 세 계정이 새 방에 정상 참가한다.
8. 새 방에서 ready 및 게임 시작이 정상 동작하는지 확인한다.
9. 새 게임 시작 후 이전 gameId의 늦은 event가 새 게임을 종료하지 않는지 확인한다.
10. 별도 새 게임에서 브라우저 탭 하나를 닫아 disconnect fallback도 같은 결과인지
    마지막에 확인한다.

## 완료 조건

- 명시적 이탈과 disconnect 모두 전체 GameSession을 정확히 한 번 종료한다.
- 관련 서버 registry와 Socket channel에 종료된 세션 상태가 남지 않는다.
- 모든 참가자가 로비로 이동하고 인게임 상태가 초기화된다.
- 종료 직후 새 방 생성·참가·ready·게임 시작이 가능하다.
- 이전 세션의 늦은 종료가 새 세션에 영향을 주지 않는다.
- 기존 조커 채팅과 NIGHT 행동 계약이 회귀하지 않는다.
- 전체 테스트와 build가 통과한다.
- stage·commit·push는 자동화하지 않는다.

- 게임 결과·승패 판정
- 투표 집계·밤 결과·사망·NIGHT→DAY
